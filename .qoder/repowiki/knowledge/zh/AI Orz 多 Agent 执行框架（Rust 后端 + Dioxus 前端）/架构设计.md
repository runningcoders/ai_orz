采用 Cargo workspace 四模块划分：根 crate `ai_orz` 为应用入口（`src/main.rs` → `lib.rs::run`），按四层架构组织——`src/handlers`（Axum HTTP 适配层，按 hr/finance/system/project/organization/a2a/user 领域子目录拆分）、`src/producer`（外部 WS/SSE 轮询与定时任务生产者）、`src/consumer`（内部事件消费者，含 AOP stats、tool exec log、task event 等）、`src/service/{domain,dal,dao}`（Domain 编排 → DAL PO↔Entity 转换 → DAO 本地 SQLite/外部 API 出站，严格禁止 DAO→DAO、DAL→DAL、Domain→Domain）；横切基础设施集中在 `src/pkg`（AOP 队列、tool_registry、storage[fts5/hnsw/lance/vector]、stats、logging、jwt、request_context、process、monitoring 等）。`common` crate 通过 feature flag（sqlx/axum-integration/tokio-integration 等）向后端与前端共享 DTO、枚举、错误类型；`ai-orz-macros` 是独立 proc-macro crate，提供 `#[generate_http_handler]`（从 Params 结构体上的 `#[param(source="path|query|body")` 推导 Axum 提取器）、`#[derive(Params)]`、`#[register_handler_tool]`（将 handler 注册为 BuiltinToolFactory）、`#[derive(StatsEvent)]`、`#[derive(LogFields)]`，实现一份 IDL 同时生成 HTTP handler 与 LLM 工具调用参数。路由由 `src/router.rs` 集中装配，区分 public_routes / protected_routes（JWT + role 中间件），并通过 SPA Fallback 服务静态资源。启动流程在 `lib.rs::run` 中顺序完成：config → pkg init → service init → producer/consumer 注册 → base data 初始化 → AOP stats hook 注入 → AOP scheduler 启动 → axum server（带优雅停机信号处理）。
