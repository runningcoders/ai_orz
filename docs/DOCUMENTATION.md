# 文档编写与维护规范（Documentation Convention）

> 🎯 **定位**：文档规则 SSOT——三层文档（`A-设计` / `B-落地方案` / `C-知识`）的文件头、路径引用、RAG 卡图谱法则、章节模板与归档约定全量细则
> 状态：v3.0（2026-11-01 对齐 15 模块知识库；v2.1 的 `docs/wiki|design|plan` 四象限已废止）
> 触发场景：编写 / 修改 / 归档任何 `docs/` 文档、新增现状长文或 RAG 知识卡、修正文档引用路径时打开
>
> 关联文档：
> - [README.md](./README.md) — 知识库地图与运维手册（命令 / 查询配方 / 维护场景）
> - [AGENT_GUIDE.md](./AGENT_GUIDE.md) — 实现需求入口（流程 / 模块路由 / status 语义 / 反模式）
> - [../AGENTS.md](../AGENTS.md) — Agent 快速入门手册
> - [CODE_STANDARDS.md](./CODE_STANDARDS.md) — 编码规范 SSOT

> 🎯 **铁律**：代码是 SSOT（字段级细节跳源码），文档只承载代码无法表达的信息：设计动机、模块边界、影响面、扩展路径。

## 1. 强制文件头

三层文档的头部**格式不同**，因为消费方不同：`A/B` 要给程序读（索引、门禁、Agent 判断权威性），`C-知识` 要给人读。

### 1.1 `A-设计` / `B-落地方案` —— YAML frontmatter（机器可读，`make wiki-meta` 强制校验）

```yaml
---
kind: 设计决策            # 设计决策 | 落地方案
module: 02-Agent运行时    # 所在模块目录名，必须与实际路径一致
name: runtime_design      # 文件名（不含 .md）
title: Runtime Domain 设计 # 中文标题，索引展示用
status: 现行              # 见下表
scope:                    # 本篇涉及/覆盖的代码路径（可空数组）
- src/models/agent.rs
related:                  # 关联文档，相对 docs/modules/ 的路径（可空数组）
- 02-Agent运行时/A-设计/thinking_task_policy_engine_design.md
---
```

| 层 | 允许的 `status` | 语义 |
|---|---|---|
| `A-设计` | `现行` / `落地中` / `草案` / `已废弃` / `未标注` | 设计是否仍具权威性 |
| `B-落地方案` | `已完成` / `进行中` / `草案` / `已废弃` / `未标注` | 方案推进到哪 |

- **`未标注` 不是合法目标态**：它只是"作者还没声明"的诚实标记，`make wiki-meta` 会点名，Agent 见到它必须以 `C-知识` 为准。
- `status` 应能从正文显式信号推导（`状态：xxx` 行 / checkbox 完成度），别只写 frontmatter 而正文无据。
- **设计被取代不要删旧文**：旧篇标 `status: 已废弃`，新建 `status: 现行` 的替代文档，二者 `related` 互链——"为什么当初不那么做"本身是知识。

### 1.2 `C-知识` 文档 —— 分层头部

**现状长文**（`C-知识/<主题>.md`，用 `<cite>` 块声明引用）：

```markdown
# [主题名]（[所属层]）

<cite>
**本文引用的文件**
- [xxx_design.md](docs/modules/<模块>/A-设计/xxx_design.md)
- [xxx.rs](src/xxx/yyy.rs)
</cite>
```

**RAG 原子知识卡**（`C-知识/<卡名>/<卡名>.md`，用 YAML frontmatter）：

```yaml
---
kind: RAG 原子知识卡
name: <卡名，与目录名一致>
category: <两级分类，如「知识图谱与记忆沉淀 / 本体治理」>
scope:                      # 召回预过滤用，glob 友好
  - "src/service/dao/ontology/**"
source_files:               # 源码锚点 + 关联卡（相对仓库根）
  - "src/service/dao/ontology/mod.rs#L1-L60（DAO 入口）"
---
```

### 1.3 归档件

只加归档头，正文永不修改（见 §4 模板 D）。

## 2. 路径引用统一规范（强制执行，三环境通跳）

> 🎯 **核心原则：一律写「相对仓库根的相对路径」，永不写本机绝对路径，永不写 `file://` / `file:///` 伪协议。行号用 `#Lx-Ly` fragment（GitHub 原生兼容；IDE 降级为文件级跳转，可接受）。**

| 引用类型 | 唯一合法格式 | 例子 |
|----------|------------|------|
| 代码（行范围） | `[描述](路径#L起始-L结束)` | `[日志初始化](src/pkg/logging.rs#L15-L42)` |
| 代码（单行） | `[描述](路径#L行)` | `[UserRole 定义](common/src/enums/user.rs#L8)` |
| 代码（无行号） | `[描述](路径)` | `[初始迁移](migrations/20260420000000_initial.sql)` |
| 设计文档 | `[描述](docs/modules/<模块>/A-设计/xxx_design.md)` | `[日志设计](docs/modules/12-基础设施与部署/A-设计/logging_design.md)` |
| 现状长文 | `[描述](docs/modules/<模块>/C-知识/<主题>.md)` | `[日志系统](docs/modules/12-基础设施与部署/C-知识/日志管理系统.md)` |
| RAG 卡 | `[描述](docs/modules/<模块>/C-知识/<卡名>/<卡名>.md)` | `[日志宏卡](docs/modules/12-基础设施与部署/C-知识/基于 tracing 的结构化日志系统（宏 + 文件滚动 + JSONL 查询）/基于 tracing 的结构化日志系统（宏 + 文件滚动 + JSONL 查询）.md)` |
| 外部链接 | 直接写 http(s) | `[sqlx](https://docs.rs/sqlx)` |

**三环境行为**：
| 环境 | 行为 |
|------|------|
| GitHub 仓库页 | 相对链接自动解析为 `blob/<branch>/path#Lx-Ly` 并高亮行 ✅ |
| 本地 IDE | Cmd+Click 打开文件（fragment 被忽略，文件级跳转）⚠️ |
| 前端文档中心 | 导入期把 `./` `../` 归一化为仓库根相对 → 渲染期拼 GitHub blob + 点击拦截新窗口 ✅ |

**两个坑（都实际踩过）**：
- 路径含空格时必须写 `%20`（如 `CoreTool%20trait`）；中文字符原样保留。
- **路径含半角括号 `()` 的模块（`07-外部Agent(A2A)`、`10-异步基建(AOP)`）必须用尖括号形式** `[描述](<docs/modules/07-外部Agent(A2A)/00-INDEX.md>)`，否则 Markdown 在首个 `)` 处截断链接。

**相对写法（`./` `../`）**：允许写，但它是唯一需要构建期兜底的写法——文档中心的 md 副本被换成 `docs/modules/{hash}.md`，相对自身位置解析必然错，所以 `build.rs` 导入时用 `common::doc_link::normalize_repo_relative` 统一归一化（围栏代码块与行内代码里的示例链接不动）。新写文档仍建议直接写仓库根相对，少一层隐式解析；`..` 层数写错（越过仓库根）时归一化会原样保留，等于死链。

**红线（`make docs-lint` 必 fail）**：
- ❌ 本机绝对路径（`file:///Users/...` 或裸 `/Users/...`）
- ❌ `file://` 伪协议前缀
- ❌ 行号写 legacy 冒号格式 `path:15-42`（存量已迁移归零；分类器兼容解析但新文禁写）

**契约型代码块规则**：trait 签名/struct 字段/enum 变体/SQL schema/ASCII 图可留代码块，紧邻下方附 `> 当前实现：[xxx.rs#L12-L50](src/xxx.rs#L12-L50)`；实现快照型（函数体/控制流/命令）删代码块，改 `> 逻辑见：[func](src/xxx.rs#L288-L352)`。

## 3. 知识图谱节点组织与 RAG 卡拆分合并强制规范（强制执行）

> 🎯 **定位**：治理「增量构建知识库时，不查重直接新建，导致多张完全重复卡」的系统性问题。定义节点「合并 / 拆分 / 关联」的判定标准与标准写法。
>
> **适用范围**：`docs/modules/*/C-知识/` 下的现状长文节点 + RAG 原子知识卡节点。**任何新增 RAG 卡的动作都要先过本法则，再决定是「合并」还是「新建」。**

---

### 3.1 黄金法则（两条，优先级最高）

1. **优先合并**：候选主题 T 到来 → 先扫现存节点做相似度匹配，命中已有节点就**先尝试合并**。只有合并失败（颗粒度爆炸、视角完全不兼容）才考虑拆分建新节点。
2. **明确拆分 + 必连线**：确有关联但不适合合并时，才分开展示。拆分后必须在两张卡之间**建立显式关联声明**（`source_files[]` 互引 + §3 说明关系类型）。拆分不连线 = 两张孤立重复命中 = FAIL。

---

### 3.2 5 级决策算法（每个候选主题 T 必须走一次，不可跳过）

```
候选主题 T（来自代码改动或 A-设计 文档）
    │
    ▼
Step 0. 前置查重（必填分支，不可省略）
    扫 docs/modules/*/C-知识/ 全部 md：
      ① name 关键词模糊匹配
      ② category 精确匹配
      ③ scope[] glob 交集面积 >= 30%
    │
    ├── 命中 0 张 → 【Level 5：纯新主题】 → 直接新建卡 ✅
    │
    └── 命中 ≥ 1 张 → 按 Level 1~4 逐层判定（按顺序优先级从高到低）
            │
            ├── Level 1（完全重复）❌禁止新建，强制合并 + 删除副卡
            │   判定：scope[] 互为子集 AND §4 约束重叠率 > 90%
            │         AND 主题 T 是旧卡主题的同义词/不同措辞
            │   动作：把 T 独有源码锚点 → 旧卡 §2；T 独有硬约束 → 旧卡 §4；
            │         旧卡 YAML scope[]/source_files[] 取并集；
            │         T 的草稿副卡 → 直接删除（历史靠 git 追溯，不归档）；
            │         所有引用副卡路径 → 替换为旧卡路径。
            │
            ├── Level 2（主卡-子卡 层级包含）优先合并，合并不下才拆分
            │   判定：scope[T] ⊂ scope[旧卡]（真子集）
            │         （如「日志自动上下文字段注入」⊂「日志系统」）
            │   动作首选（合并）：T 内容合并进旧卡 §3 加编号小节 + §4 追加硬约束 +
            │                       §2 追加独有源码锚点
            │   动作备选（拆分，满足以下任一才允许）：
            │         a) 合并后主卡 §4 硬约束超过 15 条；或
            │         b) 旧卡 scope[] 与 T scope[] 实际是两个不相交主题的并集
            │   拆分后声明：
            │         主卡 §2 表格末行加：`细粒度拆解：[子卡名](docs/modules/<模块>/C-知识/子卡名/子卡名.md)`
            │         子卡 §3 开头加：`本卡是 [主卡名](docs/modules/<模块>/C-知识/主卡名/主卡名.md) 的 XX 模块细粒度展开`
            │         子卡 source_files[] 末尾追加主卡相对仓库根路径
            │
            ├── Level 3（总卡-视角细卡 分层/分视角）允许拆分，但必互相声明关联
            │   判定：scope[] 交集 30%-80%，是同一体系的不同层面
            │   典型模式：
            │     • 严格分层：身份凭证 Model 层 / Domain 层 / Handler 层（三张）
            │     • 协议三角：A2A 协议层 / Client 端 / Server 端（三张）
            │     • 双端视角：DuckDB 统计写入侧 / StatsHandler REST 查询侧（两张）
            │     • 双端实现：AOP 框架层 / Domain 事件消费者全链路业务层（两张）
            │   动作：允许每张独立建卡，不合并
            │   必做关联声明（每张都写，缺一张 = FAIL）：
            │     • 每张卡 source_files[] 末尾追加其余几张兄弟卡的相对仓库根路径
            │     • 每张卡 §3 架构约定开头加一句：
            │       「本卡与 [兄弟卡A名](path) + [兄弟卡B名](path) 构成 XX 体系的
            │         YY / ZZ 互补视角；按 DOCUMENTATION §3 Level 3 保留平行卡」
            │
            └── Level 4（总卡-细卡 总分结构）保留主总卡 + 子细卡，并互相引用
                判定：scope[旧卡] ⊃ scope[T]（真超集），旧卡 §3 已有总分说明
                典型模式：Memory 搜索三合一（总卡）+ recommend_seed_nodes 三因子推荐
                        + knowledge_graph traverse BFS/DFS（两张细卡）
                动作：旧卡保留作为「总卡」，T 新建作为「细粒度子卡」
                必做关联声明：
                  • 总卡 §2 关键文件表末尾加一行：`细粒度拆解卡：[子卡名](docs/modules/<模块>/C-知识/子卡名/子卡名.md)`
                  • 子卡 §3 开头加：`本卡为 [总卡名](docs/modules/<模块>/C-知识/总卡名/总卡名.md) 描述的 XX 体系中
                                       YY 模块的细粒度独立召回卡`
                  • 子卡 source_files[] 追加总卡相对仓库根路径
```

**红线**：跳过 Step 0 前置查重 → 直接新建 RAG 卡 = FAIL。Level 1 完全重复场景下仍然新建卡（即使写了 Overlaps 说明）= FAIL。Level 2/3/4 拆分后**没写关联声明** = FAIL，视为两张孤立重复卡，需回退修正。

### 3.3 四种节点关系类型声明速查表（强制对齐用词）

| 关系类型 | 判定 | 主卡/旧卡侧声明位置 + 固定句式 | 子卡/副卡/兄弟卡侧声明位置 + 固定句式 |
|---|---|---|---|
| **①完全重复**（Level 1） | scope 全等 + 主题同义 + §4 重叠率>90% | 主卡吸收合并，§2/§4 追加内容；无需额外声明。副卡**直接删除**（不归档，历史靠 git 追溯）。所有引用副卡路径 → 替换为主卡路径。 | （副卡不再召回，已删除） |
| **②主卡-子卡**（Level 2） | scope[子] ⊂ scope[主]，真包含层级 | 主卡 §2 表格末行：`细粒度拆解：[子卡名](docs/modules/<模块>/C-知识/子卡名/子卡名.md)` | 子卡 §3 首句：`本卡是 [主卡名](...) 的 XX 模块细粒度展开`；子卡 `source_files[]` 末尾追加主卡相对仓库根路径 |
| **③总卡-视角细卡**（Level 3） | scope 交集 30-80%，同一体系不同层面/分层 | 每张卡 §3 首句统一句式：`本卡与 [兄弟卡A名](A路径) + [兄弟卡B名](B路径) + … 构成 XX 体系的 YY/ZZ/… 互补视角；按 DOCUMENTATION §3 Level 3 保留平行卡`；每张卡 `source_files[]` 末尾追加**所有**兄弟卡相对仓库根路径（互相完整闭环）| （与左列相同，Level 3 是对称兄弟关系，每张写法一致）|
| **④总卡-细卡**（Level 4） | scope[总] ⊃ scope[细]，总卡有总分结构 | 总卡 §2 表格末行：`细粒度拆解卡：[细卡1名](path) + [细卡2名](path) + …` | 细卡 §3 首句：`本卡为 [总卡名](...) 描述的 XX 体系中 YY 模块的细粒度独立召回卡`；细卡 `source_files[]` 追加总卡相对仓库根路径 |

> 路径占位 `<模块>` / `<卡名>` 请替换为真实值；卡的路径形态恒为 `docs/modules/<模块>/C-知识/<卡名>/<卡名>.md`。

### 3.4 工具链约定

1. **先按 §3.2 走完 Step 0 查重**，把判定结论（Level 1~5）写进提交说明或任务汇报，再动手写卡。
2. **写完必须过门禁**：`make wiki-index && make wiki-check`（新增卡会进索引；`A/B` 层还会被 `--meta` 校验 frontmatter）。
3. **新增 `A-设计` / `B-落地方案` 时**：带 frontmatter，写完即冻结意图，不写指向 `C-知识` 的链接。

> **⚠️ ⛔ 明确禁止的反模式**：
> - ❌ 跳过 Step 0 直接 Write 新卡 = 绕开 5 级决策 = FAIL。
> - ❌ 写 "Overlaps OK" / "允许重叠" / "重叠不用管" 等措辞 = 绕过 Level 1/2 判定 = FAIL（唯一合法重叠是 §3 Level 3 已明确声明关联关系的互补视角平行卡）。
> - ❌ 新增 RAG 卡后，长文里仍只引用「自己这张新卡路径」，不补引兄弟/主卡/总卡路径 = 关联关系没入链路 = FAIL。
> - ❌ 在 `A-设计` / `B-落地方案`（含归档件）中新增指向 `C-知识` 的链接 = 违反单向引用模型（存量已有不要求回删，但新写的快照文档不得再包含此类链接）。
> - ❌ **手改 `INDEX.md` / `INDEX.json` / 各 `00-INDEX.md`** = 覆盖派生物，`make wiki-lint` 会红。

### 3.5 Commit 消息「重复检查自我声明」签名规范（批量同步 RAG 卡时强制带上）

> 🎯 目的：**透明化 Step 0 判定结果，形成责任链闭环**。某次错判把「语义别名」标成 Level 5 时，靠 git log 能立刻定位那次提交的自我声明并回溯判定过程。

**模板（占独立一段；数字必须与本次 Step 0 实际结果一致，禁止写 0 蒙混）**：

```
—— 重复检查自我声明（DOCUMENTATION §3.5 v3.0）——
本次候选主题总数：<N> 个
Step 0 5 级判定结果 →
  Level 1（完全重复 → 合并删除副卡）：<X> 张
  Level 2（主卡-子卡 → 合并到主卡）：<M> 张
  Level 2（主卡-子卡 → 拆分新建子卡 + 声明）：<K> 张
  Level 3（视角兄弟卡 → 独立新建 + 互声明）：<P> 张
  Level 4（总卡-细卡 → 新建细卡 + 声明）：<Q> 张
  Level 5（纯新主题 → 直接新建）：<R> 张
  合计处理 RAG 卡：<X+M+K+P+Q+R> 次（含合并，不与新建重复计数）
——
  🔍 语义别名疑似清单（name/scope 不命中但语义读下来近似同主题）：
    • <疑似1：候选主题 T_name → 疑似对应现存卡 <现存卡名>；建议：人工确认后决定合并 or 新建>
    • 0 条（如无则写这一句；高重复领域被判 Level5 的必须至少写 1-2 条留痕）
——
```

**红线**：6 个分级数字（X/M/K/P/Q/R）加总必须等于候选主题总数 N（Σ = N）。

## 4. 各层章节模板

文件头统一按 §1；章节内容用下列清单，字段级细节填相对路径链接（`路径#Lx-Ly`），**不贴实现快照代码块**。

### 模板 A：`A-设计/*.md`（决策快照，为什么）

| 章节 | 内容要点 |
|------|---------|
| 一、设计目标 | 设计哲学 + **关键决策表**（问题/方案/原因 3 列）|
| 二、架构思路 | ASCII 分层/数据流图 + 关键结构定义源码链接 |
| 三、涉及文件清单 | 分层索引表（文件/角色/内容摘要）+ **零改动面**说明 |
| 四、边界与行为红线 | 编号列表，每条一句话（回归必保语义）|
| 五、扩展模式 | 按场景列步骤 + 每步参考文件链接 |

**红线**：写定后不追代码；发现契约与代码不一致 → 文头加一句 `注：本文为决策快照，接口细节以代码为准`（并考虑标 `status: 已废弃` + 新篇替代）。
**参考实例**：[thinking_task_policy_engine_design.md](./modules/02-Agent运行时/A-设计/thinking_task_policy_engine_design.md)

---

### 模板 B：`B-落地方案/*.md`（落地快照，怎么做 + 结果）

| 章节 | 内容要点 |
|------|---------|
| 一、目标 | 问题/解决方式表 + **收敛后效果**一句话（架构收益）|
| 二、架构思路 | ASCII 知识下沉路径 + **关键边界/行为红线** |
| 三、涉及文件清单 | 分层表（每行路径链接 + 变更摘要）+ **零改动面** |
| 四、分发点速查表 | 改动点 × N，每点：分支表 + 代码入口链接 |
| 五、验收清单 | checkbox（完成时更新 `status` 与勾选）|
| 六、执行结果摘要 | 各模块验证结果表 + 与计划偏离项 |
| 七、后续扩展路径 | **4 步模板**：common 模型 / domain 分发 / handler 目录 / 前端 |

**红线**：功能完成时删掉 Task/Step checkbox 之外的实现代码块、失败测试代码块与 `cargo test/build` 命令，只保留以上 7 节概述（≈150 行级），并把 `status` 改成 `已完成`。
**参考实例**：[容器化与网关部署方案.md](./modules/12-基础设施与部署/B-落地方案/容器化与网关部署方案.md)

---

### 模板 C：`C-知识/<主题>.md`（现状长文，是什么）

| 章节 | 内容要点 |
|------|---------|
| 头部 `<cite>` | 本文引用的文件清单（设计文档 + 源码锚点，相对仓库根）|
| 更新摘要 | 最近一次修订动了什么 |
| 目录 | 长文的章节目录（便于跳读）|
| 简介 / 项目结构 | 这块在系统里的位置与边界 |
| 核心组件 / 架构总览 | 组件职责 + 调用链 + 数据流 |
| 详细组件分析 | 按文件/模块展开，配 `路径#Lx-Ly` |
| 故障排查 | 症状 → 判据 → 定位路径（**Agent 最常查的一节**）|

**红线**：**代码变了就改这一层**——它是现状权威，也是知识库唯一的高频维护动作。

---

### 模板 D：`C-知识/<卡名>/<卡名>.md`（RAG 原子知识卡，召回用）

| 章节 | 内容要点 |
|------|---------|
| `§1 整体方案` | 一张卡回答一个可独立召回的问题；不写长文陈述 |
| `§2 关键文件路径表格` | 读代码直接跳的锚点表（`路径#Lx-Ly`）|
| `§3 架构约定` | 这块的设计约束 / 调用约定 / 边界 |
| `§4 约束清单` | 硬约束（回归必保语义），编号列 |
| `§5 历史演进` | 迭代记录（可选但推荐）|

**红线**：`scope[]` 必须**窄而准**（宽到全域会让召回全命中，等于失效）；建卡前先过 §3.2 查重。

---

### 模板 E：`archive/*`（归档）

只在文件头加一句：
```
> 📦 归档标记（YYYY-MM-DD）：被 [新文档/SHA] 取代。保留原因：[xxx]。生效方案：[新文档相对路径 | commit abc123]
```
正文永不修改。

## 5. 维护闭环（速查）

| 你改了什么 | 回填位置 | 收尾命令 |
|---|---|---|
| 代码实现 | 对应 `C-知识` 长文 | `make wiki-index` |
| 新增原子知识点 | 新建 RAG 卡（先查重）| `make wiki-index && make wiki-check` |
| 设计决策 | `A-设计`（或新篇 + 旧篇标 `已废弃`）| `make wiki-check` |
| 方案推进 | `B-落地方案` 的 `status` + checkbox | `make wiki-index` |
| 任何增删改名 | —（索引自动跟上）| `make wiki-index && make wiki-lint` |

操作规程（含 `jq` 查询配方、按场景的删除/改名步骤）见 [README.md](./README.md)。
