# 统一定时调度器 P0/P1 落地方案

> 本文把 [统一定时调度器与日程设计](../A-设计/unified_scheduling_design.md) 的 P0/P1 落成可执行的改动清单。
> A-设计定义「为什么」，本文定义「改哪些文件、写成什么样、怎么验」。
> 现状以源码为准；本文写作时的代码锚点标注在对应段落。

---

## 0. 与 A-设计的三处修正（基于代码事实）

落方案时核对源码，发现三处 A-设计描述与实际代码有出入，按实际代码执行：

| # | A-设计原文 | 代码事实 | 本方案处理 |
|---|---|---|---|
| 1 | §3.1「在 `cron_triggers` 上做增量迁移（新增列），不改初始迁移」 | `migrations/20260420000000_initial.sql#L387` 有 `CHECK (trigger_type IN (0,1,2))`；SQLite 无法 `ALTER` 放宽 CHECK | 新增迁移里**重建表**（12 步法），同时修改初始迁移的 CHECK 以保持一致；两条路径都验证 |
| 2 | §8「DAL 做兼容解析（`action` 列优先，回落 payload 内 action）」 | DAL 无 payload 解析，payload 在消费侧 `src/consumer/scheduler.rs#L87,L101` 解析 | 兼容落在**消费侧**：事件同时带顶层 `action` 与原始 `payload`，`on_event` 用 `action.or(payload.action)`；DAL 不碰 payload |
| 3 | §2.4「`consume_mode`/`order_key`/`retry_policy` 作为模板属性，不落表」 | `Subscription` 是 consumer 的静态返回值（`src/pkg/aop/core/consumer.rs#L36-L57`），非运行时可读 | 表里只存 `behavior`；模板语义由 `TriggerBehavior` 枚举 + consumer 的 `match behavior` 静态分派表达。P1 阶段 `CronTriggerConsumer` 仍是单一 Sync consumer，异步两族的 AOP 订阅声明留到 P2 落地真实派发时一并处理 |

另有一处 A-设计未写但必须处理：`CronTriggerPo::new()` 只有 5 个入参，全仓多处调用（seed / handler / 测试）。新增 16 列必须在 `new()` 内给默认值，保持签名不变。

## 1. P0：数据层扩展

### 1.1 迁移（新文件）

`migrations/20261124220000_extend_cron_triggers.sql`，核心是**重建表**：

```sql
-- 1) 建新表：trigger_type CHECK 放宽到 (0,1,2,3)，追加 16 列
CREATE TABLE cron_triggers_new (
    id TEXT NOT NULL PRIMARY KEY,
    name TEXT NOT NULL,
    trigger_type INTEGER NOT NULL CHECK (trigger_type IN (0, 1, 2, 3)),
    cron_expression TEXT,
    interval_seconds INTEGER,
    run_at INTEGER,
    next_run_at INTEGER NOT NULL,
    is_enabled INTEGER NOT NULL DEFAULT 1 CHECK (is_enabled IN (0, 1)),
    payload TEXT NOT NULL DEFAULT '{}',
    last_run_at INTEGER,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    created_by TEXT,
    updated_by TEXT,
    org_id TEXT,
    owner_user_id TEXT,
    creator_type INTEGER,
    creator_id TEXT,
    target_type INTEGER,
    target_id TEXT,
    description TEXT NOT NULL DEFAULT '',
    action TEXT,
    behavior INTEGER NOT NULL DEFAULT 0 CHECK (behavior IN (0, 1, 2)),
    start_at INTEGER,
    end_at INTEGER,
    max_runs INTEGER,
    total_runs INTEGER NOT NULL DEFAULT 0,
    last_error TEXT,
    lease_owner TEXT,
    lease_until INTEGER
) STRICT;

-- 2) 回填：存量列全量搬运；action 从 payload JSON 提取；behavior 默认 0
INSERT INTO cron_triggers_new (
    id, name, trigger_type, cron_expression, interval_seconds, run_at,
    next_run_at, is_enabled, payload, last_run_at, created_at, updated_at,
    created_by, updated_by, action
)
SELECT
    id, name, trigger_type, cron_expression, interval_seconds, run_at,
    next_run_at, is_enabled, payload, last_run_at, created_at, updated_at,
    created_by, updated_by,
    json_extract(payload, '$.action')
FROM cron_triggers;

DROP TABLE cron_triggers;
ALTER TABLE cron_triggers_new RENAME TO cron_triggers;

-- 3) 索引（含原 4 个，重建表后原索引随表销毁）
CREATE INDEX IF NOT EXISTS idx_cron_triggers_next_run_at ON cron_triggers(next_run_at);
CREATE INDEX IF NOT EXISTS idx_cron_triggers_is_enabled ON cron_triggers(is_enabled);
CREATE INDEX IF NOT EXISTS idx_cron_triggers_trigger_type ON cron_triggers(trigger_type);
CREATE INDEX IF NOT EXISTS idx_cron_triggers_created_at ON cron_triggers(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_cron_triggers_due ON cron_triggers(is_enabled, next_run_at, behavior);
CREATE INDEX IF NOT EXISTS idx_cron_triggers_owner ON cron_triggers(org_id, owner_user_id);
CREATE INDEX IF NOT EXISTS idx_cron_triggers_target ON cron_triggers(target_type, target_id);
```

同时把 `migrations/20260420000000_initial.sql#L382-L400` 的建表语句替换为上述新表定义（不带 `new` 后缀），索引段同步替换。理由：新库从零建表时不应先建旧表再重建；存量库已执行过初始迁移，靠新迁移的重建路径升级。两条路径的最终 schema 必须逐列一致，用测试钉死。

> ⚠️ `json_extract(payload, '$.action')` 在 payload 非法 JSON 时返回 NULL（SQLite 的 JSON1 对非法输入通常报错而非 NULL）。存量 6 条 payload 均为合法 JSON；为稳妥起见用 `CASE WHEN json_valid(payload) THEN json_extract(...) END`。

### 1.2 枚举（`common/src/enums/cron_trigger.rs`）

照 `SkillAuthorType`（`common/src/enums/skill.rs#L45-L78`）的「五件套」模板：

- `TriggerType` 追加 `Schedule = 3`，`From<i32>` 追加 `3 => Self::Schedule`。
- 新增 `TriggerBehavior`：`SyncMaintenance=0` / `AsyncNotify=1` / `AsyncAgentWakeup=2`，`Default=SyncMaintenance`，含 `From<i32>` / `From<i64>` / `to_i32()` 五件套。模板的消费语义由 consumer 按枚举静态分派，不生成运行时配置。
- 新增 `CreatorType`：`User=0` / `Agent=1` / `System=2`（与 `CallerType` 取值对齐但语义独立）。
- 新增 `TargetType`：`Agent=0` / `User=1` / `Project=2` / `System=3`。
- `common/src/enums/mod.rs` 追加 `pub use`。

### 1.3 PO（`src/models/cron_trigger.rs`）

- `CronTriggerPo` 追加 16 个字段（对齐 A-设计 §3.2）。
- `new()` 签名不变，新字段给默认值：`behavior=SyncMaintenance`、`description=""`、`action=None`、`total_runs=0`、租约与 Who/When 窗口字段为 `None`。
- 新增 `pub fn resolved_action(&self) -> Option<&str>`：`action` 列优先，回落 `payload` 内 `action`（消费侧用，见 §2.3）。
- `touch()` 不变。

### 1.4 DAO（`src/service/dao/cron_trigger/mod.rs` + `sqlite.rs`）

- `CronTriggerQuery` 追加 `behavior: Option<TriggerBehavior>`、`org_id: Option<String>`、`owner_user_id: Option<String>` 三个筛选。
- `CronTriggerDao` trait 新增一个方法：
  ```rust
  /// 原子领取到期触发器：仅当租约空闲时写入 lease 并返回成功领取的行
  async fn claim_due(
      &self,
      ctx: RequestContext,
      now: i64,
      lease_owner: &str,
      lease_until: i64,
      limit: i32,
  ) -> Result<Vec<CronTriggerPo>>;
  ```
- `sqlite.rs`：
  - 抽出 `const TRIGGER_COLUMNS: &str = "..."`（30 列）统一 `create` / `get_by_id` / `list` / `list_due` / `claim_due` 的列清单，避免 5 处漂移。
  - `create` / `update` 的 INSERT/UPDATE 追加 16 列绑定。
  - `update_next_run_at` 追加 `total_runs` 累加、`last_error=NULL`、`lease_owner=NULL`、`lease_until=NULL` 的清租约动作（改名 `finalize_execution` 更贴切，但为兼容测试与 Domain 透传，保留原方法名，扩展语义）。
  - 新增 `claim_due`：事务内先 `SELECT ... WHERE next_run_at<=? AND is_enabled=1 AND (lease_until IS NULL OR lease_until<=?) AND 窗口内 ORDER BY next_run_at LIMIT ?`，再对每行执行条件 `UPDATE ... SET lease_owner=?, lease_until=? WHERE id=? AND (lease_until IS NULL OR lease_until<=?)`，`rows_affected==1` 才收进返回集。
  - 新增 `record_failure`（写 `last_error`，不清租约——租约自然过期即重捞）。

### 1.5 DAL（`src/service/dal/cron_trigger.rs`）

- `CronTriggerDal` 加 `claim_due` 透传。
- `mark_executed` 三分支保持不变，**追加** `Schedule = 3` 分支：按「三选一」时间字段计算下一次（同 Once/Cron/Interval 逻辑），但考虑 `max_runs` 与 `end_at` 终态：
  - `total_runs >= max_runs`（若 max_runs 有值）或 `next_run_at >= end_at`（若 end_at 有值）→ `is_enabled=0`（Completed）。
  - 其余同对应时间类型推进。
- `create` 保持纯透传。A-设计 §7 的 Who 组条件必填校验（归属/行为一致性/同组织目标）**留到 P2**：只有 `schedule_agent_task` 工具才会产生 Who 组完整的日程记录，校验随身份固化一起落地（放 Domain，不在 DAL）。
- P0 阶段 `create_cron_trigger` handler 的三选一时间校验已覆盖 Schedule 的时间规则（cron > interval > run_at），无需重复实现。
- `record_failure` 透传。

### 1.6 DTO 与 Domain

- `common/src/api/cron_trigger.rs` 的 `CronTriggerDetail` 追加 16 字段（含 `behavior` / Who 组 / 窗口 / 租约），`src/handlers/system/cron_trigger/response.rs::to_detail` 同步映射。
- `src/service/domain/system/mod.rs` 的 `CronManager` trait 加 `claim_due_triggers` / `record_trigger_failure`，`SystemDomainImpl` 透传；`create_trigger` 调 `validate_trigger`。

### 1.7 前端最小兼容（非 P3 改造）

`frontend/src/pages/system/triggers.rs` 有 4 处 `TriggerType` 穷尽匹配，追加变体后必须补齐，否则 `make clippy-fe` 挂：

- `trigger_type_text`：`Schedule => "日程"`。
- `trigger_type_badge_class`：沿用中性 `badge orz-tag`。
- `schedule_text`：Schedule 按 cron > interval > run_at 三选一展示。
- 编辑弹窗的 `t_str`：`Schedule => "schedule"`（下拉选项的完整支持属 P3，本阶段仅保证编译与只读展示正确）。

> 这不是 P3 的「按新模型重排展示」，只是枚举扩展的必要兼容，避免中间态编译失败。

### 1.8 P0 验收判据

1. `#[sqlx::test(migrations = "./migrations")]` 下：新库建表后 6 个系统 seed 触发器可读，`resolved_action()` 对存量 `{"action":"agent_rest"}` 返回 `Some("agent_rest")`。
2. 迁移路径测试：初始迁移 + 扩展迁移跑完的表结构与「初始迁移内直接写新定义」逐列一致。
3. DAO 单测：`create` → `get_by_id` 往返 16 个新字段无丢失；`list` 按 behavior/org_id 过滤正确。
4. `mark_executed` 对 Schedule + max_runs 到顶 → `is_enabled=0`。
5. 存量 `src/consumer/scheduler.rs` 的 4 个 payload 兼容测试全绿（行为不变）。

## 2. P1：行为模板 + 租约领取 + 分发

### 2.1 事件载荷扩展（`src/models/events/cron_trigger.rs`）

`CronTriggerEvent` 追加：`trigger_type: i32`、`behavior: i32`、`org_id: Option<String>`、`owner_user_id: Option<String>`、`creator_type: Option<i32>`、`creator_id: Option<String>`、`target_type: Option<i32>`、`target_id: Option<String>`、`action: Option<String>`、`description: String`、`lease_owner: Option<String>`。

> 用 i32 而非枚举：事件要能被前端/外部消费者无依赖解析，且 AOP 封套是 `serde_json::Value`；`EventTopic` 等事件既有先例用 i32（`MessageCreatedEvent.from_role`）。保持 `order_key()` 与 `id()` 不变。

### 2.2 Producer（`src/producer/cron_trigger.rs`）

`tick()` 改动：

1. `list_due_triggers` → `claim_due_triggers(ctx, now, instance_id, lease_until, 100)`。
2. `instance_id` = 进程启动生成一次（`common::new_id!(CronTriggerProducer)`，存在 producer 结构体的 `OnceLock<String>` 或构造时字段），租约时长 `LEASE_MS = 5 * 60 * 1000`（> 60s 轮询 + 单轮最坏消费）。
3. 窗口跳过：`start_at`/`end_at` 在 `claim_due` SQL 中过滤，不满足的记录本轮不领取、也不推进。
4. 构造事件填全部扩展字段；`action` 用 `trigger.resolved_action()`。
5. `sink.emit` 失败：租约不清，等过期自然重捞（失败即下轮重试，语义与现有「不 mark → 下轮重捞」一致）。
6. `on_consumed` 不变（仍 `mark_trigger_executed`，其内部 SQL 已清租约）。

### 2.3 Consumer 分发（`src/consumer/scheduler.rs`）

`on_event` 的分派骨架：

```rust
let behavior = TriggerBehavior::from(event.behavior);
match behavior {
    TriggerBehavior::SyncMaintenance => {
        // 现有 6 个 action 分支原样保留；action 来源 = event.action.or(payload.action)
    }
    TriggerBehavior::AsyncNotify => { /* P2 实现；P1 阶段只 log_unimplemented 并 Ok */ }
    TriggerBehavior::AsyncAgentWakeup => { /* P2 实现；P1 阶段只 log_unimplemented 并 Ok */ }
}
```

**关键取舍**：P1 只做「按 behavior 分派」的骨架，异步两族暂不实现动作——因为它们的落地依赖 `schedule_agent_task` 工具（P2）产生数据，提前实现无法端到端验证。但 `behavior` 分派骨架本身可单测：用三个构造事件断言走不同分支。

⚠️ **不要动** `decide_retry` 恒 `Retry` 与 `Subscription::notify_producer()`，这两条是防止丢触发的红线（A-设计 §4.3）。

> P1 阶段 `AsyncNotify`/`AsyncAgentWakeup` 若真被触发，`on_event` 返回 `Ok` 会导致 `on_consumed` 推进触发器——这是**故意的**：P1 不产生这两族记录，只有手动造数据才会遇到；返回 `Ok` + 醒目告警比返回 `Err` 导致每 60s 无限重试更安全。P2 落地时这两个分支必须同时替换为真实派发。

### 2.4 P1 验收判据

1. `claim_due` 并发测试：两条到期记录 + 两个不同 `lease_owner` → 各领一条；同 owner 重复领取 → 空集。
2. 租约未过期期间 `claim_due` 不重复返回；`lease_until <= now` 后可重新领取。
3. `mark_executed` 后 `lease_owner`/`lease_until` 归 NULL（通过 DAO `get_by_id` 断言）。
4. Producer `build_event` 纯函数测试：扩展字段完整、`order_key` 仍是 `trigger_id`。
5. Consumer 分派测试：`behavior=0/1/2` 三个事件分别进入对应分支（用 hook 或日志断言，不依赖真实派发）。
6. 现有 `agent_rest` 等 6 个 action 行为零回归（`behavior=0` 默认路径）。

## 3. 分层与红线合规检查

| 红线 | 本方案如何守 |
|---|---|
| 域之间只通过参数交互 | system 域只发 `CronTriggerEvent`，不引用 runtime/message/hr；异步派发在 consumer（编排层）做 |
| 反向边 | 不改任何 `dal → domain` / `models → domain` / `domain → consumer` 依赖；枚举只在 `common` |
| `ctx.user_id` 只从 root_user_id 还原 | P0/P1 不创建日程，身份固化留到 P2 的 `schedule_agent_task`；Who 组只做存储与透传 |
| 推送面 = 受众 | 同上，P2 落地时处理 |
| 完成三权分立 | 不动 task 状态机 |
| 运行时数据出口 | 触发器状态仍在 DB（进程外读者），不新增 `static HashMap`；租约是 DB 列不是内存表 |
| Sync consumer 禁止 ordered | `CronTriggerConsumer` 订阅不变，不加 `.ordered()` |
| 失败不 mark | `decide_retry` 与 `on_consumed` 语义不动 |
| inline test ≤ 200 行 | 新增测试分文件；`sqlite_test.rs` 与 `scheduler.rs` 现有测试块均需检查行数 |

## 4. 不做（本阶段边界）

- 不实现 `schedule_agent_task` 工具与 Agent 身份固化（P2）。
- 不实现 `AsyncNotify` / `AsyncAgentWakeup` 的真实派发与消息类型拍板（P2，消息类型待定：`TaskAssignment(9)` vs 新增 `ScheduleTrigger(15)`）。
- 不动前端 `/system/triggers`（P3）。
- 不引入日历视图、跨表外键、动态消费者注册、毫秒精度。
- 不修 C-知识卡的三处过时描述（独立待修项，见 A-设计 §12.5）。
