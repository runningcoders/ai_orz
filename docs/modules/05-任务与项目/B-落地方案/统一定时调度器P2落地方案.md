# 统一定时调度器 P2 落地方案

> P0/P1 建好了表、租约与分派骨架；P2 让日程**真正可用**：Agent 能自主创建、到点能被唤醒执行。
> 范围按 [A-设计 §5 / §7](../A-设计/unified_scheduling_design.md) 与 [B-方案 P0/P1](./统一定时调度器P0P1落地方案.md) 的边界。

## 1. 三处拍板（基于代码事实修正 A-设计）

### 1.1 消息类型用 `ScheduleTrigger = 16`，不是 15

A-设计 §12 留的待拍板项，答案是**两者都不能按原案**：

- `15` 已被 `TaskPendingReview` 占用（`common/src/enums/message.rs#L109`），前端 `MSG_TASK_PENDING_REVIEW=15` 与滞留重投白名单都依赖它，迁移要动存量数据 + 前端常量，风险最高。
- `TaskAssignment(9)` 会命中 `applies_task_scope_gates`（`src/consumer/message.rs#L2214`）的任务门闩，日程无 `task_id` 会走默认分支。

选 `ScheduleTrigger = 16`：零迁移、零语义混用。同步改 7 处：

| 文件 | 改动 |
|---|---|
| `common/src/enums/message.rs` | 枚举 + `From<i32>` 映射 16 |
| `src/models/message.rs` | `to_prompt()` 穷尽 match（必改，否则编译不过） |
| `src/consumer/message.rs` | `classify_chain_novelty` → `Novelty::None`（框架动作伴生消息，不回血协作压力）；`chain_type_label` 中文标签 |
| `src/consumer/message_route_policy.rs` | `OWNER_BRIEFING_MESSAGE_TYPES` 加新类型——否则系统来源的日程消息 Final 命中 `system_origin → Discard`，Agent 产出被静默丢弃 |
| `src/service/dal/agent/builder/default.rs` | `current_message` 前缀 `【日程触发通知】` |
| `src/service/domain/message/mod.rs` | `list_stale_pending_notifications` 白名单加新类型，否则日程消息滞留不重投 |
| `frontend/src/utils/message.rs` | `MSG_SCHEDULE_TRIGGER=16` + Markdown 归一化 |

`message_type` 列无 CHECK 约束（初始迁移 `#L226`），**不需要新迁移**。

### 1.2 同组织校验做不了——降级为「存在 + Onboarded」

A-设计 §5.2 / §7 要求「目标 Agent 必须在同一 org 内」。实测这是**不可实现**的：

- `agents` 表无 `organization_id` 列（初始迁移 `#L66-L81`）；
- 全库无 `organization_agents` / `entity_relations` 关联表；
- 源码注释已明说：`src/service/domain/runtime/cancel.rs#L15-L16`「无法做租户门：agents 表没有 organization_id 列，全库也没有 Agent↔组织关联表」；
- `AgentQuery` 无 org 字段，`agent_dao.find_by_id` 的 SQL 是 `WHERE id=? AND status<>0`，不带 org 谓词。

按项目既有口径（`resolve_scored` / `cancel` / `get_capabilities`），handler 内降级为**存在性 + `AgentStatus::Onboarded`** 校验。真要补租户门是独立迁移（`agents.organization_id` + DAO 过滤），不在本阶段范围。

### 1.3 身份固化：`agent_id` 而非 `caller_type` 判 Agent

后台唤醒场景 `caller_type=System` 但执行者是被唤醒的 Agent（`RequestContext` 注释明示）。可靠判据是 `ctx.agent_id().is_some()`，创建者 ID 用 `ctx.message_sender_id()`（优先 agent_id，回退 caller_id）。归属用户 `owner_user_id = ctx.uid()`（只由 root_user_id 还原）。

## 2. 改动清单

### 2.1 工具 `schedule_agent_task`

`src/handlers/system/cron_trigger/schedule_agent_task.rs`，双宏 `#[register_handler_tool]` + `#[generate_http_handler]`：

- **不加 `neural` tag**：Awaken 场景「绑定即权限」全放行，Settle/Compact 按 tag 过滤可避免沉淀循环误建日程。
- DTO `common::api::ScheduleAgentTaskRequest`（放 `common/src/api/cron_trigger.rs`）：`title` / `description` / `cron_expression` / `interval_seconds` / `run_at` / `start_at` / `end_at` / `target_agent_id` / `behavior` / `action` / `max_runs`。**不含** org/owner/creator/target 身份字段。
- 时间三选一优先级 `cron > interval > run_at`，抽纯函数 `resolve_next_run_at` 可单测。
- `behavior` 白名单：默认 `AsyncAgentWakeup`，拒绝 `SyncMaintenance`。
- 目标 Agent 缺省 = 创建者自己；校验存在 + Onboarded（见 §1.2）。
- 写 PO：`trigger_type=Schedule`，Who 组四组身份从 ctx 固化，`description` / `action` 顶层列落值，`payload="{}"`。
- 注册：模块 `mod.rs` 加 `pub mod` + `pub use ..._handler`；`src/router.rs` 加 `POST /schedules`。工具本体由 `#[ctor]` 自动进 ToolRegistry，无需手动注册。

### 2.2 Consumer 真实派发

替换 P1 的告警占位（`src/consumer/scheduler.rs`）：

- `AsyncNotify` → `dispatch_async_notify`：`send_to_user(ctx, cmd)`，受众 `owner_user_id`，正文 `build_schedule_notify_content`。
- `AsyncAgentWakeup` → `dispatch_async_agent_wakeup`：`send_to_agent(ctx, cmd)`，`message_type=ScheduleTrigger(16)`，正文 `build_schedule_wakeup_content`（含日程 ID / 用户原始意图 / 期望动作 / 完成后如何汇报）。
- 两者都先 `RequestContext::new_system()` + `enrich_org_from_project_user(&ctx, owner)` 补 `root_user_id`：少了这步 `MessagePo.root_user_id=""` → SSE 不推、Final 路由丢失。
- **幂等**：`external_key = "schedule:{trigger_id}:{created_at}"`。租约崩溃重捞时同一封套会再次投递，`send_to_agent` 靠它直接返回既有消息，不重复唤醒。
- 两个内容构造抽纯函数（可单测）。

> 派发只到「消息落库 + 事件发布」为止：本消费者是 Sync，真正的 LLM 唤醒在 Async 的 `agent.awakening` 里跑，不占 cron 轮询线程。

### 2.3 Domain 校验

`src/service/domain/system/mod.rs` 加纯函数 `validate_trigger`，由 `CronManager::create_trigger` 调用（工具与系统接口都经过）：

- 时间规则：Once/Cron/Interval 各自必填；Schedule 三选一。
- 窗口：`end_at > start_at`。
- `SyncMaintenance`：Who 组**允许为空**（系统 seed / 存量 6 条触发器历史就是空，收紧会打断 seed）。
- 异步模板：Who 组六字段全必填。

## 4. 剩余边界（本阶段不做）

- **P3 前端**：`/system/triggers` 按 When/Who/What/How 重排展示、behavior 可读标签、系统项 readonly——本轮只补了消息类型的 Markdown 归一化。
- **租户门**：`agents.organization_id` 迁移 + DAO 过滤（独立需求）。
- **C-知识卡**：三处过时描述（默认触发器 2 条 / CAS 乐观锁 / 5 字段 cron）待独立回填。
