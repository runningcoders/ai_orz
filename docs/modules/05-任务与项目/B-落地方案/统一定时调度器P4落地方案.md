# 统一定时调度器 P4 落地方案：时间语义、日程查询与三天/周视图

## 1. 目标与边界

P0~P3 完成了规则表扩展、租约领取、Agent 自主创建日程、前端同页四组模型展示。
本阶段解决用户提出的新问题：

- 「今天/昨天/明天干什么」的三天视图，以及周视图；
- Agent 能查日程并按时间筛选，含相对日词（「明天」）与重复日程（每日/每周）；
- 日程数据里不会存「明天」字面量，必须靠规则展开 + 时间语义折算。

不做：月视图、日历同步/RSVP、实例表、跨用户日程查询（身份边界为「只看自己」）。

## 2. 数据语义不改变

`cron_triggers` 表**不加列、不加迁移**。本阶段全部是查询侧能力：
- 复用已有 `cron_expression` / `interval_seconds` / `run_at` 三选一规则；
- 复用 `start_at` / `end_at` 生效窗口与 `max_runs` / `total_runs` 次数约束；
- `next_run_at` 同时作为 Interval 的相位锚点（与 `mark_executed` 口径一致）。

## 3. 落地内容

### 3.1 DTO 与枚举

- `common::enums::ScheduleDateTerm`：`yesterday/today/tomorrow/three_days/this_week/next_week/custom`。
- `common::api::QueryScheduleRequest`：`date_term` + 可选 `from/to`（必须成对）+ `keyword` /
  `behavior` / `is_enabled` / `limit`。
- `common::api::ScheduleOccurrence`：一条实例（trigger_id / run_at / name / description /
  action / behavior / rule_kind / recurring）。
- `common::api::QueryScheduleResponse`：实例列表 + 实际使用的区间与系统时区。

### 3.2 纯算法层 `common::schedule`（前后端共用）

原落在 `src/pkg/schedule_occurrence.rs`，后下沉到 `common/src/schedule/`：
cron 解析（`cron.rs`）+ 实例展开与日期折算（`occurrence.rs`）+ 时区感知的日历日键、
HH:MM 格式化工具。**理由**：时间展开是纯算法，前端将来在日历上直接新建/拖拽日程时
需要在本地预览，不应先落库再往返服务端；放 common 后前后端同一份代码，规则判定与
表达式规范化都不会出现第二份实现。

- `effective_type(cron_expression, interval_seconds)`：与 `mark_executed` 共用
  `cron > interval > run_at` 口径；DAL 与 query handler 都调用它。
- `config::timezone()` 只从 `server.timezone` 读值注入（服务端配置访问），纯时间算法
  一律在 `common::schedule`。`pkg::cron` 薄壳已删除，调用点直连 common/config，
  零调用的 `validate_expression` 包装也一并移除（common 版本已带 `now` 参数与单测）。
- `expand_rule(rule, from, to, timezone, max_items)`：返回 `[from, to)` 内的实例时刻。
  - Cron：`Schedule::after` 从下界前一毫秒逐点取（包含恰好落在下界的点）。
  - Interval：以 `next_run_at` 为锚，`ceil_div` 算出区间覆盖的整数倍 k；历史实例不受
    `max_runs` 裁剪，未来实例按 `total_runs + future_index` 与 `max_runs` 比较。
  - Once：`run_at`（存量回落到 `next_run_at`）单点。
  - 统一受 `created_at` / `start_at` / `end_at` 约束；单条最多 400 点。
- `resolve_term_range(term, now, timezone)`：相对日词 → 本地日历日半开区间。

单测 17 个（common）：表达式规范化 8 + 时间规则优先级 / 向上取整 / 锚点前后双向展开 /
窗口裁剪 / 剩余次数 / Cron 每日展开 / Once 单点 / 本地零点 / 周一为首日 9。

### 3.3 领域查询层（查询逻辑不写 handler）

⚠️ 架构修正：查询能力归 domain，DAO / DAL 只是它的基建。参数是否另立领域结构体，
判据是「DAO Query 能否表达全部查询意图」，而非一律禁止引用 DAO 值对象。
- `src/service/domain/system/schedule_query.rs`（纯函数 + 领域参数）：
  - `ScheduleQuery`：领域级日程查询参数（身份刻意不在参数里）。因日期词、显式区间、
    关键词是 `CronTriggerQuery` 表达不了的查询意图而存在。
  - `resolve_range`：显式 `from/to` 优先、必须成对且 `to > from`；否则日期词按系统时区折算。
  - `collect_occurrences`：关键词匹配 name/description/action + 规则展开 + 排序截断。
- `CronManager::query_schedules(ctx, ScheduleQuery)`：身份从 ctx 固化，空则拒绝；
  从 ctx 注入 owner 后调用 DAL.list（domain 内部把领域参数转成 DAO 的 `CronTriggerQuery`）。
  consumer 可直接复用本方法，无需复制 handler 的查询逻辑。
- `CronManager::list_triggers` **直接复用 `dao::CronTriggerQuery`**：过滤条件可被它完整
  表达，再包一层领域参数属于「为隔离而隔离」（同 project/task 范式）。若将来需要
  DAO Query 表达不了的字段，再声明领域参数并在调用下游时转换。

### 3.4 Handler 与路由

- `src/handlers/system/cron_trigger/query_schedule.rs`：薄适配层，双宏 handler 同时是
  Agent 工具 `query_schedule`（tags `query,scheduling,autonomy`）与 HTTP 接口。
  - 只做：HTTP 参数 → `ScheduleQuery` 映射 + 默认 200 / 硬上限 500 clamp + 调用 domain。
  - 身份、日期解析、过滤、展开、排序全部不在本层。
- `list_cron_triggers` 只做 `ListCronTriggersRequest` → `CronTriggerQuery` 映射并交给 domain，
  本身不含查询逻辑。
- 路由：`POST /api/v1/system/schedules/query`。
- 工具 description 明确告知模型不要自己算时间戳。
- tag 策略沿用 P2 的 `schedule_agent_task`：不加 `neural`（避免 Settle/Compact 沉淀循环
  误查），用 `query,scheduling,autonomy`——`query` 让意图分析阶段能 respond「我明天
  有什么日程」，Awaken 场景仍按「绑定即权限」放行。

### 3.5 前端

`frontend/src/pages/system/triggers.rs` 顶部加「列表 / 三天 / 周视图」切换：
- 三天 / 周视图**只是时间快捷选项**，不是独立数据通路：仍然是一次 `query_schedule`
  调用（`date_term` 是服务端把时间词折算成 `from`/`to` 的预设，响应回传真实区间），
  前端只按响应区间分桶，没有日历专属接口或专属接口参数；
- 三天视图：一次请求 `three_days`，分三桶（昨天/今天/明天）；
- 周视图：一次请求 `this_week`，分七桶并标周一至周日；
- 形态 / 行为筛选器对日历同样生效：`occurrence_matches_filters` 用与列表**同一套判据**
  （「形态」= 行为模板分区，`SyncMaintenance` 为系统形态）在区间实例上就地过滤，
  空态文案区分「区间内无实例」与「筛选后无实例」；
- 每桶按时间展示实例（HH:MM + 名称 + 行为模板），悬浮显示说明；
- 分桶与 HH:MM 都走 `common::schedule::{calendar_day_key, calendar_day_keys,
  format_time_hm_in_tz}`，以响应携带的 `timezone` 为准，与服务端展开同一时区口径。

`frontend/src/api/system.rs` 增加 `query_schedule` 封装。

## 5. 已知边界

1. **时区口径已统一**：后端按 `server.timezone` 折算「哪一天」，响应携带该时区名；
   前端用 `common::schedule` 的时区工具按同一时区分桶与格式化，不再用浏览器本地时区，
   相同实例不会再落到相邻列。遗留提醒：其他页面若用 `utils::time` 的本地格式化函数
   展示日程时间，仍与日历视图口径不同，后续统一时再收敛。
2. **展开不读实例历史**：`last_run_at` 只记最后一次，失败重试导致的次数漂移不影响展示；
   需要精确执行历史时要另建实例表（明确不做）。
3. **关键词在内存过滤**：规则数上限 500，超出部分不参与查询；当前数据量远低于此。
4. **Agent 视图不含系统触发器**：系统默认触发器无 owner，按「只看自己」边界过滤掉。
5. **`org_id` 可空**（定稿）：日程优先绑定用户 / Agent；本地部署只有一个组织，
   系统日程缺省即本地组织，因此 `validate_trigger` 不再要求 `org_id`。
   `owner_user_id` 仍是必填项——推送面与工具凭据都靠它。若将来需要多组织隔离，
   应走独立实例而不是在同一张表上补租户门（`agents` 表无 `organization_id`，做不了）。
6. **`interval_seconds` 极端值**（已收口）：所有入口统一走
   `common::schedule::interval_next_run_at`，`<= 0` 与溢出（`checked_mul` / `checked_add`）
   直接报错。此前 `now + interval * 1000` 在极端参数下会 wrap 成过去时间，
   等于「创建即被立即反复领取」；`schedule_agent_task` 也不再静默回落到 `run_at`。
