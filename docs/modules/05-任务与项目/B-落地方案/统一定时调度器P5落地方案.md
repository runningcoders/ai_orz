# 统一定时调度器 P5 落地方案：日程更新与取消

## 1. 目标

P0~P4 让 Agent 能**建**日程（`/schedules`）和**查**日程（`/schedules/query`），但缺了修改闭环：
建错了、时间要调整、任务要撤销，都只能人工进管理接口。本次补两个 Agent 工具：

- `cancel_schedule`：取消自己创建的日程，幂等；
- `update_schedule`：更新自己创建的日程，只开放安全字段。

同时修管理端 `update_cron_trigger` 的两个正确性缺陷（详见 §3）。

## 2. 数据模型：Who 组收敛为三字段

不新增表、不新增消息类型。Who 组最终收敛为三个**互不兼任**的字段：

| 字段 | 语义 |
|---|---|
| `owner_user_id` | 归属用户：日程算谁的、查询可见范围、提醒推给谁 |
| `creator_type` + `creator_id` | 创建者：可以是 User、Agent 或 System |
| `agent_id` | 负责 Agent：到点唤醒它执行，或由它发出提醒 |

原 `target_type` / `target_id` 删除——多态目标里只有 Agent 被真正消费，留着会与
`agent_id` 形成两套「谁执行」的口径。迁移里 `target_*` 两列直接换成 `agent_id`，
索引 `(target_type, target_id)` 换成 `(agent_id)`。

> 用户经 HTTP 创建日程：`creator` 是用户、`agent_id` 由参数指定（缺省无值）；
> Agent 自建：`creator` 与 `agent_id` 都指向它自己。
> 通知消息的发送者取 `agent_id`，不再用 `creator_id` 冒充（否则用户创建的日程
> 会产出 role=Agent、id=用户 的不一致消息）；无负责 Agent 时用 `system` 哨兵，
> `send_to_user` 按发送者 ID 推导角色（`system` → System、users 表 → User、
> agents 表 → Agent），不在调用入口写死。
>
> `creator_*` 的用途只有两处**创建时兜底**，不参与可见/可改权限：
> 上下文没有负责 Agent 时，Agent 创建者兜底 `agent_id`；上下文没有归属时，
> User 创建者兜底 `owner_user_id`。可见/可改一律看 `owner_user_id`。

取消即 `is_enabled = 0` 软删（与 `cancel` 状态机一致），
`max_runs`/`total_runs`/租约字段原样保留。

## 3. 管理端更新的两个缺陷（已修）

`update_cron_trigger` 原先只把 DTO 字段写回 PO，绕过了 domain 的创建校验，也不重算游标：

1. **校验缺失**：可以把 cron 改成非法表达式、interval 改成负数、窗口改成 `end <= start`，
   要等 Producer 领取时才炸。现在 `CronManager::update_trigger` 统一调用 `validate_trigger`，
   与 `create_trigger` 同一套规则。
2. **游标漂移**：改了 `cron_expression`/`interval_seconds`/`run_at` 后 `next_run_at` 还是旧值，
   下一次仍按旧规则触发，用户感知为「改了没生效」。现在 domain 从库里读回旧记录，
   用 `trigger_time_rule_changed` 判断时间三要素是否变化，变了就按 `cron > interval > run_at`
   重算（复用 `recompute_next_run_at`，与两个创建入口同口径）。

另外落实 A-设计的状态机约束：软删（`is_enabled=0`）记录不可经通用更新复活，必须走 `resume` 显式恢复。

## 4. 两个新工具

均为双宏 handler（Agent 工具 + HTTP 接口），身份从 ctx 固化，consumer 可直接复用 domain 方法。

### 4.1 `cancel_schedule`

- 路由 `POST /api/v1/system/schedules/cancel`，tags `scheduling,autonomy`（不加 `neural`）。
- `CronManager::cancel_schedule(ctx, trigger_id) -> Result<bool>`：
  - `owner_user_id` 从 ctx 取，空则拒绝；
  - 不存在 / 不属于自己 / `SyncMaintenance` 模板统一报 `NotFound`，不泄漏他人日程；
  - 已软删（`is_enabled=0`）返回 `Ok(false)`（幂等 no-op，与 `cancel_thinking::NotThinking` 同理），
    本次真的取消返回 `Ok(true)`。
- 响应 `{ cancelled, message }`，模型不会因重复取消而误判失败。

### 4.2 `update_schedule`

- 路由 `POST /api/v1/system/schedules/update`，tags `scheduling,autonomy`。
- `ScheduleUpdate` 是领域参数，身份刻意不在结构里，由 domain 从 ctx 固化。
- `schedule_mutation.rs` 两个纯函数：
  - `ensure_owned`：只放行「自己的异步日程」；
  - `apply_allowed_update`：只投影标题、描述、时间规则、窗口、`max_runs`、`agent_id`；
    **归属、创建者、行为模板、运行统计一概不动**。
- **窗口 / 次数是三态**：字段缺省 = 保持，显式 `null` = 清除（窗口变无限制 / 次数变不限），
  传值 = 覆盖。单层 `Option` 区分不了「没传」和「清空」，用户会永远取消不掉限制。
- **时间三选一是整组替换**：只要给了 `cron_expression`/`interval_seconds`/`run_at` 中任意一个，
  三处就一并从参数覆盖（未给 = 清除）。否则「原来有 cron、这次想换 interval」会被
  `cron > interval` 优先级吃掉，表现为改了没生效——与 §3.2 的重算规则配套。
- `agent_id` 可改派（业务配置），handler 先过「存在 + `Onboarded`」校验再进领域；
  `max_runs` 由 `validate_trigger` 统一要求为正数（0 会让规则创建即耗尽）。
- 更新后复用 `update_trigger`，因此自动获得校验与游标重算。
- 响应复用 `CronTriggerDetail`。

### 4.3 运行时列与配置列分家

`CronTriggerDao::update` 原先写全列，管理端「读 → 改 → 写」会把 `total_runs` 回退、
把 `lease_owner` / `lease_until` 清空 —— 与执行并发时可能导致重复触发。

现在通用 `update` **只写配置列**（名称/时间规则/窗口/次数/Who 组/behavior/payload 等），
运行时列只能经专用原子语句改写：

| 方法 | 语义 |
|---|---|
| `claim_due` | 条件写租约（`rows_affected=1` 才算领取成功） |
| `update_next_run_at` | 推进游标 + `total_runs+1` + 清租约 |
| `complete_run` | 终态：`total_runs+1` + `is_enabled=0` + 清租约 + 记 `last_run_at` |
| `record_failure` | 只记错误摘要，不动租约 |

`complete_run` 用 `total_runs = total_runs + 1` 在库里自增，禁止「读出来加一再写回」。
同时删除从未使用的 `list_due` 路径（producer 早已改为 `claim_due`，留着容易被误用绕过租约）。

## 5. 分层落位

```
handler（薄）: DTO → 领域参数；身份固化；DTO 透传
               agent_guard::ensure_onboarded（跨域：查 hr，system 域不得引用）
    ↓
domain/system: ensure_owned / apply_allowed_update（纯函数）
               update_trigger（校验 + 游标重算 + 拒绝复活）
               collect_occurrences（多路归并，全局有序后再截断）
    ↓
dal/dao       : 单表读写（只认 CronTriggerPo / CronTriggerQuery）
```

`cancel_schedule` / `update_schedule` 的领域方法 owner 一律从 ctx 取，调用方无法伪造。
`CronTriggerQuery` 仍只在 `list_triggers` 等「DAO Query 能完整表达」的场景直接复用，符合 P4 判据。

> 「负责 Agent 是否可用」必须查 hr 域，属跨域编排，只能放 handler（`agent_guard`），
> 与 `schedule_agent_task` 共用。等第三个调用方出现再考虑抽服务。

**消息侧身份解析**：`send_to_user` 不再把 `from_role` 写死为 Agent，而是按发送者 ID
推导（`system` 哨兵 → System、users 表命中 → User、agents 表命中 → Agent，都查不到
回退 Agent）。日程提醒的发送者是 `agent_id`，无负责 Agent 时用 `system` 哨兵——
两个场景共用同一条解析路径，未来出现「用户代发」也不用改调用点。

判据下沉为 `MessageDelivery::resolve_role_by_id` 公开只读方法，供上层适配层按 ID
补齐 / 校验身份。⚠️ **职责边界**：domain 只兜底「命令里没有角色字段」的场景
（当前只有 `send_to_user`）；带 `from_role` 的命令（如 `send_to_agent`）由入口
适配层保证角色与 ID 一致，domain 信任并落库、**不覆盖**——校验与修复属上层，
不让 domain 替入口擦屁股。

**执行侧身份下发**：唤醒正文携带 `安排者 / 归属用户 / 负责 Agent` 三行；日程实例
DTO（`ScheduleOccurrence`）也带 `creator_type` / `creator_id` / `agent_id` /
`owner_user_id`，日历与查询结果不必再逐条查详情。

## 7. 已知边界

1. **Agent 不能改行为模板**：`ScheduleUpdate` 不含 `behavior`/`trigger_type`，
   防止把异步日程改成 `SyncMaintenance` 绕过系统约束。
2. **`run_at`/`interval_seconds` 极端值**：统一走 `common::schedule::interval_next_run_at`
   的受检乘加，非正数与溢出直接报错。
3. **`max_runs` / 窗口的清除走 `null`**：三态字段的 `null` 是清除，`0` 会被校验拒绝
   （避免「以为清空、实际立刻耗尽」）。
4. **更新后 `total_runs` 不重置**：规则变更不抹掉历史执行次数，避免刷次数绕过上限。
5. **组织维度的 Agent 校验做不了**：`agents` 表无 `organization_id`，只能校验存在 + `Onboarded`。
