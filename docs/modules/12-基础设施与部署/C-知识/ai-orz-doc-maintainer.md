## 一、适用范围与三层总览

### 1.1 三层文档（SSOT）

AI Orz 的 `docs/` 按 **15 个能力域**组织，每个模块内部固定三层：

| 层 | 位置 | 回答问题 | 性质 | 维护者（两个 Skill 分工）| 典型体量 |
|------|------|---------|------|------------------------|---------|
| **A-设计** | `docs/modules/<模块>/A-设计/*.md` | **为什么做**（设计决策 + 关键决策表）| 历史快照（写定不追代码），`status: 现行/落地中/草案/已废弃/未标注` | 👉 `ai-orz-doc-maintainer`（本 Skill）| 单篇 200-400 行 |
| **B-落地方案** | `docs/modules/<模块>/B-落地方案/*.md` | **怎么做 + 落地结果快照**（7 章骨架） | 历史快照，`status: 已完成/进行中/草案/已废弃/未标注` | 👉 `ai-orz-doc-maintainer`（本 Skill）| 单篇 150-250 行 |
| **C-知识** | `docs/modules/<模块>/C-知识/` | **是什么**（现状长文 + RAG 原子知识卡） | **活文档**（跟随代码增量同步）| 👉 `ai-orz-wiki-maintainer` | 长文 8 段式；卡 40-80 行 |

> **没有归档目录**：旧设计与旧方案按其能力域**留在原模块**，用 `status: 已废弃` / `已完成` 表达生命周期，被取代的设计在 `related` 互链替代文档。历史内容靠 git 追溯，不靠 tombstone 目录。

**单向引用模型（v3.0 核心）**：

```
     代码变更（唯一输入信号）
        │
        ▼ wiki-maintainer 同步
  C-知识 长文 ──cite──► RAG 知识卡        ← 活文档区（持续更新）
        │                   │
     cite / source_files[] 单向指向          ← 唯一维护方向的跨区链接
        ▼                   ▼
  A-设计 ◄──────────────► B-落地方案      ← 历史快照区（写定即冻结）
  （A↔B 互引允许：同期冻结，链接不腐烂）
  （A/B 不反向链接 C-知识：知识库改版后冻结文档无法跟进 = 永久断链）
```

**职责划分的理由**：
- 代码变更后**只需**同步 `C-知识`——读者要"当前状态"看长文/RAG 卡
- `A-设计` / `B-落地方案` 是考古入口：读者要"当时为什么这么做"才主动打开
- `C-知识` 的 cite / source_files[] 单向指向 A/B → 检索链路（RAG 召回 → 长文 → 源码 → 考古设计/方案）完整覆盖
- 功能完成 → B 标 `已完成`；设计被取代 → A 标 `已废弃` 并互链替代文档（**都不移动文件**）

### 1.2 本 Skill 覆盖的动作（与 ai-orz-wiki-maintainer 严格隔离）

✅ 做：
- `A-设计` 新建 / 补 YAML frontmatter / 补关键决策表 / 移除过期的代码快照
- `B-落地方案` 新建 / 从 superpowers 执行蓝图按 7 章模板精简落成
- 设计被取代时的 `status: 已废弃` + `related` 互链（不移动、不建归档）
- 方案验收后的 `status: 已完成` + 7 章收敛
- `docs/superpowers/` 的 7 天过期处置（精简落成或直接删除）
- 任何文档中的「代码块性质判定」与「代码引用路径引导替换」
- placeholder 清除（TBD / TODO / 酌情 / 参考 Task 等）

❌ **不做（转给 ai-orz-wiki-maintainer）**：
- `C-知识` 下的人类长文更新
- `C-知识/<卡名>/` 下的知识卡创建
- 「根据代码变更同步更新知识库」→ 直接转给 ai-orz-wiki-maintainer
- 在 A/B 中维护指向 `C-知识` 的链接（v3.0 禁止新建；存量不要求回删）

### 1.3 路径格式与引用铁律（强制执行；快照侧视角）

**路径格式约定**（DOCUMENTATION.md §2，三环境通跳）：
- 引用**源码文件**（.rs/.ts/.toml/.sql 等）→ 统一写 `相对路径#Ln-Lm`（如 `src/pkg/logging.rs#L15-L42`）
- 引用**文档**（A/B/C-知识长文/RAG 卡的 .md）→ 统一写**相对仓库根路径**（如 `docs/modules/12-基础设施与部署/A-设计/logging_design.md`）；**一律相对路径，永不写本机绝对路径与 `file://` 伪协议**
- 路径含空格写 `%20`；含半角括号的模块（`07-外部Agent(A2A)`、`10-异步基建(AOP)`）用尖括号形式 `[描述](<路径>)`

**引用规则矩阵（v3.0 单向模型）**：

| 链接方向 | 位置 | 规则 | 维护方 |
|---------|------|------|--------|
| `C-知识` cite → A/B + 卡 | 长文 `<cite>` 区 | ✅ 强制（活→历史，唯一维护方向）| ai-orz-wiki-maintainer |
| RAG `source_files[]` → A/B + 长文 | 卡 YAML | ✅ 强制（同上）| ai-orz-wiki-maintainer |
| A-设计 ↔ B-落地方案 | 两者 frontmatter `related` | 🔸 可选（同期冻结，链接不腐烂；B 强烈建议链对应 A）| 本 Skill |
| A/B → `C-知识` | — | ❌ **禁止新建**（历史快照反向链活文档，改版后永久断链）；存量不要求回删，但永不主动补 | — |

**⭐【路径格式硬约束】**：出现 `file:///` 绝对路径 / `file://` 伪协议 / legacy 冒号行号（`path:15-42`）→ 执行结果 FAIL，改完再过。

## 二、文件头 YAML frontmatter（A/B 强制）

`A-设计` / `B-落地方案` 的头部是**机器可读**的：`make wiki-meta` 强制校验，缺字段直接失败。

```yaml
---
kind: 设计决策            # 设计决策 | 落地方案
module: 02-Agent运行时    # 所在模块目录名，必须与实际路径一致
name: runtime_design      # 文件名（不含 .md）
title: Runtime Domain 设计 # 中文标题，索引展示用
status: 现行              # 见下表
scope:                    # 本篇涉及/覆盖的代码路径（可空数组）
- src/models/agent.rs
related:                  # 关联文档，相对 docs/modules/ 的路径（可空数组）
- 02-Agent运行时/A-设计/thinking_task_policy_engine_design.md
---
```

7 个字段**一个都不能少**（`scope` / `related` 可为空数组）。

### 2.1 status 枚举

| 层 | 允许的 `status` | 语义 |
|---|---|---|
| `A-设计` | `现行` / `落地中` / `草案` / `已废弃` / `未标注` | 设计是否仍具权威性 |
| `B-落地方案` | `已完成` / `进行中` / `草案` / `已废弃` / `未标注` | 方案推进到哪 |

- **`未标注` 不是合法目标态**：只是"作者还没声明"的诚实标记，`make wiki-meta` 会点名。
- `status` 应能从正文显式信号推导（`状态：xxx` 行 / checkbox 完成度）。
- **设计被取代不要删旧文**：旧篇标 `status: 已废弃`，新建 `status: 现行` 的替代文档，二者 `related` 互链——"为什么当初不那么做"本身是知识。

### 2.2 正文里的写作残留（必须删除）

| 残留类型 | 例子 | 处理动作 |
|---------|------|---------|
| Skill 执行期标记 | `For agentic workers: REQUIRED SUB-SKILL to execute this blueprint` | ✅ 整段删除 |
| Step / Task checkbox 执行清单 | `- [ ] Step 1.xxx / - [x] Task 2.1.xxx` | ✅ 一律删除；用静态验收表替代 |
| 具体实现代码快照块 | `impl trait for X { ... }` 整段、完整测试代码、cargo test 参数命令 | ✅ 一律删，替换为路径引导 |
| Placeholder | TBD / TODO / 酌情 / 参考 Task X / 如果需要则 / 待确认 | ✅ 逐一替换为确定性描述或删除该条 |

## 三、代码块性质判定表（强制执行；99% 的保留/删除争议用本表现场判定）

> 判断口诀：**"粘到编辑器里能直接编译/运行 ⇒ 实现快照型 ❌；只声明接口形状不含内部逻辑 ⇒ 契约表达型 ✅"**

| 代码块场景 | 判定 | 可以保留吗？ | 处理方式（如果判 ❌）|
|-----------|------|------------|-------------------|
| **1. trait 方法签名列表（无 `{...}` 实现体）** | 契约 ✅ | 可保留（但非强制） | 保留 → 必须紧跟源码路径引导 |
| **2. struct 字段列表** | 契约 ✅ | 同上 | 同上 |
| **3. enum 变体列表**（全是 `Variant(i32)` 或带字段声明但无 impl）| 契约 ✅ | 同上 | 同上 |
| **4. SQL `CREATE TABLE` Schema** | 契约 ✅ | 同上（设计文档常用）| 同上 + 附 migrations/ 目录对应路径 |
| **5. 目录树 / 数据流 ASCII 图** | 契约 ✅ | 强烈建议保留（无对应源码，是架构意图）| 不用附源码路径 |
| **6. 函数 `{ }` 内部逻辑 / match 分支体 / 循环 / 控制流** | 实现快照 ❌ | **禁止** | 删 → `> 字段级逻辑见 [xxx.rs::func](src/.../xxx.rs#Lxx-Lxx)` |
| **7. 完整测试代码 / `cargo test` 参数 / `git commit` 命令 / bash 脚本** | 实现快照 ❌ | **禁止** | 删 → 只写"X passed / 0 failed"表格 |
| **8. Superpowers 蓝图中的 Task/Step checklist** | 实现快照 ❌（A/B 中禁止）| **禁止**（仅 superpowers 临时文档允许） | 删 → 用验收清单或执行结果摘要表格替代 |
| **9. 能直接编译的函数调用栈示例** | 实现快照 ❌ | **禁止** | 删 → 替换为 ASCII 数据流图或路径引导 |
| **10. 极短的行内 token（如 `foo(ctx, ..)`）** | 契约 ✅ | 允许保留 | 直接写在行内，不单独开代码块 |

### 契约代码块保留时「源码路径引导」的标准写法

```
> 当前实现：[file.rs::StructName](src/path/to/file.rs#L起始行-L结束行)
```

- 必须是**相对仓库根路径 + `#Ln-Lm`**；放在代码块**紧邻下一行**
- 允许省略行号，但不推荐（写行号方便未来读者核对"当时的版本是哪段"）

## 四、代码引用首选格式（优先级远高于贴代码块）

无论什么文档、什么场景，**优先用「文字短描述 + 可点击路径链接」**：

```
[简短描述](src/相对路径/到/file.rs#L起始行-L结束行)
```

- 文字描述要把"读者为什么要点这个链接"的动机写出来
- 行号范围**推荐写**
- 错误对比：完整 impl 块（20 行）❌ vs `> 逻辑见 [identity_credential.rs::update](src/service/domain/finance/identity_credential.rs#L80-L210)` ✅

```
4. 前端：api + 区块组件，复制 [模板](frontend/src/...)
```

### 5.3 历史文档处理（没有模板 C）

被取代的设计与已完成的方案**不移动、不加归档头**：
- `A-设计`：`status` 改 `已废弃`，正文状态行写「被 [替代设计](docs/modules/<模块>/A-设计/新设计.md) 取代（YYYY-MM-DD）」，替代设计 `related` 指回旧篇
- `B-落地方案`：`status` 改 `已完成`，正文保持 7 章快照
- 删除的内容交给 git 追溯，**禁止新建任何 `archive/` 目录或 tombstone 文件**

## 七、与 ai-orz-wiki-maintainer 的协作接口

经常遇到「我改完代码，既需要写设计/方案文档，又需要同步 `C-知识` 长文 + 知识卡」的场景。**两者不合并，协作是单向解耦的：**

```
（1）新代码写好 → 跑通测试 → 推送 commit ✅
（2）调用 【ai-orz-doc-maintainer】→ 落地 A-设计 + 把 superpowers 蓝图精简成 B-落地方案 ✅
       ↳ 只写自己的 frontmatter + A↔B 互链；不写任何指向 C-知识 的链接
（3）调用 【ai-orz-wiki-maintainer】→ 同步 C-知识 长文 + 知识卡 ✅
       ↳ 在长文 <cite> 区、RAG 卡 source_files[] 中写 A/B 的真实相对仓库根路径
       ↳ wiki-maintainer 自己 grep docs/modules/*/A-设计 与 B-落地方案 找对应主题，找不到就不写
（4）后续设计被取代（场景 D）→ doc-maintainer 报告状态变更 → wiki-maintainer 把引用改指现行替代设计
```

**关键约束**：
- 顺序推荐 doc → wiki（A/B 先存在，cite 才有东西可指），但**不是硬依赖**：找不到对应文档时允许留空
- 设计退役**只改 `status`、不移动文件**，因此协作文档里不存在「路径映射重定向」这件事
- 两 Skill 无任何"等对方"的交叉点，各自可独立执行
