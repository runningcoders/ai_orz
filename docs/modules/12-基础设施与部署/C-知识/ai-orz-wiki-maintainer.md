## 一、适用范围与核心不变量

AI Orz 的 `docs/` 按 **15 个能力域**组织，每个模块内部固定三层。本 Skill 负责**活文档区**（跟随代码变更持续更新的 `C-知识`），并通过单向引用覆盖完整检索链路：

| 层 | 位置 | 回答问题 | 性质 | 维护者 |
|------|------|---------|------|--------|
| **A-设计** | `docs/modules/<模块>/A-设计/*.md` | **为什么做**（设计决策 + 关键决策表）| 历史快照（`status: 现行/已废弃`）| `ai-orz-doc-maintainer` |
| **B-落地方案** | `docs/modules/<模块>/B-落地方案/*.md` | **怎么做 + 落地结果快照**（7 章） | 历史快照（`status: 已完成`）| `ai-orz-doc-maintainer` |
| **C-知识 长文** | `docs/modules/<模块>/C-知识/<主题>.md` | **是什么**（现状百科，代码首选入口）| **活文档** | 👉 `ai-orz-wiki-maintainer`（本 Skill）|
| **C-知识 RAG 卡** | `docs/modules/<模块>/C-知识/<卡名>/<卡名>.md` | **总结 + 索引**（给 Agent RAG 召回的原子知识单元）| **活文档** | 👉 `ai-orz-wiki-maintainer`（本 Skill）|

**单向引用模型（v3.0 核心）**：

```
     代码变更（唯一输入信号）
        │
        ▼ 本 Skill 同步
  C-知识 长文 ──cite──► RAG 知识卡        ← 活文档区（本 Skill，持续更新）
        │                   │
     cite / source_files[] 单向指向          ← 唯一维护方向的跨区链接
        ▼                   ▼
  A-设计 ◄──────────────► B-落地方案      ← 历史快照区（doc-maintainer，冻结）
```

**职责划分的理由**：
- 代码变更后**只需**同步 `C-知识`——读者要"当前状态"看长文/RAG 卡
- A/B 是冻结的考古快照，**不反向维护**指向 `C-知识` 的链接
- 本 Skill 是跨区链接的**唯一维护方**：cite / source_files 单向指向 A/B；设计退役时把引用改指 `status: 现行` 的替代文档

### 1.2 两个 Skill 的职责分界与协作

单向解耦，无交叉等待点：
- 写 `C-知识`（本 Skill）时在长文 `<cite>` + RAG 卡 `source_files[]` 写清楚：对应 `A-设计` + `B-落地方案` 路径（**自己 grep `docs/modules/*/A-设计` 与 `B-落地方案` 按主题找**；找不到就留空，不强制、不占位、不等对方）
- 写 A/B（doc-maintainer）时**不写**任何指向 `C-知识` 的链接
- **引用改指（事件触发）**：当 doc-maintainer 报告「设计 X 已废弃，现行替代为 Y」时，本 Skill 全局把 cite/source_files 中的 X 改指 Y。**文件没有移动，因此不存在路径重定向。**

### 1.3 路径格式与引用铁律（强制执行；活文档侧视角）

**路径格式约定**（DOCUMENTATION.md §2，三环境通跳）：
- 引用**源码文件**（.rs/.ts/.toml/.sql 等）→ 统一写 `相对路径#Ln-Lm`（如 `src/pkg/logging.rs#L15-L42`；长文 cite 区、章节来源段、RAG 卡 source_files[] 都沿用）
- 引用**文档**（A/B/长文/RAG 卡 .md）→ 统一写**相对仓库根路径**（如 `docs/modules/12-基础设施与部署/A-设计/logging_design.md`）；**一律相对路径，永不写本机绝对路径与 `file://` 伪协议**
- 路径含空格写 `%20`；含半角括号的模块（`07-外部Agent(A2A)`、`10-异步基建(AOP)`）用 `[描述](<路径>)`

**⭐【路径格式硬约束】**：出现 `file:///` 绝对路径 / `file://` 伪协议 / legacy 冒号行号 → 执行结果 FAIL。

**引用规则矩阵（v3.0 单向模型，只含本 Skill 负责的方向）**：

| 主体 | 位置 | 引用什么 & 写法 |
|---------|------|----------------|
| **C-知识 长文（本 Skill）** | `<cite>` 引用区（源码列表之后）| `A-设计`：`[标题](docs/modules/<模块>/A-设计/x_design.md)`（优先 `status: 现行`）<br>`B-落地方案`：`[标题](docs/modules/<模块>/B-落地方案/x.md)`<br>RAG 卡：`[卡名](docs/modules/<模块>/C-知识/<卡名>/<卡名>.md)` — 同主题有平行卡时至少写 1 张<br>（A/B 找不到对应文档可留空，不强制）|
| **RAG 卡（本 Skill）** | YAML `source_files[]`（源码之后）| `A-设计`：`docs/modules/<模块>/A-设计/x_design.md`<br>`B-落地方案`：`docs/modules/<模块>/B-落地方案/x.md`<br>长文：⭐ **强制至少 1 条**对应长文相对仓库根路径（活文档区内部闭环）<br>兄弟平行卡：0~N 张（按 DOCUMENTATION.md §3.3 关系声明）|

**A/B → `C-知识` 方向由 doc-maintainer 侧禁止新建，本 Skill 不检查、不要求。**

**引用覆盖率底线（每次同步自审）**：
- 本次新增的所有 RAG 卡 → 100% 至少有 1 条长文相对仓库根路径出现在 `source_files[]` 中（0 条 = 失败）
- 本次新增的所有长文 → 100% `<cite>` 区至少 1 条 RAG 卡路径；A/B 路径有则写（找不到可留空，不算失败）

### 2.2 硬性约束

| 编号 | 约束 | 细则 |
|-----|------|------|
| H-1 | **引用区路径统一写相对仓库根路径 + `#Ln-Lm`** | 不写绝对路径 / `file://`；GitHub 原生解析 + IDE 可点 + 文档中心通跳 |
| H-2 | **故障排查节必须存在** | 哪怕只有 2-3 条最短路径也要写；这是 Agent 最常查的一节 |
| H-3 | **目录锚点与正文标题完全一致** | 大小写 / 全半角 / 空格一致，否则文档中心跳转失效 |
| H-4 | **每节末尾附「章节来源」纯中文标题段**（不加粗） | 通常省略于简介/故障排查/结论/附录；mermaid 图后紧贴「图表来源」 |
| H-5 | **mermaid 只允许 3 种图** | `graph TB/LR` 架构/组件关系；`sequenceDiagram` 时序；`classDiagram` PO/实体 |
| H-6 | **严禁任何代码快照块（除 mermaid 外）** | trait impl 体/函数逻辑/测试代码/命令参数/DTO 完整定义全部删，改为路径引导 |
| H-7 | **允许行内 1-2 个短 token 的 inline code** | 如「接受 `limit` 与 `offset` 两个分页参数」；不要展开成独立代码块 |
| H-8 | **文件名 = 主题名（中文）** | 放在对应模块 `C-知识/` 下；RAG 卡另建同名子目录 |

### 3.2 硬性约束

| 编号 | 约束 | 说明 |
|-----|------|------|
| K-1 | **YAML 5 字段必须齐全（不允许增删字段）** | `kind / name / category / scope[] / source_files[]` |
| K-2 | **`name` = 目录名 = 文件名**（三者完全一致，中文） | 例：目录「用户工作区 vs Agent 工作区」→ md 同名 → name 同值 |
| K-3 | **`scope[]` 写 glob 数组，不写具体文件路径** | 用于 RAG 引擎「传入一组文件」时快速匹配；`**` 表示所有后代 |
| K-4 | **`source_files[]` 写核心锚点 3-10 个** | 允许附 `#Ln-Lm`；不要全列（长文 cite 才列全） |
| K-5 | **4 章节标题一字不差：1.整体方案 2.关键文件表格 3.架构与约定(3.X) 4.约定与约束 bullet** | RAG 引擎按"第 4 节"语义匹配强制检索 |
| K-6 | **同主题多卡必须按 DOCUMENTATION.md §3 图谱法则判定关系** | 禁止裸重叠：Level 1 → 合并+删除副卡；Level 3/4 → 平行保留但必须双向声明 |
| K-7 | **禁止写长文式的完整目录 / mermaid 图 / `<cite>` 区** | 知识卡是原子短卡，平均 40-80 行，§1 不超 3 段，§4 不超 15 条 bullet |

### 3.3 新卡 vs 更新旧卡的选择策略

| 场景 | 做法 |
|-----|------|
| 某主题卡描述的能力**彻底被重写**（核心流程/锚点文件 ≥70% 不同） | 新增平行卡，YAML `name` 加后缀区分，如「策略引擎（重构后：policy_set!宏混合）」 |
| 某主题卡描述的能力**新增 1-2 个接口/字段**但核心流程未变 | 原卡原地增量更新：`source_files[]` +新路径；§4 +新 bullet；不新建平行卡 |
| 某主题从来没覆盖过（新能力） | 必须新增一卡，不能硬塞到相近卡中 |
| 卡的 `source_files` 指向文件**已重命名/移动** | 原地改路径即可（路径修复，不是内容变更）|
| 设计退役（旧 A 标 `已废弃`，替代 Y 为 `现行`） | `source_files[]` 中旧 A 路径 → 改指 Y；无替代则保留并注明「旧设计，仅考古」|

## 四、完整执行 SOP（8 步）

| Step | 动作 | 交付物 / 检查点 |
|-----|------|----------------|
| 0. **前置查重（强制，不可跳过）** | 对每个候选主题按 DOCUMENTATION.md §3.2 走 5 级决策算法（扫描现存卡做 name/category/scope 三维匹配 → Level 1 合并删除副卡 / Level 2 优先合并 / Level 3 平行卡+互声明 / Level 4 总细卡+互声明 / Level 5 新建）| 判定结果表 + commit 消息带 §3.5 自我声明 |
| 1. 收集变更范围 | 确定 BASE_SHA→HEAD；`git log BASE..HEAD` 排除纯文档类提交（前缀 `docs`/`docs(cleanup)`/`docs(plan)`/`docs(readme)`/`docs(skill-communication)`），保留 feat / refactor / fix / test / style 类 | 提交清单（按前缀分组+作者+日期）|
| 2. 变更文件清单 | `git diff --name-only BASE..HEAD \| grep -v "^docs/"` 得变更文件 F，按模块聚合（15 个能力域）| 模块分布表 |
| 3. 候选长文页命中 | 反向 grep `docs/modules/*/C-知识/*.md` 的 `<cite>` 区 + 「章节来源」段：引用的路径 ∈ F → 标记待更新；再按模块语义补 TOP 页面 | 候选长文清单 |
| 4. 长文增量更新 | 按 §2 规范逐页更新：+cite/→新引用、+"更新摘要"段、+§5 详细内容、+每节来源路径指向最新行号、+更新 mermaid 图+来源 | 格式合规；所有相对路径引用真实存在；0 代码快照（除 mermaid）|
| 5. **生成新知识卡**（本 SOP 核心）| **按本次代码变更的语义主题生成**（不是按长文页 1:1 映射）。严格按 §3 模板：YAML 5 字段 + scope glob + 4 章节。**禁止裸重叠：与旧卡的关系必须经 Step 0 判定** | 新增 N 张卡；name/目录/文件名三者一致；变更文件应被新卡 scope 覆盖 ≥90% |
| 6. 创建全新长文页 | 若 Step 5 出现全新能力（卡已建但 `C-知识` 尚无对应长文）→ 按 §2.3 归属模块建 md + 骨架 + 逐节写作 | 故障排查节至少 2-3 条最短路径不缺 |
| 7. 提交推送 | commit 前缀：`docs(wiki): <范围> — 长文更新X页 + 知识卡新增Y张（BASE..HEAD 摘要）`；量大可按模块拆 commits | 最终可推送（用户没说不推就默认 push）|
| 8. **引用改指（事件触发，非每次）** | 当 doc-maintainer 报告「设计 X 已废弃，现行替代为 Y」时：全局 grep 长文 `<cite>` 与 RAG 卡 `source_files[]` 中的 X → 改指 Y；无替代设计则保留并注明「旧设计，仅考古」 | `C-知识` 侧 0 断链。**文件未移动，无需路径重写** |

## 五、失败时的回退路径（异常处理 SOP）

| 异常 | 判定 | 回退动作 |
|-----|------|---------|
| 候选长文命中后，某页「章节来源的行号全错」 | 是 → BASE→HEAD 的变更移动了源码行 | 全部重新指向最新行号；**宁可不写 `#Ln-Lm`，也不要写错误范围** |
| 新知识卡 scope 写太宽（`['**']`）导致召回噪音大 | 是 → scope 字段不允许 `['**']`（仅两张顶层总览卡允许）| 收敛到本次变更真覆盖的 2-5 个 glob |
| 某篇长文目录和正文标题对不上（锚点失效）| 是 → 文档中心跳转失败 | 快速修复：目录 `#xxx` 必须与标题 `## xxx` 完全相同 |
| 用户说"这次只同步某一个 commit，不要跑全量 SOP" | 是 → 用户是权威 | 直接 Step 2（只拿该 commit 变更文件）→ Step 3-7；跳过 Step 1 |
| Level 1 合并后，副卡路径仍被引用 | 是 → 合并未收尾 | 全局 grep 副卡路径 → 全部替换为主卡路径；副卡文件直接删除（不建归档副本）|

## 六、与其它 Skill 的协作边界

| 场景 | 应该调用的 Skill | 不应该调用本 Skill |
|-----|-----------------|------------------|
| 新功能开发完成后 → 写 A-设计 / B-落地方案 | 走 `ai-orz-doc-maintainer`（`.trae/skills/ai-orz-doc-maintainer/SKILL.md`，未纳入 Git） | ❌ 本 Skill 是维护现状知识库，不是写设计决策快照 |
| superpowers 执行蓝图 → 精简为 `B-落地方案` 7 章 | ai-orz-doc-maintainer | ❌ 本 Skill 不处理 A/B |
| 设计退役后 → `C-知识` 引用改指现行替代设计 | ✅ 本 Skill（SOP Step 8，被动触发）| ❌ doc-maintainer 不直接改 `C-知识` 文件 |
| 用户说"更新最近代码到知识库" | ✅ 就是本 Skill | ❌ 不要用 ai-orz-doc-maintainer |
| 用户说"给 agent 增加一张知识卡" | ✅ 本 Skill §3（只做知识卡那部分） | 不要求一起更新长文（用户明确说"只加知识卡"时）|

## 七、校验清单（每次同步完成后的自审清单）

- [ ] **两套活文档都更新了吗？** 至少 1 篇长文 + 至少 1 张卡（同步 0 长文或 0 卡 = 不完整）
- [ ] **Step 0 前置查重执行了吗？** 每个候选主题都有 5 级判定结果；Level 2/3/4 拆分卡的关联声明写齐了？
- [ ] **长文硬约束**：H1 + cite + 目录锚点 + 每节来源 + 故障排查节 + 0 代码快照（除 mermaid）？
- [ ] **知识卡硬约束**：YAML 5 字段齐全 + name=目录=文件名 + scope glob 正确 + source_files 3-10 锚点 + 4 章节标题一字不差？
- [ ] **新增 RAG 卡 `source_files[]` 至少 1 条长文路径**（内部闭环）？
- [ ] **所有相对路径引用都存在吗？**（提取 cite / 章节来源 / source_files[] 中的链接目标 → 逐个检查；必要时删掉损坏路径或指向正确文件）
- [ ] **新增长文页挂对了 15 个能力域模块吗？**
- [ ] **提交 message 前缀是 `docs(wiki):` 吗？**
- [ ] （Step 8 专用）设计退役映射中的每条旧路径，在 `C-知识` 中已 grep 清零或注明「仅考古」？
- [ ] **没有新建任何 `docs/archive/` 路径**（副卡直接删除、退役设计原地保留）？
