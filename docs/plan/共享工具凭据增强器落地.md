## 一、目标

**做什么**：把 MCP Server / HTTP 工具的凭据消费从「配置内嵌原文（`env` / `headers` 字段）」整体迁移为「类型级需求声明 + 凭据增强器」——配置层只存非敏感的匹配键与注入点声明，运行时由 domain 编排层统一取数、pkg 纯函数加工、经 `check` 注入单次工具实例；内置工具 gh_cli / tavily_search / lark_cli 统一工厂化，per-tool resolver trait 与 OnceLock 注册三清零；tavily 共享 config 兜底废除、CLI 型工具参数收进各自 PO config，达成「全局 config 零工具参数」不变式。

**为什么**：工具是组织共享的、凭据是用户私有的——共享配置里出现凭据原文或 credential_id 等同把私人凭据公开（任何人调用该工具都以凭据主人身份对外执行）。现状 MCP `env` / `headers` 字段允许凭据原文直接落库共享配置，是必须根除的问题源；三种内置工具各自维护 OnceLock resolver 注册是同一种应消亡的注册机制（探测注册表、resolver 注入同属一类）。设计动机与决策全表见 [设计快照 §1.2](../design/tool_credential_requirement_design.md)。

## 二、架构思路

### 2.1 决策链脉络（D1-D28 提炼）

| 决策 | 落地内容 |
|------|---------|
| D1 类型级需求声明 | 配置只存 `(kind, platform, field?)` 匹配键 + `enhancer?` + `binding` 注入点，三者皆非敏感；禁止 credential_id 与凭据原文落库 |
| D2/D3 凭据类型扩展 | 新增 `GenericToken` / `OAuth` / `UserPassword` 三 kind；匹配键升级 `(kind, platform)` 二元组，`user_credentials` 表加 `platform` 列 + 唯一索引升级（D20） |
| D5/D7 增强器模型 | 凭据衍生行为（前缀拼接 / Basic 组装 / OAuth 刷新）建模为 pkg 增强器 trait；能力管控优于红线管控——OAuth 构造只装配 AccessToken，refresh_token / client_secret 物理不可达 |
| D10/D11 包裹与幂等 | 注入值 = 显式增强器( canonical(凭据) )；显式选择默认增强器与不选等价 |
| D17 生产端二元化 | dal 生产凭据（user dal `find_default` / lark dal 渠道路径附 attributes），pkg 纯值加工零数据访问，取数上移 domain 编排层；无 per-tool resolver、无数据端口、无 OnceLock 注入注册 |
| D22 check 单次实例 | `CoreTool` 增 `credential_requirements()` + `check(&mut self, resolved)` 生命周期方法；编排层每次调用 create → check → call，实例不复用（凭据是对象状态） |
| D23 连接隔离 | 声明凭据需求的 stdio MCP 连接按调用者隔离——落地为 per-operation 连接（每次调用独立连接、用后即关）+ 实例级注入，结构性 (server, 调用者) 隔离，凭据只存在于当次子进程 |
| D25 Internal binding | 内置工具消费形态：值存工具实例字段（`Internal { field }`），保持 binding 枚举单一模型 |
| D26 入口统一 | 所有 Agent 工具调用经 domain `RuntimeToolExecution` 单点编排（think_loop 切换 + DAL `call_tool_by_id` / `execute_auto` / `execute_manual` 双删）；`ToolExecutionRequest { tool, args, resolved }` 统一传参；顺带修复 Auto 模式 MCP 工具主循环不可执行 |
| D27 tavily 兜底废除 | 全局 config `[tavily]` 整段删除，TavilyKey 纯单轨与 GithubToken 一致；timeout_ms 挪工具 PO config 缺省兜底零迁移 |
| D28 PO config 闭环 + readiness 数据驱动 | browser / gh_cli / lark_cli 的二进制名与行为参数全部进各自 PO config（CLI 型 = po.config.command 不变式）；readiness 探测注册表消亡，改为 domain `tool_readiness` 数据驱动（复用 `resolve_tool_credentials`） |
| lark DAL trait 体系化 | 850 行单文件拆 `LarkCredentialDal` / `LarkListenerDal` 子 trait，为 runtime 依赖注入提供凭据端口（前置重构） |

### 2.2 运行时编排链（核心链路）

```
配置期（管理面，非敏感声明）
  McpServerConfig / HttpToolConfig .credential_requirements[]
        │
        └─ handler validate_requirements() 五规则校验
           （binding↔协议 / platform↔kind / field↔enhancer 互斥 / supports 矩阵 / 三元组去重）

运行期（编排注入，D17 生产路由二元化 + D22 单次实例）
  domain RuntimeToolExecution::call_tool(ctx, tool, args)
        ├─ ToolRegistry::credential_requirements(&po)      ← Builtin 工厂静态声明 / Mcp·Http config 解析
        ├─ resolve_tool_credentials(ctx, requirements)
        │      ├─ LarkApp → LarkCredentialDal 渠道路径（明文态 + attributes{identity_mode}，D24）
        │      └─ 其余 kind → UserDal::find_default(kind, platform)（DB 加密态，纯单轨 D27）
        ├─ pkg::credential::resolve_requirements()          ← 纯值加工：按需解密 → 增强器包裹 canonical（D10）
        ├─ 任一未命中 → credential_missing_json 结构化引导（D19，Agent 可读自愈）
        └─ 全命中 → dal.call_tool(ToolExecutionRequest { tool, args, resolved })
                          └─ DAL per-call 重组装实例 → CoreTool::check(resolved) 注入实例字段
                             → call 内只做 binding 纯放置（env / header / query / internal）
```

**执行中的关键偏差与决策调整**（相对原始蓝图的结构性调整，均以独立提交落地）：

- **lark DAL 提前 trait 体系化**：原计划在 Task 3.3 内顺手改，实际前置为独立重构提交（a22eede3）——`resolve_tool_credentials` 的依赖注入需要 `LarkCredentialDal` 端口先存在；850 行单文件拆为 credentials / listener / impl 三模块。
- **D23 落地形态简化**：蓝图设想的「连接缓存键升级 `(server_id, user_id)`」未引入——现状 stdio 本就是 per-operation 连接（无跨调用 session 缓存），每次调用独立连接 + 实例级注入即结构性 (server, 调用者) 隔离，凭据只存在于当次子进程，缓存键机制无必要（07dd7cf4，隔离语义由 `stdio_tool_injections_are_isolated_per_instance` 测试锁定）。
- **Step 4 连带完成 Step 5**：pkg 侧 per-tool resolver trait 定义删除后，`service::init` 的注册行编译必失败，故 dal/user.rs、dal/lark 的 resolver 实现段与注册三行在同一提交（be1575dc）内聚删除，grep 收口确认六类 resolver 符号零残留。
- **`ToolExecutionRequest` 用 `ToolPo` 载体**：蓝图初稿传 `Tool`，落地时发现 `Tool` 的 `Clone` 实现是 `unreachable!()`（含非 Clone 的 `Box<dyn CoreTool>`），改传 PO、实例由 DAL per-call 重组装——这正是「单次实例」注释的本意（68ed836f）。
- **`dispatch_manual_tool` 返回 `ToolExecutionResult`**：与 trait 其余方法统一返回类型，替代蓝图初稿的 `(Value, ToolCallEntry)` 元组（4a610c0d）；同时删除 `RuntimeDomainImpl::tool_dal()` 死代码辅助方法。
- **Builtin 更新管道 diff 式 guard**：DAO guard 从全字段挡改为工厂字段保护（name/description/protocol/control_mode/parameters_schema/tags 不可改，config/status 放行），顺带修复 Builtin 启停被挡的现状 bug；Builtin config 变化不触发向量重索引（6c9af46d）。
- **增强器声明单点化**：每工具模块级 `credential_requirements()` 自由函数作为单点声明，工厂覆写与 CoreTool 实例方法同源调用，一致性测试锁定声明零漂移（be1575dc）。
- **前端共享模块抽取**：MCP 表单的协议无关校验逻辑整体迁入 `components/credential_form.rs`（非复制粘贴），HTTP 工具表单直接复用并升级为 scope 参数化六规则（04f961c5）。
- **GetToolResponse 无 runtime_ready 字段**：工具详情页经 `query_tools` 列表通道取 `ToolListItem.runtime_ready` 同源探测，CLI 型与 key 型 NotReady 文案区分（983a843a）。
- **config 脱敏通道的红线旁路**：config 整体脱敏时 `credential_requirements` 键会命中敏感词被 REDACTED，故 DTO 用独立顶层字段透出——这正是顶层字段存在的目的（1c0f788a）。
