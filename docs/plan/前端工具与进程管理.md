## 一、目标（为什么做）

工具/进程前端体验存在三处闭环缺口：HTTP 工具无创建入口、无可视化进程管理页面、聊天对话上下文无工具调用历史可追溯；后端进程能力已在 pkg/process 与 shell_exec 中落地，但前端无对应消费端。

| 问题维度 | 解决方式 |
|---------|---------|
| HTTP 工具创建需手调 API，无前端表单 | tools.rs 页头加「+ 创建 HTTP 工具」按钮，Modal 表单（字段对齐 CreateToolRequest + HttpToolConfig） |
| 无统一进程管理入口 | 新增 `/system/processes` 路由页面：进程列表（双端状态徽标 + 自动刷新开关）+ Modal 详情（日志 tail + kill） |
| 聊天页看不到当前对话的工具调用历史 | ChatSidePanel 新增「工具」Tab：并行 query_tool_call_entries + list_processes 按 call_id join，展开可看 input/output |
| 进程管理 API 缺少列表接口 | 后端新增 shell_list handler（双露为 HTTP GET /processes + LLM 工具 shell_list，对齐 shell_status/shell_kill 三件套） |

**收敛后效果**：工具创建→执行→进程监控→工具调用追溯形成完整前端闭环；进程列表页与聊天侧栏复用同一 ProcessDetailContent 组件（减少重复）；HTTP 方法白名单保持 GET/POST（PUT/PATCH/DELETE 另行安排）。

## 二、架构思路（怎么做的）

前后端三层数据链路 + 共享组件复用模式：

```
┌─────────────────────────────────────────────────────────────┐
│  前端 ChatSidePanel「工具」Tab                               │
│  并行拉取：① query_tool_call_entries(limit=30)               │
│           ② list_processes()                                │
│  前端按 entry.call_id == process.call_id join                │
│  关联 Running 进程显示 pid 徽标（点击 Modal 复用详情组件）     │
│  行展开看 input/output 摘要；refresh_tick 防抖刷新链路共用    │
└─────────────────────────────────────────────────────────────┘
                              │
                              │  两个前端页面共享同一组件
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  共享组件 ProcessDetailContent { pid }                       │
│  懒加载 shell_status(pid, tail_lines) →                       │
│  展示 entry 全字段 + log_tail（mono）+ 手动刷新 + kill 确认   │
│  被两处使用：① /system/processes 列表页 Modal                │
│            ② ChatSidePanel 工具 Tab pid 徽标 Modal           │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │  API 客户端（3 方法）
┌─────────────────────────────────────────────────────────────┐
│  前端 API：frontend/src/api/system.rs                        │
│  list_processes() / get_process_status(pid, tail) /          │
│  kill_process(pid)（对应后端 3 个 handler）                  │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │  HTTP（用户）+ LLM 工具（双露）
┌─────────────────────────────────────────────────────────────┐
│  后端 handlers/system/process/                               │
│  shell_list.rs（新增：双露 #register_handler_tool）          │
│    → system.domain().process_manager().list_processes(ctx)   │
│    → 逐条 refresh 探活 → 转 ProcessInfo                      │
│  shell_status.rs / shell_kill.rs（进程管理配套 2 件套已存在） │
└─────────────────────────────────────────────────────────────┘
```

**关键边界 / 行为红线（回归必保）**：
1. **HTTP 方法白名单**：创建表单 Method 下拉仅 GET/POST 两项；PUT/PATCH/DELETE 另行安排，不纳入本期
2. **进程详情不建独立路由页**：一律 Modal 形态（列表页 Modal + 聊天侧栏 Modal），两处共享同一 ProcessDetailContent 组件
3. **工具调用 Tab 数据依赖**：query_tool_call_entries 走 JSONL 扫描查询，limit=30 控制开销；进程列表为内存态，服务重启后为空属预期
4. **shell_list 双露范围**：用户 ctx 全量可见 / Agent ctx 按 agent_id scope 过滤（仅见自己启动的进程），复用 tool_call_entry 同款 scope 模式
5. **前端表单校验**：JSON 文本域提交前 `serde_json` 解析校验；必填字段（name / url 模板）行内提示
