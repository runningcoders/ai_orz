## 一、重构目标（为什么做）

通用后台任务模块（BackgroundTaskRegistry）已有 progress/{task_id} 单任务进度查询，但缺少**全局管理视图**：系统管理员看不到"所有任务列表"，向量重建/See

---d 导入/系统初始化等异步任务执行情况无统一面板；已完成的历史任务（Completed/Failed）无限积累在 registry 的内存 HashMap 中，长时间运行会泄漏。

| 问题维度 | 解决方式 |
|---------|---------|
| (a) 无全局任务列表，后台异步任务执行情况不可见 | 后端 registry 增 list_all_progress() 方法；新增 list_tasks handler GET /system/tasks 支持 task_type/status 筛选+started_at 降序；前端 `/system/tasks` 页面渲染表格展示 |
| (b) 已完成/失败历史任务无限积累在内存 | 新增 cleanup_tasks handler POST /system/tasks/cleanup；registry cleanup_finished(max_count) 每类型保留最近 max_count 个完成/失败；前端"清理已完成"按钮 + 确认弹窗 |
| (c) 任务详情不可查（result JSON / error 栈 / step_message 全量字段） | 前端任务表行点击 → 详情弹窗展示完整 task_id/类型/状态/步骤/step_message/error（alert-error 样式）/result（pre JSON pretty） |
| (d) 列表刷新手动体验差 | 前端 use_future 实现 3 秒自动轮询；筛选变化（filter_type/filter_status 信号）→ use_future 依赖自动重启 future：立即加载 + 重启轮询循环（不会并发多个循环）；组件卸载自动取消 |
| (e) 分页/筛选缺失，任务多时难查找 | 后端返回所有匹配任务（任务数量通常不大）；前端**客户端分页**（PAGE_SIZE=20）：pagination 控件上一页/下一页/页码；按类型下拉（initialize_system/rebuild_vectors/seed_* 共 5 类）、按状态下拉（Running 等 4 态）筛选 |

**收敛后效果**：系统管理员在"/系统/后台任务"菜单中，实时查看所有异步任务（3 秒自动刷新），支持类型/状态筛选，点击行查看详情和返回结果，批量清理已完成历史任务保留最近 10 个。

## 二、架构思路（怎么做的）

```
后端 API 层
├─ GET /api/v1/system/tasks?task_type=xxx&status=xxx
│   handler list_tasks
│     → registry.list_all_progress()
│     → 内存筛选 task_type / status（retain）
│     → sort_by started_at desc
│     → ListTasksResponse { tasks: Vec<TaskProgressSnapshot>, total }
│
├─ POST /api/v1/system/tasks/cleanup?max_count=10
│   handler cleanup_tasks
│     → before = list_all_progress 统计 Completed/Failed
│     → registry.cleanup_finished(max_count) 每类型保留 N 个
│     → after = 再统计
│     → CleanupTasksResponse { cleaned = before - after }
│
└─ GET /api/v1/system/tasks/{task_id}/progress（已存在，不动）
    → 详情页点击任务行不调此接口，直接用 tasks() 缓存的数据展示

后端基础层 registry 扩展
  BackgroundTaskRegistry 新增：
    pub async fn list_all_progress(&self) -> Vec<TaskProgressSnapshot>
      tasks.read().await.values().map(|t| t.progress()).collect()
    cleanup_finished(max_count)（已存在，复用）

前端层 SystemTasks 页面
├─ Signal 状态
│   ├─ tasks: Vec<TaskProgressSnapshot> 列表数据
│   ├─ loading: bool
│   ├─ filter_type: Option<String>  类型筛选
│   ├─ filter_status: Option<TaskStatus>  状态筛选
│   ├─ current_page: usize  客户端分页
│   ├─ detail_task: Option<TaskProgressSnapshot>  点击行的详情
│   └─ show_cleanup_confirm: bool  清理确认弹窗
│
├─ use_future 自动轮询（3s 间隔 POLL_INTERVAL_MS）
│   读取 filter_type() + filter_status() → 建立依赖
│   每次筛选变化 → 自动取消旧 future + 启动新 future
│   新 future：立即 list_tasks 请求一次 → loop { sleep 3s → 再请求 }
│   组件卸载 → use_future 自动取消 future（无内存泄漏，无残留轮询）
│
├─ 客户端分页（PAGE_SIZE=20）
│   total = tasks().len()；total_pages = ceil(total / 20)
│   page = current_page.min(total_pages-1)；start/end 切片 page_tasks
│
├─ 统计卡片
│   tasks() 实时计算 running/completed/failed 3 种 badge 计数
│
├─ 筛选栏
│   类型 select：全部 / 系统初始化 / 向量重建 / Seed 导出/导入/应用默认（6 选项）
│   状态 select：全部 / Pending / Running / Completed / Failed（5 选项）
│   onchange 选值 → 设置 filter_type/status，同时 current_page 重置到 0
│
├─ 列表表（table table-zebra）
│   行可点击：cursor-pointer hover
│   列：类型（中文 label）、状态（badge：primary/success/error/ghost）、进度（cur/total + step_message small）、开始时间（mm-dd HH:MM:SS）、耗时（ms/s/min 自动格式化）
│   点击行 → detail_task.set(Some(t)) → 打开详情弹窗
│
├─ 分页控件（join 按钮组）
│   « 前一页 / 当前页显示 / 后一页 »；禁用边界
│
├─ 详情弹窗
│   modal modal-open；点击遮罩关闭
│   字段：task_id 等 6 项
│   error → alert-error 红色框
│   result → pre + serde_json::to_string_pretty 显示
│   modal-action "关闭" 按钮
│
└─ 清理确认弹窗
    文字说明"每类型保留最近 10 个，运行中不影响"
    按钮：取消（关弹窗）+ 确认清理（btn-warning 触发 on_cleanup）
    on_cleanup：POST cleanup_tasks(Some(10)) → toast.success("已清理 N 个") → 立即刷新 list 一次
```

**关键边界（行为红线，回归必保）**：
1. **use_future 轮询而非 use_effect+spawn**：轮询必须用 use_future（读 filter_type/filter_status 信号），不能用 use_effect+手动 spawn。理由：筛选变化时 use_future 自动取消旧 future 并重启，不会产生多个并行轮询循环；组件卸载时自动取消。这是本计划前端的**核心架构决策**
2. **客户端分页而非服务端分页**：后台任务数量通常有限（每类型保留最近若干个），registry 内部 HashMap 数量不大。后端返回全量匹配任务 + 前端 Signal 切片分页。禁止给 BackgroundTaskRegistry 的 list_all_progress 增加 pagination 参数（会让简单场景复杂化）
3. **清理接口只清理 Completed/Failed，绝不碰 Running/Pending**：cleanup_finished(max_count) 内部实现必须先判断 `snapshot.status == Completed || Failed` 才考虑清理。Running/Pending 任务无论多么旧都必须保留（否则用户正在等的异步任务进度从列表消失但实际后台还在跑）
4. **详情弹窗展示数据来源**：点击任务行时，从当前 `tasks()` Signal 缓存中找对应 task_id 展示（**不额外调用 progress/{task_id} 接口**）。理由：3 秒轮询已是实时最新，缓存数据足够新，详情显示无需再发网络请求。若任务刚好 3 秒内完成，下一轮轮询会自动更新，用户体验可接受
5. **导航菜单权限**：系统管理下拉菜单的"后台任务"链接，必须放在 Admin 权限区域（和 SystemSeed 同一区块）。普通 Member 用户看不到这个导航入口（路由级鉴权也应在 router.rs system_routes 中确认，但导航菜单必须一致）

## 四、扩展速查表

### 4.1 用 use_future 做带筛选依赖的自动轮询模式（通用模板）

本计划 use_future 轮询是**通用可复用模式**，任何需要"筛选变化立即重启 + 组件卸载自动取消"的轮询场景都可直接套用：

```
use_future(move || async move {
    // 1. 先读取所有筛选依赖信号 → 建立自动重启依赖
    let req = MyListRequest {
        filter_a: filter_a(),   // 读取 signal → 建立依赖
        filter_b: filter_b(),
    };
    // 2. 立即首次加载一次（不要等 3s 后才显示）
    match list_xxx(&req).await {
        Ok(v) => data.set(v),
        Err(e) => toast.error(...),
    }
    loading.set(false);
    // 3. 进入轮询循环
    loop {
        TimeoutFuture::new(POLL_INTERVAL_MS).await; // 3000ms
        // 循环体内再读一次信号（让依赖持续注册到下一轮）
        let req = MyListRequest { filter_a: filter_a(), filter_b: filter_b() };
        if let Ok(v) = list_xxx(&req).await {
            data.set(v);
        }
    }
    // 4. 组件卸载/筛选变化时，use_future 自动取消正在跑的 future
});
```

> 适用场景：后台任务列表、AOP 队列监控面板、通知中心、构建日志流。不适用：需要 websocket 推的场景（轮询间隔 < 1s 就该用 WS）

### 4.2 取消功能扩展（后续 7 步模板）

Self-Review Notes 明确"取消功能暂不实现，后续扩展时走协作式取消"。当需要取消时：
1. TaskStatus 增 Cancelled 变体（common/src/api/background_task.rs）
2. BackgroundTask trait 增 `fn cancel(&self) {}` 默认空实现 + `fn is_cancelled(&self) -> bool { false }`
3. 每个任务对象加 `cancelled: AtomicBool`；run() 方法关键步骤（如循环内）检查 is_cancelled() 后提前 return Ok(json!({ "cancelled": true })) 并把状态设 Cancelled
4. BackgroundTaskRegistry 增 `cancel_task(task_id) -> Result<bool>`：找到任务 → 调 cancel()；找不到 → Err
5. 新增 handler `task_cancel.rs`：`POST /system/tasks/{task_id}/cancel` → 路由注册
6. 前端：列表每行右侧增加"取消"按钮（仅 Running/Pending 状态显示）+ 确认弹窗 → 调 cancel API → 立即刷新列表
7. 详情弹窗内增加取消按钮（与右上角位置区分，Running/Pending 才显示）

## 七、后续扩展路径（后台任务管理增强 4 步模板）

> **核心不变量**：use_future 轮询模式 / list 返回全量 + 客户端分页 / 清理只动 Completed+Failed / 详情用列表缓存数据 不动。

1. **取消功能落地（§四 4.2 的 7 步模板）**
   - 优先向量重建任务（RebuildTask 最耗时，用户可能中途想换 Embedding Provider 时取消最有价值）。新增 Cancelled 状态、trait 方法、协作式检查点（每 embedding 100 条向量检查 is_cancelled()）→ 若取消写 result `{"cancelled":true, "progress":"34%"}` → 列表显示 Cancelled badge（自定义新颜色）/ 详情弹窗显示取消进度
2. **任务分类+标签（task_type 动态化）**
   - 现在类型下拉硬编码 6 项。方案：list_tasks 响应额外返回 `all_task_types: Vec<String>`（从 registry.values().map(|t| t.task_type).dedup() 收集）；前端类型 select 从此字段渲染选项 + 中文 label map 映射显示。新任务类型自动出现在下拉中，无需改前端代码
3. **WebSocket 推送替代 3 秒轮询**
   - 当前 3 秒一次 HTTP 请求体验尚可，但有延迟（最多 3s 才看到进度变化）+ 服务器压力。方案：升级时接入 SSE（Server-Sent Events）/ WS 推送：任务进度变化由 BackgroundTask::progress() 更新时主动触发事件推给 SystemTasks 页面；use_future 轮询作为 fallback（WS 未连接时自动降级轮询）；节省 HTTP 请求 90%+
4. **全局 Dashboard 面板卡片接入任务统计**
   - 统计 Phase 1（时序图）后 Dashboard 页面：复用本页面 SystemTasks 的 3 张统计卡片（运行中/已完成/失败）→ 抽通用 StatsSummary 组件，Dashboard 放"后台任务健康"卡片（3 计数 + 运行中点击跳转 SystemTasks）。和向量重建进度、AOP 队列监控、飞书 WS 健康 4 张卡片组成运维健康视图
