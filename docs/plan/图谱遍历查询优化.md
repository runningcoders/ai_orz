## 一、目标（为什么做）

`src/service/dal/memory.rs` 图谱遍历在两种极端场景下存在已确认问题：DFS N+1 查询导致宽前沿图 IO 放大，以及 SQLite 999 绑定参数上限在超广图/大 visited 集合时会溢出报错。

| 问题维度 | 解决方式 |
|---------|---------|
| DFS 每 pop 一个节点就单查边（N+1） | 「栈前沿批量预取 + edge_cache」模式：缓存未命中时一次批量拉取当前栈上所有未 fetched 节点的边 |
| list_relations_batch 单 SQL 两个 IN，每节点占 2 绑定 → 499 节点溢出 999 | IN 列表按 400 分块（每块 800 绑定 < 999，留安全余量），逐块执行后按 created_at ASC 重排保持结果有序契约 |
| fetch_nodes_by_ids 收尾 ids IN（1 绑定/ID）→ 999 ID 溢出 | 同上常量分块，多次调用 query_knowledge_nodes 拼接后再做共享可见性过滤 |
| traverse 零测试覆盖（当前无任何单测守护） | 新增 4 个 DAL 场景测试 + 1 个 DAO 分块测试，守护优化后行为与旧实现等价 |

**收敛后效果**：宽前沿图 DFS 查询次数从 O(节点数) 降到 O(层数/栈前沿批量)；IN 绑定溢出从 999 上限提升到理论无限（分块拼接）；测试覆盖 5 个关键场景，行为等价性 100% 守护；对外签名零改动，Domain/Handler/前端零感知。

## 二、架构思路（怎么做的）

两个优化点互不耦合，可独立测试独立合入；全部收敛在 DAL/DAO 内。

```
优化一：DFS 栈预取批量缓存（DAL：traverse_dfs）

pop (node_id, depth)
  │
  ▼
depth >= max_depth ? ──是──► continue
  │否
  ▼
fetched.contains(node_id) ? ──否──► 收集当前栈上所有未 fetched 的
  │是                              节点 ID + node_id（去重）
  │                                     │
  ▼                                     ▼
edge_cache[node_id] 取边        一次 list_relations_batch 批量取边
  │                              按双端点分组写入 edge_cache
  │                              所有 ID 标记进 fetched
  ▼
后续 take(max_breadth) 限宽 / visited_relations 去重 /
邻居压栈逻辑 → 与旧实现逐行完全一致（正确性保证）

正确性要点：
  · pop 顺序 / take(max_breadth) 的 created_at ASC 选边顺序完全不变
  · fetched（完整拉取）vs edge_cache（可能仅含他人发现的边）严格区分
  · 纯链图 A→B→C…仍是每节点一次查询（顺序依赖，接受残留）
  · 拒绝递归 CTE 方案（max_breadth / result_relations 收集复杂度高、
    可维护性差，SQL 复杂度过高）
```

```
优化二：IN 列表分块（DAO + DAL）

IN_CLAUSE_CHUNK = 400（2 绑定/ID 时 800 < 999，留安全余量；
                    1 绑定/ID 时 400 同样 < 999，统一常量）

· list_relations_batch（DAO：memory/sqlite.rs）：
  node_ids 按 400 分块 → 逐块执行现有 SQL → 拼接结果
  → 按 created_at ASC 重排（保持原有序契约）

· fetch_nodes_by_ids（DAL：memory.rs）：
  ids 按同一常量分块 → 多次调用 query_knowledge_nodes
  → 拼接后 → 共享可见性过滤（保持原过滤契约）

明确不动：query_short_term 的 ids IN 同型隐患但不在遍历路径，
本次不扩范围。
```

**关键边界 / 行为红线（回归必保）**：
1. **对外签名零改动**：优化前 → 优化后所有函数签名不变；Domain/Handler/前端零改动
2. **结果集等价性**：DFS 选边顺序（created_at ASC + take max_breadth）、visited_relations 去重、BFS 结果 — 必须与旧实现完全一致
3. **分块后排序契约**：list_relations_batch 无论切几块，结果必须按 created_at ASC 重排；fetch_nodes_by_ids 分块结果拼接后必须再做共享可见性过滤（不改 DAO query_knowledge_nodes 内部排序）
4. **拒绝递归 CTE**：不引入 SQL 复杂递归方案（SQL 复杂度 / 可维护性权衡不划算）
5. **不扩范围**：query_short_term 的 ids IN 同型隐患本次不处理；仅遍历路径相关两处

### 4.2 新增「DAO/DAL 大 IN 查询」时避免 SQLite 999 绑定溢出

| 类型 | 处理方式 | 代码参考 |
