# 知识图谱遍历查询优化（DFS 批量化 + IN 分块）

## 背景

`src/service/dal/memory.rs` 的图谱遍历存在两个已确认问题：

1. **DFS N+1**：`traverse_dfs` 每 pop 一个节点调用一次 `list_all_relations_for_node`，查询次数 = 访问节点数；BFS 已做到每层一条批量 SQL。
2. **IN 列表绑定溢出**：`list_relations_batch` 每个节点占 2 个绑定参数（source + target 两个 IN），SQLite 默认绑定上限 999，单层超过约 499 个节点会报错；同遍历路径的收尾 `fetch_nodes_by_ids`（经 `query_knowledge_nodes` 的 ids IN，1 绑定/ID）在 visited 集合很大时同样有 999 上限风险。

改动全部收敛在 DAL/DAO 内部，不改变任何对外签名，Domain/Handler/前端零改动。

## 优化一：DFS 栈预取批量缓存

文件：`src/service/dal/memory.rs` 的 `traverse_dfs`（L891-952）

方案：保留逐节点 pop 的深度优先语义，把「按需单点查边」改为「缓存未命中时批量预取整个栈前沿」：

- 新增两个局部结构：`edge_cache: HashMap<String, Vec<KnowledgeNodeRelationPo>>`（按双端点分组的边索引）、`fetched: HashSet<String>`（已完整拉取过边的节点）。
- 循环中 pop `(node_id, depth)` 后，若 `depth >= max_depth` 照旧 continue；若 `fetched` 不含 `node_id`：收集当前栈上所有未 fetched 的节点 ID + `node_id`（去重），一次调用 `memory_dao.list_relations_batch` 批量取边，按 source/target 双端点 `or_default().extend()` 写入 `edge_cache`，并把这些 ID 标记进 `fetched`。
- 从 `edge_cache` 取出该节点的边，后续 `take(max_breadth)` 限宽、`visited_relations` 去重、邻居压栈逻辑与现状逐行一致。

正确性要点：

- pop 顺序、`take(max_breadth)` 的 created_at ASC 选边顺序完全不变，结果集与旧实现等价；`visited_relations` 去重天然容忍双端点分组带来的重复边（BFS 现有代码即此模式）。
- 区分 `fetched`（完整拉取）与 `edge_cache`（可能只含经他人发现的边），避免把「部分边」误当「已拉全」而漏边。
- 已知边界：纯链图（A→B→C…）仍是每节点一次查询——顺序依赖本质上无法预取，且链节点边数极少、本地库查询微秒级，接受此残留；拒绝递归 CTE 方案（max_breadth 需窗口函数、收集 result_relations 的 SQL 复杂度高、可维护性差）。

## 优化二：IN 列表分块

- `src/service/dao/memory/sqlite.rs`：新增 `pub const IN_CLAUSE_CHUNK: usize = 400;`；`list_relations_batch`（L1231+）将 `node_ids` 按 400 分块（每 ID 2 绑定 → 800 < 999），逐块执行现有 SQL 并拼接结果，拼接后按 `created_at ASC` 重排以保持原有序契约。
- `src/service/dal/memory.rs`：`fetch_nodes_by_ids`（L954-977）将 ids 按同一常量分块，多次调用 `query_knowledge_nodes` 拼接后再做共享可见性过滤（不改 DAO 内部实现，避免影响 query_knowledge_nodes 的通用排序契约）。
- 明确不动：`query_short_term` 的 ids IN 属同型隐患但不在遍历路径上，本次不扩范围。

## 验证门槛

- `cargo fmt --all` + 后端 `cargo clippy --all-targets -- -D warnings` 干净（无前端改动，免 wasm clippy）。
- 后端全量测试通过（单元 835 → 约 840）。
- 新增 SQL 均为 QueryBuilder 动态拼接（非 `query!` 宏），**无需重生成 .sqlx 离线数据**；以 `SQLX_OFFLINE=true cargo check` 确认。

## 假设与边界

- DFS 预取在纯链图上查询次数不减少（顺序依赖本质限制），优化收益体现在宽前沿图；不引入递归 CTE。
- `query_short_term` 的 ids IN 同型隐患本次不处理。
- 分块常量取 400（2 绑定/ID 时 800 < 999，留安全余量），不依赖运行时探测 SQLite 上限。
