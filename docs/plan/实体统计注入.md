## 一、增强目标（为什么做）

5 个核心实体详情页前端"详情 + 统计"需发 2~3 次请求（实体 → 统计 → 模型调用统计），体验差且请求数多。统一采用 Agent 已有的 `with_stats` 模式补齐：

| 问题维度 | 解决方式 |
|---------|---------|
| (a) 详情 + 统计多次请求 → 用户等待时间长 | FetchOptions 扩展 5 个 query 参数（with_stats / with_model_call_stats / stats_time_start / stats_time_end / stats_interval），一次请求拿到实体+统计 |
| (b) 除 Agent 外 4 个实体无 FetchOptions 机制 → 无按需能力 | 为 Project/Task/Tool/ModelProvider 逐个新增 `XxxFetchOptions` + DAL 层 `get_xxx(ctx, id, options)` 方法 |
| (c) 统计类型缺 JsonSchema derive → 无法嵌入 OpenAPI DTO | common stats.rs 所有类型（StatsInterval/TimeSeriesPoint/TokenSumResult/CallSummary/各 XxxStats/ModelCallStats）统一加 JsonSchema |
| (d) 大字段（时间序列）每次都返回 → 带宽浪费 | 所有新增统计字段均为 `Option<T>` + `#[serde(skip_serializing_if = "Option::is_none")]`，未传 with_* 参数时不序列化也不执行统计查询 |

**收敛后效果**：5 个实体（Agent/Project/Task/Tool/ModelProvider）全部具备统一的"统计数据动态注入"能力，前端详情页一次请求拿到实体+统计。

## 二、架构思路（怎么做的）

复用 Agent 已有模式，从 Common → Model → DAL → Domain → Handler → API 6 层垂直对齐：

```
Layer 1: Common Model（基础依赖）
  └─ common/src/models/stats.rs：所有 Stats 类型加 JsonSchema derive
      │
      ▼
Layer 2: Entity Model（实体字段扩展）
  ├─ Agent：新增 model_call_stats: Option<ModelCallStats>
  ├─ Project：新增 stats + model_call_stats 两字段
  ├─ Task：新增 stats + model_call_stats 两字段
  ├─ Tool：新增 stats: Option<ToolStats>
  └─ ModelProvider：新增 stats: Option<ModelCallStats>
      │  所有字段 from_po 初始化为 None；Debug impl 同步补齐
      ▼
Layer 3: DAL 层（FetchOptions + get_xxx 注入逻辑）
  ├─ AgentFetchOptions 扩展：加 with_model_call_stats + stats_time_range + stats_interval
  ├─ 新增 ProjectFetchOptions / TaskFetchOptions / ToolFetchOptions / ModelProviderFetchOptions
  └─ DAL get_xxx 实现：options.with_*=true 时调 get_stats()/get_model_call_stats() 注入
      │  统计过滤参数（time_range/interval）透传 StatsFetchOptions
      ▼
Layer 4: Domain 层（签名扩展 + 透传 DAL）
  ├─ ProjectManage::get(project_id, options) → Project
  ├─ TaskManage::get(task_id, options) → Task
  ├─ ToolProviderManage::get_tool_with_options(tool_id, options) → Tool
  └─ ModelProviderManage::get_model_provider_with_options(provider_id, options) → ModelProvider
      │  保留原 get_xxx(id) 无 options 签名（向后兼容），新增 with_options 变体
      ▼
Layer 5: Common API（Request 加 query 参数 + Response 加 Option 字段）
  ├─ GetXxxRequest：5 个统计 query 参数（#[param(source="query")]）
  └─ GetXxxResponse：stats / model_call_stats Option 字段 + skip_serializing_if
      │
      ▼
Layer 6: Handler（参数映射 + 响应映射）
  ├─ Handler 层：把 Request query 参数 → XxxFetchOptions 结构体
  │   stats_interval 字符串（hourly/daily）→ StatsInterval 枚举
  │   stats_time_start/end → Option<(i64, i64)> 时间范围
  └─ Response：实体.stats / entity.model_call_stats → GetXxxResponse 对应字段
```

**关键边界（行为红线，回归必保）**：
1. **按需语义严格遵守**：with_*=None 或 false 时 → **不执行统计查询**、字段为 None、序列化时跳过（字节级兼容旧调用）
2. **统计查询非致命**：stats/model_call_stats 查询失败时，不能影响实体主查询返回（失败可 log_warn + 保持 None，参考运行时问题修复 §阶段 4.2 模式）
3. **时间过滤透传**：Handler 层的 stats_time_start/end、stats_interval 必须透传到 DAL 层 StatsFetchOptions，不得在 Handler 层硬编码默认值
4. **双契约兼容**：Domain 层必须同时保留 `get_xxx(id)` 和 `get_xxx_with_options(id, options)` 两种签名（旧调用不改造）
5. **JsonSchema 必须**：嵌入 Response DTO 的所有 Stats 子类型必须派生 JsonSchema，否则 OpenAPI 文档生成失败

## 四、扩展速查表（新增实体按需返回字段模式）

### 4.1 新增"实体按需注入字段"5 步模板（以 Skill 实体加 `with_usage_stats` 为例）

| 步骤 | 层 | 改动 | 代码入口参考 |
|-----|----|------|-------------|
| ① | Common Model | 如果涉及新类型（如 SkillUsageStats），加 JsonSchema derive | [stats.rs 所有类型](../../common/src/models/stats.rs) |
| ② | Entity Model | Skill 实体加 `usage_stats: Option<SkillUsageStats>`，from_po/None 同步 | [agent.rs Agent model_call_stats](../../src/models/agent.rs) |
| ③ | DAL 层 | 新增 SkillFetchOptions 结构 + `get_skill(ctx, id, options)`；options.with_usage_stats=true 时调 `get_usage_stats()` 注入 | [dal/project.rs ProjectFetchOptions + get_project](../../src/service/dal/project.rs) |
| ④ | Domain 层 | SkillManage trait 加 `get_skill_with_options(ctx, id, options)`，impl 透传 DAL | [finance/mod.rs ToolProviderManage](../../src/service/domain/finance/mod.rs) |
| ⑤ | API + Handler | GetSkillRequest 加 with_usage_stats + 时间参数；GetSkillResponse 加 usage_stats Option 字段；Handler 构建 FetchOptions + 映射响应 | [get_agent.rs](../../src/handlers/hr/agent/get_agent.rs)（query 参数 → FetchOptions 完整模式） |

> 关键入口（FetchOptions 典型结构参考）：[dal/agent.rs AgentFetchOptions](../../src/service/dal/agent.rs)

### 4.2 stats_interval 字符串→枚举映射模式

| query 字符串 | StatsInterval 枚举 |
|-------------|-------------------|
| "hourly"（大小写不敏感） | StatsInterval::Hourly |
| "daily"（大小写不敏感） | StatsInterval::Daily |
| 其他值 / None | None（默认 DAL 层兜底 Daily） |

代码参考：所有 Handler 中 `stats_interval.as_deref().and_then(|s| match s.to_lowercase().as_str() {...})`

## 七、后续扩展路径（4 步模板，按优先级）

> **核心不变量**：新增字段一律 Option + skip_serializing_if；with_*=None 语义零查询零序列化。

1. **新增实体字段注入（Skill/AgentTag/MemoryStore）**：
   - 复用 §4.1 的 5 步模板
   - 先确定：注入字段是 stats 类（需时间范围/粒度）还是简单关联字段（无过滤参数）
   - entry：[FetchOptions 参考 dal/agent.rs](../../src/service/dal/agent.rs)
2. **查询性能优化：批量统计**（当 5 实体列表页也需要统计时）：
   - 当前仅详情单实体注入，列表页改批量：`list_with_stats(ids, options)` → DuckDB IN 批量聚合
   - entry：DAL 层新增批量方法，复用现有 stats SQL 模板
3. **缓存层接入（高频访问统计）**：
   - DAL 层 stats 查询前先查 Cache（Redis 或 moka 内存缓存），key = `stats:{entity_type}:{id}:{time_range}:{interval}`
   - TTL = stats_interval 粒度对应 1~5 分钟
4. **前端对接：详情页自动注入参数**：
   - 所有 entity_detail 页面，进入时自动带 `with_stats=true` + `with_model_call_stats=true`（对支持的实体）
   - stats_interval 根据所选时间范围切换（<3 天默认 hourly，≥3 天默认 daily）
   - 参考：[项目任务增强.md §四 扩展模式](./项目任务增强.md)
