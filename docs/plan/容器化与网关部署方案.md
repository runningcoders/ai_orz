# 容器化与网关部署方案

> 目标：一件大事的三个阶段——① **容器化**降低部署成本（已完成）；② **网关互联层**完成生产代理与跨部署形态互联（选型已拍板：Caddy）；③ **去中心化组网能力**（DID / 地址同步 / 审计哈希链，非互信组织引入合同机制，实施延后）。
>
> 落地快照类文档，记录本次已实施的改动与决策；设计权衡见 `docs/design/` 相关文档。

---

## 一、起点：改造前的部署形态

| 维度 | 改造前 |
|------|--------|
| 产物 | 单二进制 + `dist/` 静态资源；`tar.gz` 手工分发（`scripts/package.sh`） |
| 数据 | 全部落在 `.ai_orz/`（SQLite、向量、工作区、日志、配置），见 `common/src/config.rs#L12` |
| 容器 | **无** Dockerfile / compose（`docs/wiki/zh/content/配置与部署.md` 明确写「未提供 Dockerfile，建议自行构建」）|
| 网关 | **无**；明文 HTTP 监听 `0.0.0.0:3000`（`common/src/config.rs#L427`，`src/lib.rs#L168`）|
| 中间件 | 仅一个访问日志层（`src/router.rs#L186`）：无 CORS、无压缩、无超时、无 trust-proxy |
| 多架构 | `release.yml` 原生构建 amd64/macos，**明确放弃交叉编译**（lancedb/ort-sys 太重）|

上网关前必须填的坑（否则放反代后面功能看着正常、实则全错）：

1. **真实客户端 IP 丢失** —— 不解析 `X-Forwarded-For`，日志与审计里全是网关 IP。
2. **Cookie 恒为 `secure=false`** —— 明文 HTTP 可用，切 HTTPS 后不符合安全基线（原代码 `src/handlers/organization/auth/login.rs#L51`）。
3. **SSE 被网关攒包** —— nginx 默认 `proxy_buffering on`，`/messages/sse` 与 `/a2a/subscribe` 的事件（含 15s 心跳）会被缓冲。
4. **联邦自报地址** —— peer 地址来自 `server.public_base_url`，容器/反代下必须显式填网关域名，否则对端拿到容器内网地址。
5. **探活路径** —— 只有 `/health`，编排系统惯用的 `/healthz` 缺失。

## 二、容器化设计

### 2.1 镜像分层（`Dockerfile`）

三阶段，全部在容器内原生构建：

| 阶段 | 内容 |
|------|------|
| `frontend-builder` | Node（Tailwind 由 `frontend/build.rs` 调 npm 包编译）+ `wasm32-unknown-unknown` + `dioxus-cli` → 复用 `scripts/build_frontend.sh` 产出 `dist/` |
| `backend-builder` | `cargo build --release --locked`（`SQLX_OFFLINE=true`，`.sqlx/` 已入库，纯离线编译） |
| `runtime` | `debian:bookworm-slim` + git/bash/curl/procps/tzdata，非 root 用户（uid 10001） |

要点：

- **构建链路唯一事实源**：前端仍走 `scripts/build_frontend.sh`，与 `make build-fe`、CI release 完全同口径，不在 Dockerfile 里另写一份。
- **运行时不含 Node/Python**：按决策取「单镜像含 git+sh+常用 CLI」。MCP stdio 若需 node/python，由用户基于官方镜像自建（见 §2.5）。
- **数据面单一挂载点**：`AI_ORZ_BASE_PATH=/data`，SQLite / 向量库 / Agent 工作区 / 产物 / 日志全在其下，备份与迁移只需处理一个目录。
- 构建期依赖 `protobuf-compiler` 与 `libprotobuf-dev`：lance-encoding 的 build script 需要 well-known types，缺 `empty.proto` 会直接失败。

### 2.2 多架构策略：原生 runner，不用 QEMU

`duckdb` 的 bundled C++ 源码编译 + `fastembed` 构建期下载 ONNX Runtime 二进制，决定了 QEMU 模拟构建既慢又易失败。因此沿用仓库既有判断（release.yml「不做交叉编译」），改为：

```
docker job: ubuntu-latest(linux/amd64) + ubuntu-24.04-arm(linux/arm64) 各原生构建
            → push-by-digest + 上传 digest artifact
docker-merge job: docker buildx imagetools create 合并多架构 manifest 并打 tag
```

tag 规则：`v*` tag 触发 → `<版本号>` + `latest`；手动触发 → `sha-<短摘要>`（避免污染 latest）。

### 2.3 编排（`docker-compose.yml`）

涉及文件：`docker-compose.yml`（编排）、`Caddyfile`（网关配置）、`.env.deploy.example`（部署环境变量模板，与开发用的 `.env.example` 区分）。

- **网关走 compose profile**：`ai_orz` 默认启动，`caddy` 属于 `gateway` profile。无域名本机试用用 `docker compose up -d`，生产用 `docker compose --profile gateway up -d`。
- `ai_orz` 端口只绑 `127.0.0.1:3000`：本机排障直连用；公网入口一律走网关，避免绕过 TLS 与限流。
- **数据目录默认 bind mount 到 `./data`**（`${AI_ORZ_DATA_PATH:-./data}:/data`）：Agent 工作区与产物要能被直接查看、用 rsync/tar 备份；命名卷在 macOS/Windows 上藏在 VM 里几乎不可见。想改回 docker 托管卷设 `AI_ORZ_DATA_PATH=ai_orz_data` 即可。
  - Linux 宿主必须先 `sudo chown -R 10001:10001 ./data`（容器内是 uid 10001）；macOS/Windows 的 Docker Desktop 会自动处理权限。
  - 另两个卷：`caddy_data`（**证书，必须持久化，丢失会重复申请触发 Let's Encrypt 速率限制**）、`caddy_config`。
- `SECRET_KEY` / `JWT_SECRET` / `AI_ORZ_DOMAIN` 由 `.env` 注入，必填校验写在 compose 里，缺值直接报错而非静默用默认密钥。
- 依赖顺序：`caddy` 等 `ai_orz` 健康后再启动，避免首分钟证书申请与后端初始化抢资源。
- 健康探测复用容器内同款 `curl /health`。

### 2.4 容器相关环境变量

| 变量 | 作用 |
|------|------|
| `AI_ORZ_BASE_PATH` | 数据根目录（镜像默认 `/data`） |
| `AI_ORZ_LISTEN_ADDR` | 监听地址（镜像默认 `0.0.0.0:3000`） |
| `AI_ORZ_PUBLIC_BASE_URL` | **联邦自报地址**，填网关域名，如 `https://orz.example.com` |
| `AI_ORZ_TRUST_PROXY` | 是否信任 `X-Forwarded-*`；置于网关后必须 `true` |
| `AI_ORZ_COOKIE_SECURE` | 登录 Cookie 的 Secure 标记；不设则按 `X-Forwarded-Proto` 自动判定 |
| `SECRET_KEY` / `JWT_SECRET` | 加密密钥与 JWT 密钥，生产必改 |

首次启动会把上述偏好固化进 `/data/ai_orz.toml`（与既有 `listen_addr` 行为一致，见 `src/config.rs#L170`）。

### 2.5 扩展：给 MCP stdio 加 Node/Python

```dockerfile
FROM ghcr.io/runningcoders/ai_orz:latest
USER root
RUN apt-get update && apt-get install -y --no-install-recommends \
        python3 python3-pip \
    && rm -rf /var/lib/apt/lists/*
# Node 建议从官方镜像拷，避免发行版自带的旧版本
COPY --from=node:22-bookworm-slim /usr/local/bin/node /usr/local/bin/node
USER ai_orz
```

### 2.6 部署步骤（容器 + 网关）

```bash
cp .env.deploy.example .env            # 填 SECRET_KEY / JWT_SECRET / AI_ORZ_DOMAIN
docker compose --profile gateway up -d
docker compose logs -f ai_orz          # 首次启动会打印配置生成与迁移日志
docker compose logs -f caddy           # 证书签发日志
```

前置：`AI_ORZ_DOMAIN` 的 DNS 已解析到本机，且 80/443 入站放行（ACME HTTP-01 校验要用 80）。

无网关本机试用：`docker compose up -d`，访问 `http://127.0.0.1:3000`（此时 `.env` 仍需 `SECRET_KEY`/`JWT_SECRET`）。

升级：`docker compose pull && docker compose --profile gateway up -d`（数据卷与证书卷不受影响）。
备份：SQLite 不宜热拷，建议停服后打包 `ai_orz_data` 卷，或用 `sqlite3 .backup` 后再归档。

### 2.7 裸机部署（同一份 Caddyfile）

非 Docker 用户适用，网关配置与容器形态完全一致：

```bash
# 1) 二进制：从 https://caddyserver.com/download 下载后放入 /usr/local/bin/caddy
#    或 apt install -y debian-keyring ...官方源安装（自带 systemd unit 与 caddy 用户）
sudo mkdir -p /etc/caddy && sudo cp Caddyfile /etc/caddy/Caddyfile

# 2) 环境变量 unit override（systemd drop-in）
sudo systemctl edit caddy
```

```ini
[Service]
Environment=AI_ORZ_DOMAIN=orz.example.com
Environment=AI_ORZ_UPSTREAM=127.0.0.1:3000
```

```bash
sudo systemctl enable --now caddy
sudo systemctl reload caddy            # 改配置后热重载，不断连接
```

`caddy` 用户需对 cert 目录有写权限（官方包安装时已配好；二进制自装需手动建 `/var/lib/caddy` 并授权）。

### 2.8 容器与宿主的边界（产物 / 工具链 / 环境变量 / 凭据）

**镜像里是 release 产物**：`backend-builder` 阶段 `cargo build --release --locked`（`Dockerfile:86`），前端走 `scripts/build_frontend.sh` 产出 release 静态资源；runtime 阶段只 `COPY` 二进制与 `dist/`（`Dockerfile:109-110`），**不含源码与任何构建工具链**。

**工具链不共享宿主**：容器有独立 rootfs，宿主的 node / nvm / cargo 一律不可见。两条路都不要走：

- 挂载宿主工具链进容器：macOS / Windows 宿主的二进制是 darwin / PE 格式，进 Linux 容器**根本不能执行**；即便 Linux→Linux，glibc 版本与动态库路径不匹配也会起不来。
- 需要 node / python 时按 §2.5 自建镜像层（`COPY --from=node:22-bookworm-slim`），版本固化在镜像里、可复现。这也是「容器化降低部署成本」的本意——工具链随镜像交付，而不是要求宿主预先装好。

**环境变量不继承宿主**：必须显式经 compose `environment` / `env_file` 注入。两个注意点：

- shell 子进程**继承服务进程全部环境变量**（`src/pkg/tool_registry/shell_env.rs:85`，注释说明真白名单代价大于收益——`TMPDIR` / `LANG` 缺失会挂掉 CLI）。传给 compose 的变量会继续传给 Agent 的 shell 工具，是能力也是泄漏面。
- MCP stdio 子进程走 `env_clear()` **零继承**（同文件模块头注释），凭据不会经 MCP 子进程泄漏。

**凭据不落环境变量**：第三方凭据（模型 API Key、飞书、微信等）存数据库 `user_credentials` 表，`detail` 敏感字段经 `encrypt_channel_secret` 加密（`enc:v1:` 前缀，见 `src/pkg/credential/mod.rs:97`），由界面/接口录入——**不需要挂载任何凭据文件**。SSH 只走 `SSH_AUTH_SOCK`，私钥与 config **恒不挂载**。

**唯一要注入的两个主密钥**：`SECRET_KEY`（数据库字段加密）与 `JWT_SECRET`。注意 `src/config.rs:273-314` 会在首次启动时把二者**明文固化进 `/data/ai_orz.toml`**——这是刻意设计（漏传 env 时已加密数据仍能解开），但意味着 `./data` 等同密钥库：目录 `700`、文件 `600`、备份必须加密，`/data` 已在 `.gitignore` 中。

## 三、网关选型（拍板：Caddy）

### 3.0 为什么「吞吐性能」不是首要权重

2026 年公开基准（TLS 终止 + HTTP/2 反代，Graviton4 16 核，独立测试方 dargslan）：

| 指标 | Caddy 2.8 | Nginx 1.26 | HAProxy 3.0 |
|------|-----------|------------|-------------|
| req/s | 78,500 | 92,300 | 118,000 |
| p99 延迟 | 9.8ms | 7.4ms | 5.2ms |
| 峰值内存 | 180MB | 120MB | 95MB |

差距要跑到**数万 RPS 量级**才有意义。ai_orz 的真实流量画像是：**长连接多（SSE 流式 + 联邦 WS）、单请求时延长（LLM 推理分钟级）、RPS 低**——瓶颈永远在推理链路，不在代理层。为用不到的 15% 吞吐，多付证书运维和 SSE 踩坑成本，不划算。

### 3.0.1 真正的权重：可部署性 + 互联能力

两个前提决定了权重排序：「不论容器还是裸机部署，网关都是互联层」+「网关选型要撑得住去中心化阶段（联邦 = N 个组织各自部署）」。由此得出的硬性要求：

| 硬性要求 | 为什么 | Caddy | Nginx |
|---|---|---|---|
| 证书全自动（申请+续期+热加载） | 证书运维量随联邦节点数**线性放大**，手工 certbot 不可持续 | 内置 ACME，零配置 | certbot 外挂 + 定时器 |
| SSE 默认不缓冲 | agent 流式与联邦订阅是主通道，攒包=吞心跳 | 默认正确（`flush_interval -1` 显式加固） | 必须显式 `proxy_buffering off`，忘写即故障 |
| WebSocket 免配置 | 联邦长连接 `/api/v1/organization/links/ws` | 自动透传 Upgrade | 手写 Upgrade/Connection 映射 |
| 裸机零依赖部署 | 非 Docker 用户的部署成本 | 单静态二进制，无运行时依赖 | 系统包 + certbot 生态 |
| 容器镜像 | compose 一等服务 | 官方镜像 ~50MB | 官方镜像 |
| 热重载不断连接 | 改配置不杀联邦长连接 | admin API 零停机 | reload 换 worker（也不断连，但需 `nginx -s reload`） |
| `/.well-known/` 静态托管 | 阶段三 did:web 解析 = HTTPS GET 该路径 | `file_server` 内置 | 内置 |
| mTLS 预留 | 对端身份从 link 凭证升级为证书 | `tls client_auth` 内置 | 内置 |

### 3.0.2 Caddy 已知短板与接受理由

- **限流非内置**（需 xcaddy 插件）：本就计划交给后端策略引擎，且所有单实例网关的限流在多实例下都会失效，不构成选型区分度。
- **超大文件流式吞吐** nginx 略优（约 15-17%）：ai_orz 无大文件分发场景。
- **Go GC 常驻内存** ~30MB（nginx ~10MB）：现代机器上是噪音。
- **生态较小**：我们只把它当 dumb proxy 用（TLS + 转发 + 头处理），不碰插件生态。顺带收益：Go 无内存安全类 CVE（nginx 2026-07 曾一个版本修三个，含一个存在 15 年的 9.2 分堆溢出）。

### 3.0.3 防迁移原则：网关保持 dumb

**迁移成本不取决于选了哪个网关，取决于耦合了多深的网关特有功能。** 规则：

1. 网关只做四件事：TLS 终止、反代转发、`X-Forwarded-*` 头、请求体大小限制。
2. 限流、鉴权、灰度、重写一律不下沉网关（`encode` 压缩除外——无状态、语义通用）。
3. 遵守这条，任何网关间的迁移都是小时级；违反这条，Caddy 换 Envoy 就是按周计的重构。

### 3.1 Caddy 参考配置（主选）

仓库根目录 `Caddyfile` 是实际使用的配置（域名与上游走环境变量，避免硬编码），下面是它的实例化形式：

```caddyfile
orz.example.com {
	encode zstd gzip

	reverse_proxy 127.0.0.1:3000 {
		# SSE：Caddy 默认不缓冲，显式关闭 flush 间隔更稳妥
		flush_interval -1
		transport http {
			# 联邦 WS 与 SSE 是长连接，不能沿用默认读超时
			read_timeout  0
			write_timeout 0
		}
	}

	request_body {
		max_size 200MB
	}
}
```

裸机（非容器）形态：下载 Caddy 单二进制放入 `/usr/local/bin`，systemd unit 直接以同一份 Caddyfile 启动，证书缓存目录给运行用户写权限即可——配置与容器形态完全一致，无需维护两份。

### 3.2 Nginx 参考配置

```nginx
map $http_upgrade $connection_upgrade { default upgrade; '' close; }

server {
    listen 443 ssl http2;
    server_name orz.example.com;
    ssl_certificate     /etc/letsencrypt/live/orz.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/orz.example.com/privkey.pem;

    client_max_body_size 200m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket 升级：联邦组网 /api/v1/organization/links/ws
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        # SSE：不关缓冲会导致事件攒包（连心跳一起被吞）
        proxy_buffering off;
        proxy_cache     off;
        chunked_transfer_encoding on;

        proxy_read_timeout  3600s;
        proxy_send_timeout  3600s;
    }
}
```

labels:

### 3.4 网关侧通用注意事项

- **不要在网关层做 SPA file fallback**。后端已内置 `SpaFallback`：无扩展名路径返回 200 + `index.html`，`/api/` 未匹配明确 404（`src/router.rs#L21-L93`）。网关若再加一层 try_files 会掩盖接口缺失。
- **务必转发 `X-Forwarded-Proto`**，否则自动 Cookie Secure 判定失效。
- **多级代理链路由最外层网关重写 `X-Forwarded-For`**：本服务取该头**最右**一项作为客户端 IP（左侧条目客户端可伪造），见 `src/middleware/proxy.rs`。

## 四、联邦（跨组织组网）适配

| 事项 | 处理 |
|------|------|
| 自报地址 | `AI_ORZ_PUBLIC_BASE_URL=https://orz.example.com`，两侧节点都要配；改域名后需重新同步目录 |
| 长连接 | `/api/v1/organization/links/ws` 需网关透传 Upgrade 并放宽读超时 |
| SSE | `/a2a/subscribe` 与 `/messages/sse` 需关闭缓冲（后端已补 `X-Accel-Buffering: no` 兜底） |
| 内网优先探测 | peer 多地址探测与 TTL 缓存（`src/service/dao/organization_link/resolver.rs`）不受网关影响，但候选地址里的公网项必须指向网关域名 |
| 出站 | 联邦出站走 `ssrf_guarded` 预设（显式禁用系统代理，见 `src/pkg/http/presets.rs`），放公司正向代理后面时需单独评估 |

## 五、本次已补的生产化缺口

| 项 | 位置 |
|----|------|
| `server.trust_proxy`：真实客户端 IP（取 XFF 最右项），未开启时完全忽略该头 | `src/middleware/proxy.rs`、`common/src/config.rs#L150` |
| 访问日志带 `client_ip` 字段 | `src/middleware/api_notice.rs` |
| Cookie Secure：显式配置优先，否则跟随 `X-Forwarded-Proto`（仅在 trust_proxy 下采信） | `common/src/config.rs#L411`、`login.rs` / `register.rs` / `logout.rs` |
| `/healthz` 探活别名 | `src/router.rs#L186` |
| SSE 响应补 `X-Accel-Buffering: no` + `Cache-Control: no-cache` | `src/middleware/sse_headers.rs` |
| `AI_ORZ_PUBLIC_BASE_URL` / `AI_ORZ_TRUST_PROXY` / `AI_ORZ_COOKIE_SECURE` 环境变量 | `src/config.rs#L40` |

## 六、明确未做（YAGNI，按需再补）

- **CORS**：前后端同源部署，网关也在同一域名下，不需要。
- **压缩**：由网关 `encode zstd gzip` 承担，避免后端重复实现。
- **限流 / 鉴权前置**：放网关层做，后端不重复造。
- **TLS 终止**：交给网关，后端保持明文 HTTP。
- **`/metrics`**：暂无 Prometheus 需求，观测先用内部 DuckDB 统计。
- **静态资源缓存头**：`ServeDir` 未设 `Cache-Control`（带 hash 的资产可长缓存、`index.html` 需 no-cache），有性能诉求时再补。

## 七、一件大事的三个阶段（总路线图）

> 网关、部署、去中心化不是三件事，是同一件事的三个阶段：容器化解决「跑得起来」，网关解决「连得出去」，去中心化解决「谁都能来连」。前两个阶段是后者的部署基座。

### 阶段一：容器化（✅ 已完成，见 §二）

Dockerfile 三阶段构建、compose 编排、GHCR 多架构镜像（原生 runner + manifest 合并）、后端生产化缺口（trust-proxy / Secure Cookie / SSE 防缓冲 / healthz）全部落地。

### 阶段二：网关互联层（✅ 已接入）

Caddy 已定为默认网关（见 §三），落地项与产出：

| 落地项 | 产出 |
|--------|------|
| Caddy 配置 | `Caddyfile`（`AI_ORZ_DOMAIN` / `AI_ORZ_UPSTREAM` 环境变量注入，容器裸机同一份） |
| compose 集成 | `docker-compose.yml` 增加 `caddy` 服务（`gateway` profile）+ `caddy_data` / `caddy_config` 卷 |
| 联邦相关环境变量接线 | `ai_orz` 服务增加 `AI_ORZ_PUBLIC_BASE_URL` / `AI_ORZ_TRUST_PROXY` / `AI_ORZ_COOKIE_SECURE` |
| 部署环境变量模板 | `.env.deploy.example`（与开发用的 `.env.example` 区分） |
| 裸机形态 | §2.7 systemd drop-in + 热重载 |

剩余待验证（需真实域名与机器，本机无 docker/caddy 无法自测）：

1. 证书签发与自动续期全链路。
2. 联邦联调：两侧节点 `AI_ORZ_PUBLIC_BASE_URL` 指向各自网关域名后，验证目录同步与建联。
3. 长连接实测：`/messages/sse` 心跳不被吞、`/api/v1/organization/links/ws` 长连接在网关后稳定。

### 阶段三：去中心化能力（已论证，实施延后，落地时另立 plan 文档）

- **Phase A（底座）**：组织 DID（`did:web` 为主、内网 `did:key`，自写 Ed25519 最小实现、不引 ssi crate）→ 网关侧对应要求：托管 `/.well-known/did.json`；地址列表 gossip（复用 directory 同步 payload + cron 对账，不引 libp2p）；审计日志哈希链（复用 AOP 事件 + cron，`prev_hash` + Merkle root）。
- **Phase B（可验证交付）**：结构化验收标准 + 超时自动裁决 + 签名证据包。
- **Phase C（价值交换）**：计量与结算（记账式 ledger，不接真实支付）。

签名底座是阶段三的前置：JWT 目前仅 HS256 对称签名（`src/pkg/jwt.rs#L103`），无非对称能力、无密钥管理，Phase A 第一步补齐。

> **Phase A 第一步已单独立项**：见 [联邦鉴权升级方案](docs/plan/联邦鉴权升级方案.md)（静态 token → `did:key` 组织密钥对 + 每请求 Ed25519 签名，双模回退兼容旧版本）。方案已定，未实施。

### 非互信组织：合同机制（远期方向留存）

互信组织（邀请制）维持现状——A2A `tasks/send` 入站即建 Project 执行，无前置。非互信组织派任务时引入合同层，核心设计与哲学：

- **状态机**：要约 Offer → 承诺 Accept（双签生效）→ 交付 Deliver（附产出物哈希证据）→ 验收 Accept / 拒收 Reject → 结算 Settled / 争议 Disputed。
- **三个关键机制**：
  1. **双签生效、各存一份**：合同双方各持一份 + 交叉签名，哈希一致即为同一份合同——不引入共享状态，与 D1「集团名纯展示消解一致性」同一哲学。
  2. **超时自动裁决**：合同必须预置超时行为（未承诺→Expire、未交付→Breach、未验收→自动 Accept），否则流程挂起无解。
  3. **验收标准机器可判定**：结构化断言（`artifact_exists` / `schema_match` / `test_pass` / `human_approve` / `llm_judge`），不可自动判定的显式走争议通道。
- **争议处理不做链上仲裁**：导出签名证据包（Merkle root + 双签），离线可验证，线下解决。
- **明确不做**：链上 DID、libp2p/DHT、BFT 共识、代币激励、Agent 执行结果上链。

依赖关系：合同机制依赖 Phase A 的组织密钥对 + `organization_links` 增加信任等级字段（互信=现状快速路径，契约=必须走合同流程）。现有链路零改动，合同是可选前置层。
