## 一、目标（为什么做）

| 问题维度 | 解决方式 |
|---------|---------|
| 撤回已入队但未处理的过时/错误消息 | 写入 `MessageStatus::Recalled` + 消费者入口守卫（出队即 ack 跳过） |
| 取消正在处理的消息 | 复用 `cancel_thinking(agent_id)`（轮次边界中断），在飞定位靠运行时状态反向索引 |
| 新纠正消息被旧消息 FIFO 堵死 | 先撤回旧消息 → 队列快速跳过（Phase 1），无需物理移除事件 |
| 同 Agent 积压里「下一条先处理谁」不可控 | ⏸ 顺延下一期：发送入口透传 `priority`（默认 0）→ 事件 → 同 key 等待队列重排（方案见 [design §3.3](../design/message_recall_design.md)） |
| 谁可以撤回 | Domain 层权限 gate：发送方 / **收件方（仅未处理消息）** / 归属用户 / Owner Agent / SuperAdmin |
| 谁可以取消思考 | Domain 层**仅做存在性校验、不设关系门**（与既有跨 Agent 工具一致）：任意 Agent 可取消任意 Agent 的当前轮次；不存在的目标 → `NotFound` |

**收敛后效果**：撤回与取消共享既有机制（状态枚举 + 取消信号 + Discard-via-ack）；priority 走队列**既有**堆序通路 ⇒ **AOP 队列零改动**，Phase 1 即可交付主场景。

## 二、架构思路（怎么做的）

```
撤回请求（Agent tool / REST / 前端）
  │
  ▼
MessageDomain::recall_message（权限 gate + 状态 gate）
  │  ├─ 已在飞（运行时状态命中）→ cancel_thinking(agent_id) + update_status(Recalled)
  │  │    └─ 若持有者正是调用者自己 → InvalidRequest，引导改用 cancel_thinking
  │  ├─ Pending                  → MessageDal::update_status(Recalled)
  │  └─ Processed / Failed / 已撤回 → 幂等返回，不报 error
  ▼
（Phase 1 不动物理队列）事件仍在 AOP 队列
  ▼ 事件出队
MessageConsumer::handle_message
  ├─ find_by_id 返回 None（撤回态被软删除过滤挡掉）
  │    └─ find_by_id_with_recalled 确认「已撤回」→ return Ok（等价 ack，零 LLM）
  └─ 确认不了（行真不存在）→ 才上抛 not_found
  ▼
门闩推进 → 后继消息出队
```

**关键边界 / 行为红线（回归必保）**：见 [design §四](../design/message_recall_design.md) 编号 1-18。其中**最易回归的三条**：
1. 收尾写入有**两条路径**，都必须拦 `Recalled` —— `on_consumed`（ack / Discard 后回调，当前无条件写 `Processed`）与 `on_failed`（`Retry` 时无条件写回 `Pending`）。漏任一条，撤回都会被收尾写入抹掉。
2. 撤回态在业务读路径上是 `None`（软删除过滤）⇒ 消费者守卫必须在 `None` 分支区分「已撤回」与「不存在」，且**返回 `Ok`**（上抛会 nack 重投 8 次，反而堵死队列）。
3. 在飞判定**不看** `messages.status`（`Processing` 当前无写入路径），只用运行时状态反向索引。

## 四、改动入口速查表

### 4.1 撤回领域方法（核心编排点）
| 状态 | 处理逻辑 | 备注 |
|------|---------|------|
| 已在飞（运行时状态命中 `current_message_id`） | `cancel_thinking(agent_id)` + 标 `Recalled` | 尽力而为，轮次边界；**不看 DB `status`** |
| `Pending`（无人在跑） | 标 `Recalled`，队列事件出队即被守卫跳过 | 主路径 |
| `Processed` / `Failed` | 幂等返回 `not_recallable` | 不报 error |
| `Recalled` | 幂等返回 `already_recalled` | 不报 error |
| 撤回者 = 正在处理该消息的 Agent 自己 | `InvalidRequest` + 点名 `cancel_thinking` | 防自断成半截状态 |
> 入口：[recall.rs](src/service/domain/message/recall.rs)；读消息走 `find_by_id_with_recalled`（`find_by_id` 会把撤回态过滤成 `None`）

### 4.2 消费者守卫（队列跳过点）
| 检查位置 | 处理逻辑 |
|---------|---------|
| `handle_message` 分发前 | `find_by_id` 为 `None` → `find_by_id_with_recalled` 确认已撤回 → `return Ok`（等价 ack）；确认不了才上抛 `not_found`；`Some(m)` 时再兜底判一次 `status == Recalled` |
> 代码入口：[consumer/message.rs::handle_message](src/consumer/message.rs#L180-L213)

### 4.3 在飞取消（复用点）
| 能力 | 复用来源 |
|------|---------|
| 在飞定位 | 新增 [agent_runtime_state.rs::find_busy_agent_by_message](src/pkg/agent_runtime_state.rs)（`current_message_id` 反向索引） |
| 取消信号 | [agent_runtime_state.rs::cancel_thinking](src/pkg/agent_runtime_state.rs#L272-L279) |
| 取消感知 | [think_loop.rs](src/service/domain/runtime/think_loop.rs#L360-L375) 每轮开头 `is_cancelled` |

### 4.4 工具暴露（Agent 可调用）

| 工具注册 | 宏内 `ctor` 启动即注册，无需手工登记 |

### 4.5 发送入口优先级透传（priority）—— ⏸ 本期未落地
| 关注点 | 动作 |
|-------|------|
| 状态 | 用户拍板**顺延下一期**；本期一行代码未动（`messages` 表无 `priority` 列、事件 `priority()` 仍为默认 0） |
| 语义 | 只重排同 key 的**等待队列**（`priority desc, created_at asc`）；**不能抢占在飞** ⇒ 工具描述不得承诺「打断当前处理」 |
| 默认值 | `0` = 现行为；存量行迁移补 0；仅显式指定时生效 |
| 取值 | `u8`（越大越优先）；**不引入** `PriorityLevel` 枚举（避免 LLM 参数 schema 出现判别联合 + 多一层值映射） |
| 透传链 | 发送 DTO `priority: Option<u8>` → Send Command → `MessagePo.priority` → `MessageCreatedEvent.priority` → 封套 → 队列堆序（队列零改动） |
| 与撤回的关系 | **互补**：priority 决定「下一条谁先上堆」，`recall_message` 决定「这条还要不要处理」；要打断在飞只能靠 recall |
> 依据：[design §3.3 / §四 红线 13-14](../design/message_recall_design.md)

**与计划的偏离项（6 处，均已回写 design §四 红线 15-20）**

| # | 计划 | 实际 | 原因 |
|---|------|------|------|
| 1 | 消费者「加载后判 `status == Recalled`」 | 改为在 `None` 分支用 `find_by_id_with_recalled` 区分「已撤回」/「不存在」 | `find_by_id` 带 `status != 0` 软删除过滤 ⇒ 撤回的消息根本读不出来，原写法是死代码；且**必须 ack**，上抛会 nack 重投 8 次反而堵死队列 |
| 2 | 「`Processing` 撤回 → 转取消链路」 | 在飞判定改用 `AgentRuntimeStateManager::find_busy_agent_by_message` | `MessageStatus::Processing` **没有任何写入路径**，按 DB 状态判永远判不到 |
| 3 | 权限 gate 在 Domain 单点实现（含项目判据） | 按既有 `user_dal` / `agent_dal` 注入先例，给 `MessageDomainImpl` **新注入 `project_dal`** | Domain 层无「跨域调用」先例（禁同层互调），但 Domain 组合多个 DAL 是既有模式 |
| 4 | 只补 `recall_message` 的 `neural` | **同时**给 `cancel_thinking` 补 `neural` | 后者原只挂 `collaboration`（从未进任何 `installed_tags`）⇒ 也是死工具；而 `recall_message` 拒绝「撤回自己正在处理的消息」时点名它作替代 |
| 5 | 权限 gate 四类判据 | **增判据⑤「收件方」**（`ctx.agent_id() == message.to_id`），且**不叠加 status 校验** | 消息按收件方串行排队、队列只认先来后到 ⇒ 收件方对自己队列里已作废的指令原本无任何手段丢弃，只能等发送方发现。「卡在旧消息流程上」的痛点只解决了发送侧一半。status 归一交下游 `NotRecallable`，避免重复校验（design §四 红线 19） |
| 6 | `cancel_thinking` 保持 handler 直调、零校验 | 存在性校验**下沉 Domain**（`runtime/cancel.rs`），handler 退化为 DTO 映射 | Handler 直调时 `cancel_thinking("<不存在的ID>")` 与「Agent 空闲」返回完全一致（`success=false`）⇒ 调用方分不清「没这个 Agent」与「没在思考」，拼错 ID 也被静默吞掉。校验后语义二分：不存在 → `NotFound`（Error）；存在但空闲 → `NotThinking`（正常 no-op）。**这是消除语义歧义、不是收紧权限**（design §四 红线 20）|
