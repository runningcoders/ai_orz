## 一、重构目标（为什么做）

给 AOP 队列监控页面加**实时统计图表**（概览卡片 + 时序折线 + 状态/消费者环形分布），通过**纯内存**收集器滑动窗口记录 publish/consume/success/failure 事件，前端 5 秒轮询查询。零 DuckDB 依赖、零 DAO/DAL 中转、重启即重置（与 AOP 事件本身生命周期一致）：

| 问题维度 | 解决方式 |
|---------|---------|
| (a) 原 DuckDB 持久化方案：需写 DAO/DAL + stats 专用表 + DuckDB SQL，AOP 重启丢不丢无实际业务价值（历史数据无人用） | **纯内存收集器**（`AopStatsCollector`），不落任何 DB；内存占用 < 50KB；查询毫秒级 |
| (b) AOP 框架不能有业务依赖（分层红线）：在 pkg/aop 层直接记录统计会破坏零业务依赖原则 | **Hook 模式**：`pkg/aop` 定义 `AopMetricsHook` trait（4 回调），Registry 持有 `Option<Arc<dyn AopMetricsHook>>`；**业务层实现 trait 并注入**，AOP 框架永远看不到具体的统计结构 |
| (c) 采集性能不能阻塞 AOP 主流程：collector 写 RwLock 如果在 publish/worker 同步调，会阻塞事件分发与消费 | 业务 `AopStatsHook` 的 4 回调内**用 `tokio::spawn` 异步写 collector**（不 await），立即返回；collector 内部用 `Arc<RwLock<Inner>>` 单写多读，写入只是 HashMap fetch_add + 滑动桶 push，微秒级 |
| (d) 现有 AOP 监控页（实时事件列表 + 详情 Modal）不能破坏：统计图表不能把用户正在用的监控功能挤走 | **Tab 布局双视图**：Tab 1「实时监控」= 现有内容零改动；Tab 2「统计图表」= 新增卡片+图+轮询；用户可自由切换互不干扰 |
| (e) 查询与采集中间层冗余：SystemDomain → DAO → DAL → Collector 的四层链对纯内存数据是负担 | **SystemDomain 直接持有 `Arc<AopStatsCollector>`**，零 DAO/DAL；Handler 拿 `system.aop_stats()` 直接读内存快照返回 DTO |

**收敛后效果**：7 Task 完成原 DuckDB 方案 10 Task 的等价能力；AOP 事件统计查询延迟毫秒级；前端 Tab 新增零回归（监控 Tab 像素级一致）；新增同类内存统计 Collector ≈ 复制 4 步模板（Trait + Collector + 注入 + 端点）。

## 二、架构思路（怎么做的）

Hook 注入 + 内存收集 + 零中转查询 三段式（保持 AOP 框架零业务依赖红线）：

```
┌──────────────────────────────────────────────────────────┐
│ 前端 SystemAop 页面（Tab 双视图，轮询）                   │
│  ├─ Tab 1 实时监控（原内容零改动）                        │
│  │    队列统计卡片 + 事件列表 + 事件详情 Modal              │
│  └─ Tab 2 统计图表（新增，5 秒轮询）                      │
│       概览卡片（5项：发布/消费/成功/失败/平均耗时）         │
│       LineChart 事件趋势（60 分钟按分钟桶）                │
│       DonutChart 状态分布（success/failed/published ...） │
│       DonutChart 消费者分布（Top N 消费者）              │
│       最后更新时间戳（每次轮询刷新）                       │
└──────────────┬───────────────────────────────────────────┘
               │ HTTP GET /api/v1/system/aop/stats/*（3端点）
               ▼
┌──────────────────────────────────────────────────────────┐
│ Handlers → SystemDomain AopStats 子能力                  │
│  handlers/system/aop_stats.rs 3 端点：                    │
│    GET /overview        → AopOverview DTO                │
│    GET /time-series     → AopTimeSeriesResponse（60桶）   │
│    GET /distribution    → AopDistributionResponse        │
│       ?dimension=status|consumer|kind                    │
│  SystemDomain：直接读 Arc<AopStatsCollector>              │
│       ↑↑↑ 零 DAO / 零 DAL / 零中转 ↑↑↑                    │
└──────────────┬───────────────────────────────────────────┘
               │ 读（查询快照：Arc<RwLock<Inner>>.read()）
               ▼
┌──────────────────────────────────────────────────────────┐
│ AopStatsCollector（纯内存，重启即重置）                    │
│  Inner {                                                  │
│    total_counts: HashMap<(kind,consumer,status), u64>     │
│    time_buckets: VecDeque<TimeBucket>（60 个分钟桶）       │
│    total_duration_ms: u64                                 │
│    completed_count: u64                                   │
│  }                                                        │
│  API：record_publish / record_start / record_success /    │
│       record_failure（供 AopStatsHook 调用）              │
│       snapshot_overview / snapshot_time_series /          │
│       snapshot_distribution（供 SystemDomain 查询）       │
└──────────────┬───────────────────────────────────────────┘
               │ 写（4 种回调，tokio::spawn 异步不阻塞）
               ▼
┌──────────────────────────────────────────────────────────┐
│ AopStatsHook（业务层实现，注入到 Registry）                │
│  impl AopMetricsHook for AopStatsHook {                   │
│    on_publish(c, m, async)     → tokio::spawn collector   │
│    on_consume_start(c, m)      → tokio::spawn collector   │
│    on_consume_success(c, m, d) → tokio::spawn collector   │
│    on_consume_failure(c, m, d, e) → tokio::spawn collector│
│  }                                                        │
│  注入点：lib.rs run() 启动时：                             │
│    registry().set_metrics_hook(Arc::new(AopStatsHook))    │
│    domain.set_aop_stats_collector(Arc::clone(&collector)) │
└──────────────┬───────────────────────────────────────────┘
               │ Registry 持有 hook：Option<Arc<dyn AopMetricsHook>>
               ▼
┌──────────────────────────────────────────────────────────┐
│ AOP 框架层（pkg/aop）—— 严格零业务依赖                     │
│  AopMetricsHook trait（4 回调 + 空默认实现）               │
│     on_publish / on_consume_start /                       │
│     on_consume_success / on_consume_failure               │
│  Registry 3 处埋点（不感知业务）：                         │
│    1. publish() 分发循环 → 每个 consumer publish + 同步消费│
│    2. worker 协程 → on_event() 前后 start + success/failed │
│  注：未注入 hook 时 0 开销（None 直接跳过）                │
└──────────────────────────────────────────────────────────┘
```

**关键边界（行为红线，回归必保）**：
1. **AOP 框架零业务依赖红线**：`pkg/aop/core/metrics_hook.rs` 的 `AopMetricsHook` trait 和 `AopEventMeta` **禁止引用任何非 pkg 模块**（尤其禁止 use consumer / domain / common::api ）。字段定义只允许用 `std` 类型 + `serde_json::Value`
2. **Hook 异步写不阻塞主流程红线**：`AopStatsHook` 4 个实现方法**必须在第一行 `tokio::spawn`**，立即返回 `()`；禁止 `.await` 任何 collector 写操作，禁止 `write().await` 同步阻塞 AOP worker
3. **Collector 读写红线**：写操作只增不减（无删除语义，重启即重置）；滑动窗口 `time_buckets` 过期桶（>60 分钟）统一在写时惰性清理（每次写清一次旧桶），查询绝不清理（避免读锁中做可变性操作）
4. **Tab 1 零改动红线**：`system/aop.rs` 现有的"队列统计卡片区 + 事件列表区 + 事件详情 Modal"**除了被 `if active_tab=="monitor"` 包裹外，代码不得有任何增删改（像素级回归保证）
5. **轮询间隔红线**：前端 5 秒轮询（`std::time::Duration::from_secs(5)`）硬编码不暴露配置；禁止缩短到 1 秒以免对纯内存查询造成无意义压力（无持久化实时性需求不高）

### 与计划的 2 处微小偏离（均为架构优势调整，非问题）
1. **`set_aop_stats_collector` 从 Task 2 移到 Task 4**：原计划在 collector 内提供一个全局 `OnceLock` 单例供 SystemDomain 拿，最终改为「lib.rs 启动时 new collector → 通过 domain setter 注入」模式。好处：去掉一个隐式全局单例（与现有 DAO/Domain 依赖注入风格一致）；单元测试可以直接 new 不同 collector 无冲突（原 OnceLock 全局模式下测试间会互相干扰）
2. **前端 Tab 切换从 RadioGroup 改为双 Button（btn-ghost vs btn-primary）**：原计划用 Dioxus UI kit 的 RadioGroup（需引入新组件依赖），实际实现用现有 DaisyUI 两个 button + active_tab 读信号切换样式，减少一个前端 import，现有页面风格更统一（同其他页面 Tab 切换视觉一致）
