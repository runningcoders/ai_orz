# 联邦鉴权升级方案（静态 token → 组织公钥签名）

> 目标：把跨组织调用的鉴权从「长期静态共享密钥」升级为「组织密钥对 + 每请求签名」，为去中心化三阶段（DID / 地址同步 / 审计哈希链）与非互信组织的合同机制提供密码学底座。
>
> 前置：`docs/plan/容器化与网关部署方案.md` §七（三阶段路线图）、`docs/plan/跨组织业务调用方案.md`（P1-P8 现有实现）。
> 状态：**方案已定，未实施**。DID 方案拍板 `did:key`。
>
> **前提：项目尚未上线，无旧版本兼容负担。** 因此本方案不设过渡态、不设双模回退、不做灰度——一次性切换到最优形态。若未来出现版本并存，届时再按真实版本协商需求单独设计（那时的需求会比"猜一个兼容方案"明确得多）。

---

## 一、为什么现在做

它是阶段三的关键路径，三项后续能力全部依赖「组织持有密钥对」：

| 后续能力 | 依赖什么 |
|----------|----------|
| 审计哈希链与证据包 | 需要组织私钥对记录签名，否则哈希链只防篡改、不防抵赖 |
| 地址列表 gossip | 地址公告需签名，否则任意节点可伪造地址劫持流量 |
| 引荐式发现 | 介绍信需推荐方签名，接收方才能信任 |
| 非互信组织合同机制 | 要约/承诺双签、交付留痕，本质是同一套签名的业务化封装 |

现状的三个具体问题：

1. **凭证长期不变**：`access_token` / `peer_token` 一次生成后永不过期，泄露即长期可用。
2. **可重放**：入站只做 `SHA-256` 哈希匹配（`src/middleware/federation_identity.rs#L64-L76`），截获一次请求即可无限重放。
3. **身份绑在连接上**：换地址/换域名要断联重配——根因是身份没有独立于地址的稳定标识。

## 二、现状（改造前）

| 环节 | 实现 |
|------|------|
| 入站鉴权 | 单一判定点 `resolve_federation_identity()`（`src/middleware/federation_identity.rs#L64-L76`）：凭证哈希匹配 → 能力门禁 → 声明一致性 → 接待用户映射 |
| 出站凭证 | A2A 委派（`src/service/dao/agent_runtime/a2a.rs#L37-L48`）、目录拉取（`src/service/dao/organization_link/http.rs#L49`）、WS 握手（`src/service/dao/organization_link/ws/session.rs#L143-L145`）三处各带 `Authorization: Bearer` |
| 建联 | 配对码交换双方 endpoint + 双向独立 token（`src/service/domain/organization/org.rs#L249-L300`） |
| 目录同步 | `PeerOrgDirectoryEntry` 只带元信息，无身份密钥（`common/src/api/organization_link.rs#L68-L90`） |
| 非对称能力 | **无**。仅 `sha256` / `jsonwebtoken`（HS256，`src/pkg/jwt.rs#L103`）/ `base64` |

**改造面比预期小**：入站只有 1 个判定函数，且第 1 步之后的「能力门禁 / 声明一致性 / 接待用户映射」三段逻辑完全不动；出站 3 处加签名头即可。

### 2.1 信任模型的边界：配对码证明什么、不证明什么

**地址是带外知识，配对码不承担发现职责。** `CreateLinkRequest` 同时要求 `pairing_code` 与 `peer_endpoint`（`common/src/api/organization_link.rs#L121-L127`，两个字段都做非空校验）。完整方向是：B（邀请方）管理员签发配对码 → 带外告知 A → A 的管理员同时填入「配对码 + B 的地址」→ A 的服务端出站拨 B 的 `/links/pairing/verify`。

**B 侧唯一的校验是配对码哈希。** 在 `verify_pairing_code()` 中，`req.local_org`（id / name / base_url）、`req.local_endpoint`、`req.local_token` 全部由 A 自报、B 原样落库（`src/service/domain/organization/org.rs#L280-L300`）。

结论：**配对码是授权（authorization），不是认证（authentication）**——它是持有者凭证（bearer capability），持有即有效。由此产生三个后果：

| 后果 | 说明 |
|------|------|
| 首达者即身份 | 配对码签发时 B 不知道谁会来兑。有效期内谁先拨入，谁就定义自己的 id / 名称 / 地址 |
| 连接可被覆盖 | link 已存在时，凭一个新配对码 + 自报同一 org id，`find_by_pair` 命中后走 `update` 分支（`src/service/domain/organization/org.rs#L280-L297`），endpoint 与凭证被就地改写 |
| 带外信道即信任根 | 配对码经 IM / 邮件 / 口头传递，该信道的安全性就是联邦信任的上界 |

这个边界决定了本次升级的**真实价值排序**，需要先讲清楚以免高估：

- 签名**不能**关闭「首达者即身份」窗口——攻击者在建联时出示自己的密钥即可，同样被接受。
- 签名**能**把建联之后的冒充从「静默成功」变成「验签失败」，即由**不可检测**变为**可检测**（fail-closed）。
- 要真正关闭首达者窗口，必须在**签发时钉住预期身份**（见 S2）。

> 推论：DID 方案（did:key 还是 did:web）不决定这个窗口是否关闭——**钉住（pinning）才决定**。did:web 只是让「钉子」是人类可读的域名，而域名同样来自带外信道。

### 2.2 授权落点：能力由合约派生

大组网（多设备 / 多组织自然组网）目标下，token 签发模式的不便不是主要问题，**身份不唯一**才是：`organizations.id` 是本端 UUID，跨网无意义，只能靠 link 关联。三层分工因此是：

| 层 | 回答 | 手段 |
|------|------|------|
| 身份 Identity | 你是谁 | DID（公钥哈希） |
| 认证 Authentication | 怎么证明 | 每请求 Ed25519 签名 |
| 授权 Authorization | 你能做什么 | **由合约派生**（本节） |

**唯一性**：`did:key` 是 Ed25519 公钥的 multibase 编码，碰撞代价等同破解 Ed25519，**无需注册中心**。这与「自然组网」直接相容——新节点生成密钥即获得全局唯一身份，不依赖任何中心化分配机构。这是公钥方案相对 token 方案的根本优势。

**授权内部再分两层**，粒度与强制点都不同：

| 层 | 粒度 | 强制点 | 现状 |
|------|------|--------|------|
| 能力（粗粒度） | 每请求 | `resolve_federation_identity()` 第 2 步（`src/middleware/federation_identity.rs#L78-L81`） | `organization_links.capabilities` JSON 列，默认 `["a2a_task"]`（`common/src/api/organization_link.rs#L205-L206`）；**无任何更新接口**，恒为默认值 |
| 合约（细粒度） | 每任务 | 入站接单前（`src/handlers/a2a/send_task.rs`） | **无** |

**唯一事实源约束（本方案的核心约束）**：能力集必须由合约派生，**不得另行配置**。两套并行配置必然漂移，届时「能力允许但合约不允许」的语义无法判定。落地方式是把 `capabilities` 列下沉为合约记录的一个字段（见 S3）。

**关于自然发现**（大组网的另一半）：

- 现状是**一跳同步**：directory 同步按连接进行，只能发现直接对端。
- 网状需要**引荐（introduction）**：B 把 A 的 DID + 地址用 B 的私钥签名后交给 C，C 验 B 的签名即可信任这条介绍。这是 web of trust 的传递式发现——**它是签名底座的第二个用途**，不额外增加基础设施。
- 明确不做 DHT / libp2p：规模未到，且与 HTTP/A2A 主栈双栈并存，复杂度翻倍。
- **多设备（同组织多节点）**：组织 DID 作身份，各节点持有自己的密钥，由组织密钥签发**委派证书**。当前单节点，仅要求数据模型不堵死这条路（link 上记的 `peer_did` 是组织身份），不实现。

### 2.3 token 与白名单的归宿

两者命运不同：**白名单吸收进合约，联邦 token 直接删除**。

**白名单：吸收进合约——不存在「删除」这个选项**

能力集是**任何合约的必要组成部分**，不是合约的替代品：即便将来实现完整 SLA 合约，它仍须回答「这条连接开放哪些能力」。因此 `organization_links.capabilities` 是**下沉**为 `federation_contracts.capabilities`（S3），概念保留、存储位置迁移。

> 白名单不是合约的「拓展点」，它就是**合约的粗粒度形态本身**。S3 做的只是把 implicit 的变成 explicit 的。

**联邦 token：要区分两种完全不同的东西**

「token」这个词在本项目里指了两种性质相反的凭据，必须分开处置：

| | 链路共享密钥（现有） | 短期任务令牌（本次新建） |
|---|---|---|
| 生命周期 | **永久**，建联时交换一次，永不轮换 | 分钟~小时级，随任务创建而签发 |
| 作用域 | 整条连接 | **单个任务** |
| 是否共享密钥 | 是（双方持有同一把） | 否（**自签发**，签发方用自己的私钥签） |
| 绑定请求内容 | 否 | 否（但绑定 `task_id` + `aud`） |
| 存储 | `organization_links` 两列 | **无状态**，不落库 |
| 处置 | **删除** | **新建**（S2，用于异步回调） |

**删除的是前者**：非对称加密下联邦同步链路不需要任何共享密钥——出站用本端私钥签名、对端用本端公钥验签。长期有效、可重放、需额外存储与轮换，保留只剩危害。

- `organization_links.access_token` / `peer_token_hash` 两列（当前 `NOT NULL`）随迁移删除，连同生成、交换、校验三处代码。
- `VerifyPairingCodeRequest` / `Response` 去掉 `local_token` / `peer_token` 字段。
- `resolve_federation_identity()` 的凭证哈希分支整体移除，改为「解析 peer DID」（见 §2.4）。

> **注意：删的是「链路凭证 token」，不是「配对码」。** 配对码是授权手段（证明"这次连接被对端管理员许可过"），没有替代品，保留。

> **更准确地说：删除的是「一把不轮换的共享密钥」，不是「token 这种凭据形态」。** token 形态在本方案中反而增加了（任务令牌，§2.4）；组织级**会话**令牌（类似用户 JWT，让组织像用户一样访问业务）是密钥底座之上的合法扩展点，但当前没有对应的业务面（联邦业务 = `tasks/send` + callback，接待用户映射已让业务逻辑用户形状化），按 YAGNI 不建——见 §九扩展点。

**新建的是后者**，但它**不用于同步节点调用**——那里的每请求签名严格更强（见 §2.4）。它的唯一落点是异步回调，属于 S2。

**第三方 A2A 客户端：本次不实现**

`/.well-known/agent.json` 已对外暴露（`src/handlers/a2a/agent_card.rs`，注册于 `src/router.rs#L102-L103`，公开无鉴权），本端是标准 A2A 服务端。标准客户端只认 `Authorization: Bearer`，未来若接入需要一条独立通路。但**现在没有任何第三方集成需求**，且 `AgentCard` 连 A2A 规范的 `authentication` 字段都未声明（`common/src/api/a2a.rs#L15-L35`），第三方客户端发现后本就无从携带凭证。

因此不在本次预留 `peer_kind` 列或保留 token 通路——**没有实现就不需要分支**。待真正接入第三方时，作为独立需求一次性设计（`AgentCard.authentication` 声明 + 凭据存储 + 能力范围），比现在预留一列更干净。

### 2.4 两层凭据模型：身份层与业务层

联邦凭据分两层，与 TLS（握手 → 会话密钥）、OAuth（客户端凭证 → access token）同构。

**第一层 · 身份层**：`did:key` + Ed25519 长期密钥，解决「你是谁」。全局唯一、无需注册中心。用途：建联交叉签名、同步请求签名、地址 gossip 公告签名、审计哈希链签名。

**第二层 · 业务层**：每次通信携带的凭据，解决「这次通信被授权做什么」。按调用形态分两种：

| | 同步节点调用 | 异步任务回调 |
|---|---|---|
| 端点 | `/a2a`、directory 拉取、WS 握手 | `/a2a/callback/{task_id}` |
| 凭据 | 每请求签名（§四） | 短期任务令牌（Bearer） |
| 绑定 | method + path + timestamp + nonce + body 哈希 | `task_id` + `aud` + `exp` |
| 重放窗口 | 零（nonce 去重 + 时间窗） | TTL 内 |
| 服务端状态 | nonce LRU | 无 |

**为什么同步路径不换成短期 token——本方案最容易被误判的一处**

短期 TTL 是相对**永久 token** 的改进，但相对**每请求签名**是降级：

- Bearer 令牌在 TTL 内被任何人截获即可重放；每请求签名带 nonce，重放窗口为零。
- Bearer 令牌不绑定请求内容；每请求签名覆盖 method / path / body 哈希，改一字节即失效。
- Ed25519 签名开销约数十微秒，而联邦任务是分钟级 LLM 链路——为省这点开销引入有状态凭据，收益为零。

> 结论：**同步路径坚持每请求签名，不引入 token。** token 只在签名「用不上」的地方才有价值。

**「把现有 token 加上过期机制」为什么仍然不行——循环依赖**

过期意味着续期，而安全的自动续期只有一条路：对端用密钥**签名**发起轮换请求。也就是说，"有过期机制的共享 token" **依赖签名底座才能安全存在**——它替代不了签名，只能当签名的下游缓存。绕开签名的续期只剩管理员手动重发配对码，那是把安全退化成运维纪律。

再叠加两点固有短板：TTL 内可重放（签名的 nonce 窗口为零）；双端共持同一密钥（任一侧库泄露即双向冒充；非对称下对端无法伪造你）。而签名代码本就要为互联层实现（建联交叉签名、目录同步、WS 握手），业务调用复用它的边际成本 ≈ 0。

**用户为什么需要 JWT 而联邦不需要——摊销的对象不同**

用户 JWT 的存在理由：密码认证是**人类高摩擦操作**（人要输密码、要走安全信道），所以认证一次、缓存成会话凭据供后续请求复用。机器签名没有可摊销的成本：Ed25519 签名数十微秒、无人类参与、无高摩擦信道。**会话令牌是昂贵认证的摊销机制，而机器签名没有昂贵的东西可摊销**——把用户 JWT 模型照搬到联邦，是在为一个不存在的成本建缓存。

**签名哪里用不上：异步回调——而且这是当前的一个真实缺口**

委派是 A→B，回调是 B→A，A 事先不知道回调何时到达。B 用自己的节点私钥签名虽然可行，但签名只证明「是 B 发的」，**不证明「这个任务是 A 派给 B 的」**——节点私钥作用域覆盖 A 的全部任务，过大。

现状比这更糟，两处都缺凭证：

- 入站 `/a2a/callback/{task_id}` 无鉴权中间件，唯一校验是 capability URL：path 的 `task_id` + body 的 remote task id 与 tag 记录一致（`src/handlers/a2a/callback.rs#L39-L51`）。拿到两个 UUID 即可注入结果，且 handler 后续走 `SendToUserCommand`，等价于能往项目里发消息。
- 出站 `src/service/dao/a2a_callback/http.rs#L63-L68` 只带 `Content-Type`，**不带任何凭证**。

**自签发任务令牌正好补这个洞**：A 在委派（`tasks/send`）时用自己私钥签一个短期令牌放进 payload；B 回调时作为 `Authorization: Bearer` 带回。A 端校验：

1. 签名有效（用 **A 自己的公钥**，无需查对端状态）
2. `exp` 未过期
3. `task_id` claim 与 URL 路径参数一致
4. `aud` 等于 A 的 DID

零往返、零服务端状态、天然单任务作用域，且严格优于「给回调加节点签名」。第三方 A2A 接入时沿用同一形态（区别只在改由签发端点颁发），届时才需要端点与可选存储。

**任务令牌的适用边界：任务级异步操作，不是「任务相关的一切」**

判断标准：操作是否**脱离原始请求上下文、异步发生、作用域天然是单任务**。

- ✅ callback（现在）：B 推送结果，A 事先不知何时到达；一次委派可多次回调（增量同步），令牌在 TTL 内多次出示。
- ❌ `tasks/send`（委派发起）：令牌在这一刻才诞生——A 没法用它证明自己；且 B 鉴权 A 走每请求签名，严格更强。委派之后 A↔B 的其他同步交互同理。
- 🔮 未来若新增任务级异步端点（`tasks/get` 轮询、产物拉取等），按同一标准归入令牌侧；节点级同步操作一律走签名。

**TTL 修正：「有效期短一些」不适用于任务令牌**

联邦任务是分钟到小时级的 LLM 链路，最终回调可能远晚于委派。令牌 `exp` 必须 **≥ 任务超时**（对齐任务 deadline 配置 + 余量），否则任务跑到一半回调就 401。它的安全性**不来自短 TTL，而来自单任务作用域**——TTL 内即使泄露，影响面也只是这一个任务的结果注入，且 `aud` 绑定本端 DID、`task_id` 绑定路径，换任务即失效。

**统一点不是凭据格式，而是「解析出 peer DID」**

`resolve_federation_identity()` 第 1 步从「校验凭证」变为「解析出 peer DID」：

- 有 `X-Federation-Signature` → 验签 → `peer_did`
- 有 `Authorization: Bearer <任务令牌>` → 验签 + TTL + scope → `peer_did`
- 都没有 → 401

两种证明方式产出同一结论，因此**下游三段（能力门禁 / 声明一致性 / 接待用户映射）一个字都不用改**——这是「两种凭据不会造成分叉复杂度」的根本原因。

## 三、设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| DID 方案 | **`did:key`** | 邀请制场景下不需要「仅凭域名发现对方」；无域名也可建联（内网/容器/单机），换域名·IP·端口身份不变。零运维依赖（不用托管 `/.well-known/did.json`）。代价：无法从 DID 反查地址——但地址本就走 directory 同步 + 后续 gossip |
| 认证方式 | **每请求签名**（同步） | 零往返、不增加联邦调用延迟。mTLS 需证书签发/轮换/吊销体系，且与「网关保持 dumb」冲突（网关做 mTLS 则应用看不到对端身份）；挑战响应多一次往返 |
| 业务层凭据 | **两层**：身份层 Ed25519 长期密钥 → 业务层按形态分化 | 同步调用用每请求签名（绑定请求、零重放窗口）；异步回调用**自签发短期任务令牌**（§2.4）。token 不是「更安全的签名」而是「签名用不上时的补位」，故**不替换同步路径** |
| 迁移策略 | **一次性切换，无回退** | 项目未上线，不存在需要兼容的存量节点。留回退分支会引入降级攻击面（攻击者可故意不发签名头回退到弱校验），且该分支永远不会被真正清理 |
| 私钥存放 | 公钥入 `organizations` 随目录同步；私钥用 `encrypt_channel_secret` 加密入 DB | 与既有凭据机制一致（`src/pkg/crypto.rs#L98-L105`），可经接口轮换；`/data` 已含 DB，安全等级与配置文件等价 |

**明确不做（YAGNI）**：

- 不引 `ssi` crate（依赖树巨大），自写 Ed25519 最小子集。
- 不做 mTLS / 证书体系；不做 `did:web` 解析（有明确发现需求时再加别名）。
- 不动 JWT：它是用户会话链路的 HS256，与联邦鉴权是两条独立链路，不冲突。
- nonce 去重先做**进程内** LRU（单实例是常态）；多实例需共享存储时再换 Redis。
- 不做版本协商 / 双模回退 / `peer_kind` 分流（见 §2.3）。
- 不做**组织级会话令牌**（当前无业务面，YAGNI；扩展点见 §九）。注意它与被删除的链路共享密钥是两回事——若将来建，必须满足：由**本端**签发（非对端自签发，自签发只是弱化版签名，无价值）、Ed25519 签名（非 HS256）、claims 绑定合约 id 且**每次请求仍校验合约状态**（令牌是断言，合约是事实源，合约 terminated 后存量令牌必须失效）。

## 四、签名规范

**请求头**（命名沿用 `X-Federation-*`，常量加在 `common/src/constants/http_header.rs#L26` 附近）：

| 头 | 内容 |
|----|------|
| `X-Federation-Key-Id` | 发起方组织 DID（`did:key:z6Mk...`） |
| `X-Federation-Timestamp` | Unix 秒级时间戳 |
| `X-Federation-Nonce` | 随机 16 字节 hex |
| `X-Federation-Signature` | Ed25519 签名，base64url 无 padding |

**待签规范串**（`\n` 分隔，顺序固定）：

```
{method 大写}\n{path 含 query}\n{timestamp}\n{nonce}\n{sha256(body) 十六进制小写}
```

无 body 时最后一项取空串的哈希，保证字段数恒定。

**验签流程**（任一环节失败即 401）：

0. **四个头缺一即 401**——不存在"无签名头"的合法请求。
1. 取 `X-Federation-Key-Id` → 与 link 上记录的 `peer_did` 比对（不匹配即 401，防跨连接冒充）。
2. 时间戳窗口 ±300s（超出即 401，依赖两端 NTP 基本同步）。
3. nonce 查进程内 LRU（TTL 略大于窗口）→ 命中即 401（防重放）。
4. 用 `peer_verification_key` 验签规范串。
5. 通过后**复用现有逻辑**：能力门禁 → 声明一致性 → 接待用户映射。

**依赖新增**：`ed25519-dalek`（纯 Rust，无 C 依赖）。

> ⚠️ **crate 归属**：签名/验签实现放**后端**（`src/pkg/crypto` 扩展），**不要放进 `common`**——`common` 会被前端 WASM 依赖，加密码学库会显著增大 WASM 体积。`common` 只放 DID / 公钥的**字符串类型与常量**，不含算法实现。

### 4.1 A2A 端点鉴权矩阵

「A2A 走什么鉴权」不是单一答案——四个端点姿态各不相同：

| 端点 | 用途 | 当前鉴权 | 升级后 |
|------|------|----------|--------|
| `/.well-known/agent.json` | 能力发现 | 公开无鉴权（`src/router.rs#L101-L106`） | 不变（符合 A2A 规范） |
| `/a2a` | JSON-RPC（`tasks/send` 等） | `a2a_auth`：本地 JWT 优先 → 回退联邦 Bearer（`src/middleware/a2a_auth.rs#L32-L72`） | 按头显式分流（见下） |
| `/a2a/subscribe` | SSE 流式委派 | **仅 `jwt_auth`**（`src/router.rs#L121-L129`） | **维持仅 JWT**（已拍板，见缺口 B） |
| `/a2a/callback/{task_id}` | 对端推送结果 | **完全无鉴权**（`src/router.rs#L130-L137`） | 短期任务令牌（Bearer），见缺口 A 与 §2.4 |

**`/a2a` 的双模会随 token 删除而自然简化。** 现在的逻辑是「先试 JWT，失败再试联邦 token」（`src/middleware/a2a_auth.rs#L34-L41`）——这种尝试-回退链同样是降级口子，且两条路径产出的内部身份不同（本地用户 vs 接待用户），下游授权依赖「走了哪条路」是隐式的。删除联邦 token 后，凭证类型不再混淆，分流变成显式的：

- 有 `X-Federation-Signature` → 联邦验签分支；
- 否则 `Authorization: Bearer` / Cookie → 本地 JWT；
- 都不匹配 → 401。

**入站一个 `tasks/send` 请求经过的完整关卡**：

1. 传输层分流（上表）
2. 认证：签名头完整 → `Key-Id` 比对 `peer_did` → ±300s 时间窗 → nonce 去重 → 验签
3. 授权：能力门禁（合约含 `a2a_task`，**每请求**）→ 声明一致性 → 接待用户映射 → 合约条款校验（**每任务**，S3 新增）

> 第 3 步的两段区别：能力门禁回答「这条连接能不能委派」，合约条款回答「这一次委派接不接」。**当前只有前者，没有后者**——即现在只要连接开放了 `a2a_task`，任何委派都会被受理，无范围/预算/验收约束。

**缺口 A：`/a2a/callback/{task_id}` 完全无鉴权（建议与 S2 同批修）**

路由未挂任何鉴权中间件，handler 内唯一的校验是「本地 task 存在 + 任务体里的 remote task id 与 tag 记录的一致」（`src/handlers/a2a/callback.rs#L39-L51`）。这是 capability URL 式的弱防护——**知道两个 UUID 即可向任务注入结果，并能触发消息发送**（该 handler 后续走 `SendToUserCommand`）。出站侧同样裸奔：`src/service/dao/a2a_callback/http.rs#L63-L68` 只带 `Content-Type`。

**修法选择：不用节点签名，用自签发任务令牌**（理由见 §2.4）。节点签名只能证明「是 B 发的」，无法证明「这个任务是 A 派给 B 的」，作用域覆盖 A 的全部任务；自签发令牌由 A 在委派时签发，天然单任务作用域，且验证只用 A 自己的公钥，零状态。

**缺口 B：`/a2a/subscribe` 仅本地 JWT —— 已拍板：联邦不支持 SSE**

决策：**选 ②，`/a2a/subscribe` 维持仅本地 JWT，S2 不做任何改动**。

理由：

1. **功能上不缺**。联邦任务的进度推送走 callback——回调 handler 本就按 `a2a_synced_msg_count` tag 做增量消息同步（`src/handlers/a2a/callback.rs#L75-L106`），一次委派可多次回调，覆盖流式场景。SSE 订阅对联邦是冗余通道。
2. **S2 改动面收窄**。出站签名从三处减为两处半（WS 握手保留），且不用设计「SSE 连接上如何签名」这个别扭问题——SSE 是长连接，签名是按请求的，两者形态不匹配。
3. **未来反悔成本低**。真需要联邦 SSE 时再补验签分支即可，届时能力门禁 / 合约判定直接复用，无沉没成本。

推论：联邦对端通过 `AgentCard` 发现本端时，不应误以为可以使用 `tasks/sendSubscribe`。S1 落地时顺手在 `AgentCard` 的能力声明中保持现状（不宣传 streaming）即可，无需专门字段。

## 五、数据模型变更

```sql
-- 组织身份密钥（S1）
-- did / verification_key 随目录同步给对端；signing_key 为 encrypt_channel_secret 加密后的私钥
ALTER TABLE organizations ADD COLUMN did TEXT NULL;
ALTER TABLE organizations ADD COLUMN verification_key TEXT NULL;
ALTER TABLE organizations ADD COLUMN signing_key TEXT NULL;

-- 对端身份（S2）：建联时交换，入站验签依据
ALTER TABLE organization_links ADD COLUMN peer_did TEXT NULL;
ALTER TABLE organization_links ADD COLUMN peer_verification_key TEXT NULL;

-- 联邦链路不再使用共享密钥（§2.3）
-- DROP COLUMN 需 SQLite 3.35+；若目标版本更低则改建表迁移
ALTER TABLE organization_links DROP COLUMN access_token;
ALTER TABLE organization_links DROP COLUMN peer_token_hash;
```

`PeerOrgDirectoryEntry` 增补 `did` / `verification_key` 两字段，为**必填**（联邦对端必有密钥对）；`VerifyPairingCodeRequest` / `Response` 去掉 token 字段。

密钥对生成时机：组织创建时或首次需要联邦调用时惰性生成；提供轮换接口（生成新 key → 双 key 并存过渡期 → 退役旧 key）。

## 六、实施步骤

三步，S1 可独立上线，S2 为原子切换，S3 紧跟其后。

### S1 密钥底座

1. 迁移：组织三列（did / verification_key / signing_key）+ 连接两列（peer_did / peer_verification_key）。
2. `src/pkg/crypto` 扩展：Ed25519 密钥对生成、`did:key` 编解码、签名、验签、规范串构造。
3. 组织创建/启动自检：确保 Local 组织有密钥对，缺失则生成并存库（私钥加密）。
4. 目录同步 payload 带上 `did` / `verification_key`。
5. 单测：`did:key` 编解码往返、签名验签、篡改任一字段验签失败。

> S1 不改任何鉴权行为，风险最低，可单独合并。

### S2 请求签名 + 建联交换公钥（原子切换）

验签的前提是建联已交换公钥，两者必须同批上线，故合并为一步：

1. 建联改造：`VerifyPairingCodeRequest` 带本端 `did` + 公钥，响应回带对端公钥，双方**交叉签名**（签名内容 = 对方 DID + 配对码哈希）后落 `peer_did` / `peer_verification_key`；同时删除 token 的生成与交换。
2. 入站：`resolve_federation_identity()` 凭证哈希分支**替换为**「解析 peer DID」（§2.4），签名头缺一即 401；`a2a_auth` 的「先试 JWT 再试 token」改为按头显式分流（§4.1）。
3. **异步回调凭据**（§4.1 缺口 A，按 §2.4 自签发任务令牌实现，而非节点签名）：
   - 委派侧：`tasks/send` 出站时用本端私钥签发任务令牌，随 payload 下发；令牌 claim 含 `iss`（本端 DID）、`aud`（对端 DID）、`task_id`、`exp`。**`exp` 对齐任务超时配置 + 余量**（任务分钟到小时级，TTL 短了最终回调 401；安全来自单任务作用域而非短 TTL，见 §2.4）。
   - 回调侧：`/a2a/callback/{task_id}` 校验 Bearer 令牌——签名 + `exp` + `task_id` 与路径一致 + `aud` 为本端 DID，任一不符即 401。
   - 出站 `A2aCallbackDao::push_task` 携带该令牌（`Authorization: Bearer`），替换当前「只带 Content-Type」。
   - 令牌**不落库**，验证用本端公钥，零状态。
4. 出站三处统一注入签名头：A2A 委派、目录拉取、WS 握手。抽一个公共 `sign_federation_request()`，避免三处各写一遍。
5. nonce LRU（进程内，TTL 600s，容量按并发上限设）。
6. 迁移删除 `access_token` / `peer_token_hash` 两列。

**配套两项（关闭 §2.1 的首达者窗口）**：

1. **DID 指纹留档与展示**：link 列表与详情展示 `peer_did` 的短指纹（8 位分组形式），管理员可带外核对。这是 SSH 的 TOFU 模型——不阻断，但让冒充可被发现。
2. **签发时可选钉住预期 DID**：`IssuePairingCodeRequest` 增加可选 `expected_peer_did`；填了就在 `verify_pairing_code()` 中比对，不匹配即拒绝。**这是唯一能真正关闭首达者窗口的手段**，且与 DID 方案无关。

> 第 2 项是否需要取决于配对码的传递信道是否可信。互信组织走 IM 传递时 TOFU 已够；非互信组织（未来合同机制场景）建议强制钉住。

这一步做完，合同机制的「双签」就有了现成底座——要约与承诺的签名与建联签名是同一套代码。

### S3 合约授权（把白名单具象化）

目标不是增加功能，而是**先立合约的形状，不立合约的语义**。真上非互信合约时只加字段与状态机，强制点不动。

迁移新建 `federation_contracts`：

| 列 | 说明 |
|----|------|
| `id` / `local_org_id` / `peer_org_id` | 主键与双方组织 |
| `kind` | `basic`；未来加 `task_sla` |
| `state` | `active` / `terminated`；未来补 `offered` / `accepted` |
| `capabilities` | JSON 数组——**现有 `organization_links.capabilities` 下沉到此** |
| `terms_hash` | 条款哈希；`basic` 时为固定常量（占位，保证列存在） |
| `local_signature` / `peer_signature` | `basic` 时留空，未来双签 |
| `created_at` / `updated_at` | 时间戳 |

实施项：

1. 建联成功即自动写入一条 `kind=basic, state=active`，`capabilities` 取默认 `["a2a_task"]`。
2. 提供管理员编辑接口（补上当前**完全缺失**的能力可管理性）。
3. 强制点改造：`resolve_federation_identity()` 第 2 步从读 `link.capabilities` 改为读「该连接下 `state=active` 的合约」的 `capabilities`；无合约记录时按无能力处理（fail-closed）。

## 七、回滚与运维

| 场景 | 处理 |
|------|------|
| 旧版本兼容 | **不存在**。项目未上线，无存量节点需要支持 |
| 升级后异常 | 回退到切换前的提交即可；但 S2 之后 `access_token` 不再生成，**已建联的连接必须重新配对** |
| 密钥轮换 | 双 key 并存过渡；旧 key 退役前对端应已同步新公钥 |
| 时间偏移 | 两端 NTP 偏差超过 ±300s 会导致全部请求 401；健康检查应覆盖时钟偏移告警 |

## 八、验收清单

- [ ] A2A 委派、目录拉取、WS 握手三处均验签通过
- [ ] **缺少任一签名头 → 401**（无回退路径）
- [ ] 重放同一请求（同 nonce）第二次返回 401
- [ ] 篡改 body / path / timestamp 后验签失败
- [ ] 超窗（>300s）请求返回 401
- [ ] 换 endpoint / 换域名后，因 DID 不变而无需重新配对
- [ ] 建联后对端换成另一把密钥发请求 → 验签失败（§2.1：冒充可检测）
- [ ] 签发时钉住 `expected_peer_did` 后，出示其他 DID 的对端被拒绝
- [ ] 无 active 合约的连接 → 拒绝；合约 terminated → 拒绝（§2.2 fail-closed）
- [ ] 管理员编辑合约 capabilities 后，下一次请求即按新能力集判定
- [ ] `access_token` / `peer_token_hash` 列与相关代码已彻底移除
- [ ] `/a2a` 既非合法 JWT 又无签名头 → 401（无尝试-回退链）
- [ ] `/a2a/callback` 无 Bearer 任务令牌 → 401（§4.1 缺口 A）
- [ ] 用任务 T 的令牌回调任务 U → 401（`task_id` claim 与路径不符）
- [ ] 令牌过期后回调 → 401；令牌被第三方截获后重放仍能进入（已知且接受：TTL 内重放是本方案的边界）
- [ ] 委派 payload 中的令牌由 A 自签发，A 端验证无需查库（确认零状态）
- [ ] `make lint` 与 `make ci` 全绿；WASM 体积无明显增长（确认签名代码未进 `common`）

## 九、后续依赖

S1+S2 落地后，以下能力才具备实施条件：

- 地址列表 gossip（公告带签名，防伪造）
- **引荐式发现**（B 签名介绍 A 给 C，见 §2.2）——传递式组网，不需要 DHT
- 审计日志哈希链（记录带组织签名，防抵赖）
- 非互信组织合同机制：`kind=task_sla` 合约 = S3 同一张表加字段与状态机，双签复用 S2 的签名代码
- **组织级会话令牌**（让组织像用户一样访问业务 API）：密钥底座与统一解析链（`resolve_federation_identity` → peer DID → 合约 → 接待用户）就绪后，它只是**多一种凭据形态**——由本端经签名认证的握手签发、claims 携带合约上下文（合约 id / 能力子集 / 预算）、Ed25519 签名、短 TTL；验证仍走同一条解析链，下游零改动。触发条件：出现真实的「组织作为业务主体」访问面（第三方 A2A 接入、跨组织业务 API），在那之前建它是第二个做签名已在做的事的机制。**实施逃生舱**：若某条高频路径（WS 帧、轮询类）实测签名开销或复杂度成为负担，可将**该路径单独**降级为「签名握手签发的短时会话令牌」——解析链相同、下游零改动，按路径按需降级，不全局铺开。
