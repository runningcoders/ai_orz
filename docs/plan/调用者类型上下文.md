## 一、目标（为什么做）

`RequestContext` 中无显式调用方身份字段，代码各处散落着 `ctx.agent_id().is_some()` 隐式推断逻辑，存在以下问题：

| 问题维度 | 解决方式 |
|---------|---------|
| (a) 调用方身份推断散落在各处，语义不统一 | 新增 `CallerType` 枚举（User=0/Agent=1/System=2），RequestContext 显式持有 `caller_type` 字段 |
| (b) System 触发链路（Cron/A2A/AOP）无统一标识 | 新增 `RequestContext::new_system()` 工厂方法，统一所有 System 入口 |
| (c) 入口设置 caller_type 与 enrich_ctx 覆盖冲突 | 约定 caller_type 仅由入口层显式设置，enrich_ctx 链路透传不覆盖 |
| (d) stats operator_type 推断与 handler 消息发送推断不一致 | 统一改为读 `ctx.caller_type`，补齐 System 场景分支（原隐式推断只分 Agent/User 两类） |

**收敛后效果**：所有入口链路（HTTP/Consumer/Producer/Cron/A2A 回调）显式设置 caller_type，隐式推断点统一替换为读 `ctx.caller_type`，User/Agent/System 三分支语义对齐 stats operator_type。

## 二、架构思路（怎么做的）

入口层统一设置，下游链路统一读取：

```
CallerType 枚举（common 层定义）
  User=0    默认值（HTTP 入口都是用户）
  Agent=1   Agent 主动触发（工具调用、消息发送）
  System=2  系统触发（Cron、A2A 回调、AOP 调度、后台轮询）
  数值与 MessageRole 对齐，但语义层次不同：
  - MessageRole 是消息字段（from_role/to_role）
  - CallerType 是 ctx 字段（当前操作链路触发方）
  │
  ▼
入口层（仅入口设置 caller_type，enrich_ctx 不覆盖）
  ├─ HTTP 中间件 jwt_auth.rs：注入 X-Caller-Type=user header
  │   from_headers 解析：默认 User，优先从 X-Caller-Type header 读
  ├─ Consumer message.rs：
  │   rebuild_context 根据 message.from_role() 设置
  │   handle_tool_call_request 强制 Agent（ToolCallRequest 一定由 Agent 发起）
  │   on_event/ack/nack 用 RequestContext::new_system()
  ├─ Producer/Cron/AOP/SSE/HTTP fetch 等 18 处 System 触发点：
  │   全部替换 RequestContext::new(None, None) → new_system()
  └─ A2A callback handler：task_ctx 强制 System
  │
  ▼
下游消费层（统一替换隐式推断）
  ├─ Handler 层（消息发送类 4 个文件）：
  │   send_message_to_agent / send_message / send_task_assignment_message / mark_done
  │   原 if-else 三段式（Agent→User→System fallback）统一改为 match ctx.caller_type()
  └─ Stats operator_type 推断（project 域 2 个文件 11 处）：
      project/service.rs（5 处）+ project/task.rs（6 处）
      原 ctx.agent_id().is_some() 判断 → ctx.caller_type().as_str()
      operator_id 也按 caller_type 三分支选择来源
```

**关键边界（行为红线，回归必保）**：
1. **enrich_ctx 不覆盖 caller_type**：caller_type 只由入口层设置，所有 EnrichContext 实现保持不变，透传入口值
2. **默认值 User**：from_headers 无 X-Caller-Type header 时默认 User（与 HTTP 中间件行为一致）
3. **数值与 MessageRole 对齐**：User=0、Agent=1、System=2，便于从 message.from_role 映射转换
4. **new_system() 工厂方法**：统一替换所有 `RequestContext::new(None, None)`，System 触发点不再依赖默认值语义
5. **stats operator_type 补齐 System 分支**：原隐式推断（Agent→User 二分类）改为 ctx.caller_type().as_str()（三分类），operator_id 仅 Agent 和 User 有值，System 为 None

## 四、入口设置点 + 隐式推断替换速查表（新增链路时套用）

新增入口链路或替换隐式推断时，按以下表格操作：

### 4.1 入口 caller_type 设置点（新增入口走此表）

| 入口场景 | caller_type 设置方式 | 参考入口路径 |
|---------|-------------------|------------|
| HTTP 用户请求（经 JWT 中间件） | JWT 注入 X-Caller-Type=user header，from_headers 默认 User | [jwt_auth.rs](../../src/middleware/jwt_auth.rs) |
| Consumer 处理用户消息 | from_role 映射：MessageRole::User → CallerType::User | [consumer/message.rs::rebuild_context](../../src/consumer/message.rs) |
| Consumer 处理 Agent 消息 | from_role 映射：MessageRole::Agent → CallerType::Agent，工具调用请求强制 Agent | [consumer/message.rs::rebuild_context + handle_tool_call_request](../../src/consumer/message.rs) |
| Cron / AOP 调度 / 后台轮询 / A2A 轮询 | `RequestContext::new_system()` 工厂方法 | [producer/cron_trigger.rs](../../src/producer/cron_trigger.rs)、[pkg/aop/core/registry.rs](../../src/pkg/aop/core/registry.rs) |
| A2A 回调（公开端点，无 JWT） | to_builder().caller_type(CallerType::System).build() 覆盖默认 User | [handlers/a2a/callback.rs](../../src/handlers/a2a/callback.rs) |
| 飞书 WS 消息渠道入站 | RequestContext::builder().caller_type(CallerType::User).try_user_id(msg.from_id).build() | [producer/message_channel.rs](../../src/producer/message_channel.rs) |

> 代码入口：[request_context.rs::RequestContext::new_system()](../../src/pkg/request_context.rs) 和 [request_context.rs::RequestContextBuilder::caller_type()](../../src/pkg/request_context.rs)

### 4.2 隐式推断替换模式（读 caller_type 时走此表）

| 原隐式推断代码模式 | 替换方式 | 参考替换入口 |
|----------------|--------|------------|
| `if let Some(aid) = ctx.agent_id() { ... } else if !ctx.uid().is_empty() { ... } else { system }` 三段式 | `match ctx.caller_type() { Agent => ..., User => ..., System => ... }` 三分支 | [handlers/finance/message/send_message_to_agent.rs](../../src/handlers/finance/message/send_message_to_agent.rs) |
| `ctx.agent_id().is_some() { "Agent" } else { "User" }` 二分类 stats operator_type | `ctx.caller_type().as_str().to_string()`（返回 "User"/"Agent"/"System"） | [domain/project/service.rs](../../src/service/domain/project/service.rs) |
| `operator_id: ctx.agent_id().cloned().or_else(|| ctx.user_id().cloned())` | `operator_id: match ctx.caller_type() { Agent => ctx.agent_id().cloned(), User => ctx.user_id().cloned(), System => None }` | [domain/project/task.rs](../../src/service/domain/project/task.rs) |

## 七、后续扩展路径（新增入口链路 4 步模板）

> **核心不变量**：CallerType 枚举语义 / RequestContext 结构 / enrich_ctx 不覆盖约定 不动。

1. **新增入口链路 caller_type 设置**：参考 §四 速查表 4.1，判断场景选择设置方式；不确定时优先用 `RequestContext::builder().caller_type(CallerType::Xxx)` 显式声明；System 场景一律用 `RequestContext::new_system()`
2. **新增隐式推断点替换**：参考 §四 速查表 4.2，搜索所有 `ctx.agent_id().is_some()` / `ctx.agent_id().map(...).or_else(|| ctx.user_id())` 模式，一律改为 `match ctx.caller_type()` 三分支
3. **新增 stats 统计 operator_type**：直接使用 `ctx.caller_type().as_str().to_string()` 和三分支 operator_id 选择模式，参考 [domain/project/task.rs 末尾](../../src/service/domain/project/task.rs) 现有 6 处实现
4. **新增枚举场景扩展**：如未来需要第四种调用方身份，先在 [common/src/enums/caller_type.rs](../../common/src/enums/caller_type.rs) 加变体（保留数值对齐 MessageRole 的约定，如可复用），同步更新 as_str() / From<i32> match 分支，再回到 §四 更新入口速查表

完成。
