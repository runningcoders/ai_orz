# 跨组织业务调用方案（Phase 2 主体）

> 状态：**实施中**（设计稿 v2，2026-09-04；鉴权模型已拍板②，F1 接受）
> 前置：Phase 1 组网（S1–S7）✅、S8 目录推拉 ✅、S9 分层修正 ✅、R2/R3 JWT 地基 ✅

---

## 一、目标与非目标

**目标**：建联的组织之间可以发起跨组织业务调用——第一闭环是**跨组织 Agent 协作**（A 组织的 Agent/用户把任务委派给 B 组织的 Agent 执行），并在此基础上留出计量（哪个组织调了多少）的口子。

**非目标（YAGNI）**：
- 用户级联邦 SSO（A 的用户拿自己的 token 直接浏览 B 的界面）——重协议，先不做
- 计费结算——只留计量字段，结算逻辑延后
- 非对称签名 JWT + 公钥发现——凭证模型复杂度高，本期不做（见 §3 方案对比）

## 二、现状盘点（已有资产）

| 资产 | 现状 | 对 Phase 2 的意义 |
|------|------|------------------|

## 三、鉴权模型（核心决策点）

### 方案对比

| 方案 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| ① token 交换 | A 凭 link access_token 调 B 的 token 端点，换 B 签发的短期 JWT（含 iss/aud/exp） | 短期凭证、标准联邦模式、R2 iss/aud 立即收紧 | 新端点 + token 生命周期管理 + 刷新逻辑；一期凭证量级下收益有限 |
| ② 凭证直传 + 身份声明（**推荐**） | A 直接用 link access_token 调 B（Bearer，连接级鉴权 = Phase 1 管道），另带 `X-Federation-Caller` 头声明发起者（org/user/agent，明文 JSON + 由 A 签名可后补） | 零新协议端点；B 侧校验 = `authenticate_link_call` + 解析声明；R3 管道直接落地 | 声明头无密码学保护（对端节点可信前提下发明文；R1 同源风险）；长期凭证（与 Phase 1 R1 同源接受） |
| ③ 非对称签名 + 公钥发现 | 每节点发布公钥（well-known），JWT RS256/EdDSA | 密码学上最正统 | 密钥生成/轮换/分发/信任锚全套复杂度，明显过度设计 |

**推荐 ②**，理由：
1. 与 Phase 1 的信任模型一致——建联本身（配对码 + 契约凭证）已经建立了"这对组织互相可信"，调用级再叠加 token 交换是重复建设
2. R2 的 iss/aud 地基不浪费：Phase 2 的联邦 JWT 场景（用户级 SSO）真出现时地基直接用；本期 `X-Federation-Caller` 声明是它的明文前身，字段语义对齐（caller_org/caller_user/agent）
3. ①③ 可以后补：鉴权中间件抽象成 trait，直传/交换/签名都是实现

### B 侧鉴权流程（方案 ②）

```
A 侧出站                                B 侧入站
─────────────                          ─────────────
1. 查 link（Active）拿 access_token     1. extract_bearer_credential
2. 组装 X-Federation-Caller:              2. authenticate_link_call(hash 匹配 Active)
   {"caller_org":"A-id",                  3. 解析声明头（缺省 = 连接级匿名调用）
     "caller_user":"u-1",                 4. 能力白名单检查（§4）
     "caller_agent":"ag-9"}               5. RequestContext 注入：
3. POST /a2a (agents/sendTask)               organization_id = B（目标，数据作用域）
                                             caller_organization_id = A（iss 语义）
                                             caller_type = FederationUser/Agent
```

## 四、能力发现与白名单

**问题**：A 怎么知道 B 有哪些 Agent 可以调？B 怎么控制"开放给这条连接什么"？

**设计：能力端点 + 连接级白名单（默认全开 Agent 子集）**

1. **能力端点**（机器侧，契约凭证鉴权，复用 §3 流程）：
   `GET /api/v1/organization/links/capabilities` → 返回本节点开放给**调用方这条连接**的能力清单：
   ```json
   { "agents": [ {"id":"ag-9","name":"翻译官","description":"..."} ],
     "capabilities": ["a2a_task"] }
   ```
2. **白名单粒度**：连接级（organization_links 加 `capabilities` JSON 列，默认 `["a2a_task"]`）；Agent 级白名单延后到真需要时（YAGNI）
3. **发现时机**：建联后首次同步拉一次；A 侧 Agent 引用缓存 + cron 对账顺带刷新（S8 管道直接复用）

**A2A 入站鉴权（P1+P2 已实现，双模鉴权）**：v1 设计稿误判 `/a2a` 无鉴权——实际一直挂 `jwt_auth_middleware`。因此原 P1（可选 Agent 级 token）作废，P1/P2 合并为 `/a2a` 双模鉴权：本地 JWT 优先（既有语义不变），失败回退联邦凭证（`authenticate_link_call` 哈希匹配 Active 连接）+ 可选 `X-Federation-Caller` 声明（明文 JSON；缺失 = 连接级匿名，合成身份 `federation:{peer_org_id}`；非法/声明组织与连接归属不符 → 401 fail-closed）。注入：`organization_id` = 本端（目标），`caller_organization_id` = 对端（iss 语义，R3 计量），不注入本地角色。`/a2a/subscribe` 暂维持 JWT-only（YAGNI，需要时换同一中间件）。

## 五、发起侧：跨组织 Agent 寻址

- @ 提及协议扩展：`[@名](agent:ag-9@org-B12)`（`agent:<id>@<org_id>`，org_id 在本端 links 里有 Active 连接即合法）；不合法降级普通链接（既有原则不变）
- 委派执行：A 侧 runtime 命中 `agent@org` 形态 → 组装 `A2aRuntimeConfig { endpoint: link.endpoint, agent_name: 对端 Agent 名, auth_token: link.access_token }` → 走既有 A2A 出站
- 结果回传：沿用 A2A callback/polling（callback URL 带一次性 task 关联，不暴露凭证）

## 六、计量（R3 落地）

- B 侧鉴权中间件把 `caller_organization_id` 写入 RequestContext（地基已就绪）→ A2A 调用日志天然带 org 维度
- 正式计量表（调用量/耗时/Token 用量按 org 聚合）延后到有结算需求时；本期只保证**日志可聚合**
