# 跨组织业务调用方案（Phase 2 主体）

> 状态：**P1–P4 全部完成**（设计稿 v3，2026-09-04；鉴权模型已拍板②，F1 接受）
> 前置：Phase 1 组网（S1–S7）✅、S8 目录推拉 ✅、S9 分层修正 ✅、R2/R3 JWT 地基 ✅

---

## 一、目标与非目标

**目标**：建联的组织之间可以发起跨组织业务调用——第一闭环是**跨组织 Agent 协作**（A 组织的 Agent/用户把任务委派给 B 组织的 Agent 执行），并在此基础上留出计量（哪个组织调了多少）的口子。

**非目标（YAGNI）**：
- 用户级联邦 SSO（A 的用户拿自己的 token 直接浏览 B 的界面）——重协议，先不做
- 计费结算——只留计量字段，结算逻辑延后
- 非对称签名 JWT + 公钥发现——凭证模型复杂度高，本期不做（见 §3 方案对比）

## 三、鉴权模型（核心决策点）

### 方案对比

| 方案 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| ① token 交换 | A 凭 link access_token 调 B 的 token 端点，换 B 签发的短期 JWT（含 iss/aud/exp） | 短期凭证、标准联邦模式、R2 iss/aud 立即收紧 | 新端点 + token 生命周期管理 + 刷新逻辑；一期凭证量级下收益有限 |
| ② 凭证直传 + 身份声明（**推荐**） | A 直接用 link access_token 调 B（Bearer，连接级鉴权 = Phase 1 管道），另带 `X-Federation-Caller` 头声明发起者（org/user/agent，明文 JSON + 由 A 签名可后补） | 零新协议端点；B 侧校验 = `authenticate_link_call` + 解析声明；R3 管道直接落地 | 声明头无密码学保护（对端节点可信前提下发明文；R1 同源风险）；长期凭证（与 Phase 1 R1 同源接受） |
| ③ 非对称签名 + 公钥发现 | 每节点发布公钥（well-known），JWT RS256/EdDSA | 密码学上最正统 | 密钥生成/轮换/分发/信任锚全套复杂度，明显过度设计 |

**推荐 ②**，理由：
1. 与 Phase 1 的信任模型一致——建联本身（配对码 + 契约凭证）已经建立了"这对组织互相可信"，调用级再叠加 token 交换是重复建设
2. R2 的 iss/aud 地基不浪费：Phase 2 的联邦 JWT 场景（用户级 SSO）真出现时地基直接用；本期 `X-Federation-Caller` 声明是它的明文前身，字段语义对齐（caller_org/caller_user/agent）
3. ①③ 可以后补：鉴权中间件抽象成 trait，直传/交换/签名都是实现

### B 侧鉴权流程（方案 ②）

```
A 侧出站                                B 侧入站
─────────────                          ─────────────
1. 查 link（Active）拿 access_token     1. extract_bearer_credential
2. 组装 X-Federation-Caller:              2. authenticate_link_call(hash 匹配 Active)
   {"caller_org":"A-id",                  3. 解析声明头（缺省 = 连接级匿名调用）
     "caller_user":"u-1",                 4. 能力白名单检查（§4）
     "caller_agent":"ag-9"}               5. RequestContext 注入：
3. POST /a2a (agents/sendTask)               organization_id = B（目标，数据作用域）
                                             caller_organization_id = A（iss 语义）
                                             caller_type = FederationUser/Agent
```

## 四、能力发现与白名单

**问题**：A 怎么知道 B 有哪些 Agent 可以调？B 怎么控制"开放给这条连接什么"？

**设计：能力端点 + 连接级白名单（默认全开 Agent 子集）**

1. **能力端点**（机器侧，契约凭证鉴权，复用 §3 流程）：
   `GET /api/v1/organization/links/capabilities` → 返回本节点开放给**调用方这条连接**的能力清单：
   ```json
   { "agents": [ {"id":"ag-9","name":"翻译官","description":"..."} ],
     "capabilities": ["a2a_task"] }
   ```
2. **白名单粒度**：连接级（organization_links 加 `capabilities` JSON 列，默认 `["a2a_task"]`）；Agent 级白名单延后到真需要时（YAGNI）
3. **发现时机**：建联后首次同步拉一次；A 侧 Agent 引用缓存 + cron 对账顺带刷新（S8 管道直接复用）

**A2A 入站鉴权（P1+P2 已实现，双模鉴权）**：v1 设计稿误判 `/a2a` 无鉴权——实际一直挂 `jwt_auth_middleware`。因此原 P1（可选 Agent 级 token）作废，P1/P2 合并为 `/a2a` 双模鉴权：本地 JWT 优先（既有语义不变），失败回退联邦凭证（`authenticate_link_call` 哈希匹配 Active 连接）+ 可选 `X-Federation-Caller` 声明（明文 JSON；缺失 = 连接级匿名，合成身份 `federation:{peer_org_id}`；非法/声明组织与连接归属不符 → 401 fail-closed）。注入：`organization_id` = 本端（目标），`caller_organization_id` = 对端（iss 语义，R3 计量），不注入本地角色。`/a2a/subscribe` 暂维持 JWT-only（YAGNI，需要时换同一中间件）。

## 五、发起侧：跨组织 Agent 寻址（P4 已实现）

- @ 提及协议扩展（`common/src/mention.rs`）：`MentionRef.org: Option<String>` + `parse_mention_dest` 支持 `agent:<id>@<org_id>`（仅 Agent；空段/多 @/非 Agent 类型带 @ 一律降级普通链接，既有原则不变）；`format_mention_ref` 对应输出。合法性（org 是否有 Active 连接）由上层校验，协议层只做格式解析
- 直连路由（`src/consumer/message.rs::try_federated_delegation`）：仅用户消息触发（Agent 回复中的 @ 对端提及不外呼，防调用环）；可路由 → 联邦委派并跳过本端 Agent 唤醒，对端回复以对端 Agent id 为 from 落库给原用户；不可路由 → 降级普通提及（仅上下文注入）。组织上下文优先取消息自带 organization_id
- 委派编排（`organization domain::delegate_agent_task`）：路由决策（Active 连接 + `a2a_task` 能力，返回 `Ok(None)` = 降级 / `Ok(Some(reply))` = 成功 / `Err` = 已建联但调用失败）+ `X-Federation-Caller` 声明（caller_org + caller_user）；传输（`organization dal::send_federated_agent_task` → `a2a.rs::execute_federated_agent_call`）：send → 轮询 tasks/get 直到终态（120s 预算，1s 间隔；send 响应已终态带文本则直接返回）
- B 侧收口（`consumer/message.rs`）：tasks/send 创建的一次性 project（tags 含 `a2a`、无 task 关联）在 Agent 回复后自动 complete —— 否则对端轮询 tasks/get 永远 working（修复既有缺口，外部 A2A 客户端同步受益）
- 结果回传：同步路径由 tasks/send + 轮询闭环；长任务异步（callback / a2a_task_id tag + polling producer）留待需要时接入

## 五.5、前端接入与能力发现管道（P5 已实现）

## 六、受理层身份模型：接待员模式（P6 已实施 2026-09-04）

> 拍板：跨组织请求由**被访组织**决定谁来接待与执行，请求侧不可指定服务者；接待落地后的一切行为与「一个本地用户在用我们组织」完全同构。

### 身份三层

| 层 | 身份 | 来源 | 可见性 |
|---|---|---|---|
| 对外 | link 凭证 + 合成访客 `federation:{peer_org_id}` | 建联（Phase 1）+ 双模鉴权（P1+P2） | 仅到受理层为止 |
| 受理 | **接待 user**（对接员身份）+ **接待 Agent**（`ROLE_A2A_GATEWAY`） | 接待 user：当前 = 组织内最高权限管理员（创建者，凭据最全），user 表无新字段；接待 Agent：`ROLE_A2A_GATEWAY` 角色解析 | B 侧全链路可见 |
| 执行 | 内部普通 Agent | 接待 Agent 受理后按既有协作模型委派 | 仅 B 侧内部，对端不可见不可寻址 |

- **接待 user**：被访组织为联邦访客落地一个真实 user 身份（「对接员」）。`tasks/send` 入站时，合成身份 `federation:{peer_org_id}` 映射到该 user——project 的 user_id/owner、消息 from 全部落在他名下。**此后一切（权限、SSE、消息流、记忆）与本地用户路径零差异**，不需要任何特殊分支
- **接待 Agent**（已有 `resolve_agent(by_role)` 解析）：收到需求后按复杂度决策——简单问答直接回复（回复即完成）；复杂事项建 task / @ 协作 Agent 拉起内部委派，执行者以**自己的身份**工作，日志/记忆/权限全走本地体系
- 对端可寻址的永远只有接待 Agent（capabilities 白名单只暴露它即可）；内部 Agent 身份不外泄
- 递归防护不变：内部委派产生的 Agent 回复中的 @ 对端提及不外呼（联邦路由仅用户消息触发）

### A2A task ↔ project 生命周期映射（长任务）

- `tasks/send` 即建 project（已有）→ working（InProgress）；**project 不实时关闭**——关闭与否完全由任务是否做完决定
- 状态映射：project InProgress（含子 task 进行中）→ working；project 完成（task 终态 / 接待侧手动完结）→ completed
- 双通道回传：同步 = `tasks/get` 轮询（现状）；异步 = `notification_url` callback（既有渠道管道）或对端轮询
- **完成判定（已实施 2026-09-04，`consumer/message.rs`）**：Agent 回复后按「做完才关」判定——project 无进行中 task（一次性问答）→ 回复即完成（保留同步轮询路径）；有 Pending/PendingReview/InProgress task（接待员已内部委派）→ 保持 working，等任务完成/接待侧确认后再收口。对端轮询持续看到 working 是正确语义。用例 `test_a2a_project_with_inflight_task_stays_working`
- **接待 user 映射（已实施 2026-09-04）**：三层各一方法——`UserDao::find_reception_user`（SQL：org 内 role IN (SuperAdmin,Admin) 按 role+created_at 取最早，user 表不加字段，未来换专用接待用户只改此实现）→ `UserDal::find_reception_user` → 组织域 `UserManage::reception_user`（返回完整 UserPo，上游自取所需字段；无管理员 fail-closed NotFound）。落点在 `a2a_auth` 中间件第 7 步（合成身份的诞生点）：联邦路径 `X-User-Id` = 接待用户 ID，project root_user/owner、消息 from 全部落他名下；`X-Federation-Caller` 声明仅做一致性校验（401 fail-closed），留给审计/计量（见 §八）
- **项目来源审计（已实施 2026-09-05）**：联邦入口创建 project 时 tags 追加 `federation:<peer_org_id>`（保留基础 `a2a` tag；本地 JWT 路径无 caller 不受影响）。`projects_fts` 建表已含 tags 列（FTS5 表级 MATCH 覆盖），tag 天然可全文检索——回答「这个项目来自哪个组织」。精确索引（`project_tags` 规范化表）仅在项目量大 + 高频按 tag 过滤时再上（JSON 数组列无法走 B-tree/表达式索引）

### 与既有实现的关系

`resolve_agent(by_role)` / project tags=`a2a` / `X-Federation-Caller` 全部保留；**接待 user 映射与完成判定均已实施**，P6 收官。

## 七、网络拓扑：内外网可达性（P7，设计已拍板 2026-09-04）

> 拍板：节点地址区分内网/公网；出站前探测，**内网优先、公网回退**。目标 = 把「可访问」与「不可访问」区分开。不做穿透/中继（YAGNI）。

- **多地址模型**：节点/组织目录条目携带地址列表 `[{url, scope: public|private}]`——建联时自报 + 目录同步累积。一台有公网 IP 的设备并入系统后，它的内外网地址都会被对端记录
- **可达性解析**：出站调用（capabilities / 委派 / 目录同步）前解析 endpoint——优先探测内网地址，连通即用；不通回退公网；两者皆不通 = 该对端暂不可达（按既有「单对端失败跳过」惯例降级，不阻塞其它对端）
- **探测缓存**：探测结果带 TTL，避免每次调用都付探测延迟；缓存过期或调用失败时重探
- **协议不变**：凭证、声明头、能力发现均与地址无关；`link.endpoint` 语义从「单地址」升级为「当前首选可达地址」（由解析器维护），上层零感知
- 纯内网且本端无任何可达地址的节点：暂不可达，等「方向性组网」（内网侧主动出站拉取的反向通道）有真实需求时再立项
