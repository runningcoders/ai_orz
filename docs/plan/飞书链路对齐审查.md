## 一、结论先行

### 1.0 先说最重的一条：飞书长连接**从来没有建立过**

`src/service/dao/lark/ws.rs:25` 硬编码的取连接地址端点是：

```rust
const PATH_WS_ENDPOINT: &str = "/open-apis/callback/ws/endpoints";
```

**真机探测（2026-09-20，本机直连官方域名、假凭据，只判路径是否存在）：**

| 探测 | 结果 |
|------|------|
| `POST https://open.feishu.cn/open-apis/callback/ws/endpoints`（我方路径，Bearer） | **HTTP 404 `page not found`** |
| `POST https://open.feishu.cn/callback/ws/endpoint`（官方路径，`{AppID,AppSecret}`） | **HTTP 200** + `{"code":1000040343,"msg":"internal error","data":{"URL":""}}` |

也就是说：**我方路径不存在（404），整条 WS 链路在「取连接地址」这一步就失败了**，`fetch_ws_endpoint` 抛 `ThirdPartyError`，supervisor 以 1s→60s 退避无限重试 —— 现象是「日志里一直在重连、永远收不到事件」。全仓只有这一处飞书 WS 实现（已核对）。

协议层还错的更多（格式、鉴权、心跳、重连口径、事件应答），逐条见 **§二**。

### 1.1 三类洞（微信那轮堵过、飞书一个都没堵）

1. **静默失效族**——解析失败 / 有意跳过 / 空字段当成功，全部只留 `debug` 甚至不留痕；
2. **「连上了但收不到」不可见且不自愈**——WS 死亡不改 `state`、不带原因、不触发告警；
3. **前端仍是「手动按钮」反模式**——device flow 要用户手点「已完成授权」，与微信改造前的「我已扫码完成」同构。

严重度分布：

| 级别 | 含义 | 条数 |
|------|------|------|
| **P0-0** | **协议层根本错**：连接无法建立 / 帧格式不符 / 缺事件应答 | 8（F0-1…F0-8） |
| **P0** | 直接表现为「连上了却收不到消息」，且线上不可诊断 | 3（F1–F3） |
| **P1** | 能通但不会自愈 / 排查黑洞 / 体验反模式 | 5（F4–F8） |
| **P2** | 契约与展示一致性（字段被忽略、降级被当正常） | 7（F9–F15） |
| **P3** | 能力面（群聊 / @mention），登记不做 | 1（F16） |

> 教训（已回收进 `third-party-protocol-alignment-audit` 技能）：**协议形态（端点 / 传输编码）必须先证伪，再谈字段级对齐**。上一版本报告在没验证端点与帧形态的前提下逐条讨论 close 帧与心跳细节，方向是对的但顺序错了 —— 那些都是连接建立**之后**才谈得上的事。

## 二、协议层对账结论（依据：官方实现 + 真机探测）

### 2.1 取证三源

| 源 | 获取方式 | 用途 |
|----|---------|------|
| **官方 Node SDK `@larksuiteoapi/node-sdk@1.74.0`** | `npm pack`（已解到 `/tmp/lark_spec/package`） | 主 spec：WSClient 状态机、pb 帧结构、错误码、心跳与重连参数 |
| **官方域名真机探测** | `curl` 两个端点（假凭据） | 端点存在性**硬证据** |
| 第三方 Rust 实现 `zeptoclaw` | docs.rs / crates.io | 旁证（同一套结论：protobuf 帧、`method=0/1`、WS base 不带 `/open-apis`） |

> **hermes 不支持飞书**：已拉取 `NousResearch/hermes-agent`（sparse checkout `gateway/`），`gateway/platforms/` 下只有 `weixin.py` / `qqbot/` / `slack` 系 / `whatsapp` 等，**无 lark/feishu 适配**（全仓 `lark|feishu` 命中均在无关语境）。此路不通。
> **`lark-cli` 不含长连接**：官方 CLI（`github.com/larksuite/cli`，Go）确实开源，但 `cmd/event/` 下是**订阅底账检查 + stdin 消费**（`consume.go`），长连接事件接收仍由各语言 SDK 承担。故我方 WS 必须照官方 SDK 协议实现，CLI 只适合做身份授权（device flow）那一半。

### 2.2 我方 vs 官方：协议层对照

| 维度 | 官方（Node SDK 1.74.0 + 实测） | 我方现状 | 判定 |
|------|------------------------------|---------|------|
| **取连接地址端点** | `POST {domain}/callback/ws/endpoint`（**无 `/open-apis`**） | `POST https://open.feishu.cn/open-apis/callback/ws/endpoints` | ❌ **404**（实测） |
| **鉴权方式** | body `{AppID, AppSecret}`（或 clientAssertion）；**不用 Bearer** | `Authorization: Bearer {tenant_access_token}` + `{}` body | ❌ 前提就错（WS 模式不需要 tenant token） |
| **帧编码** | **protobuf 二进制**（pbbp2.Frame），`Frame.encode().finish()` | **JSON 文本** `{"type":"event"\|"pong"\|"close"}` | ❌ 传输层完全不同 |
| **帧类型区分** | `method`：`0`=control(ping/pong)、`1`=data(event/card)；`headers[].type` 细化 | 顶层 JSON `type` 字符串 | ❌ |
| **心跳帧** | protobuf control 帧：`headers=[{key:"type",value:"ping"}]`、`service=serviceId`、`method=0`、`SeqID=0`、`LogID=0` | JSON 文本 `{"type":"ping"}`，**硬编码 30s** | ❌ |
| **心跳间隔来源** | **服务端下发**：`ClientConfig.PingInterval`（秒，默认兜底 120s），且 **pong payload 会再更新一次** | 硬编码 `HEARTBEAT_INTERVAL = 30s` | ❌ 未消费服务端参数 |
| **重连参数** | **服务端下发** `ReconnectInterval`（默认 120s）/ `ReconnectCount`（-1=无限）/ `ReconnectNonce`（默认 30s，**仅首次**抖动 `nonce*random()`） | 指数退避 1s→60s，±20% 抖动 | ❌ 口径不同（我方更激进） |
| **事件应答（ACK）** | **必须回帧**：同 headers + `biz_rt` + payload `{"code":200}`；处理异常 `{"code":500}` | **无 ACK 概念**，`on_frame` 恒 `Continue` | ❌ 缺失 |
| **分片重组** | `message_id`+`sum`+`seq` 重组，到齐才解析 | 无 | ❌ 缺失（长事件会丢） |
| **握手字段** | headers 定义了 `handshake-status` / `handshake-msg` / `handshake-autherrcode` | 无 | ⚠️ 未处理 |
| **致命错误处置** | `code=internal_error(1000040343)` → **可重试**；其余非 0（含 `exceed_conn_limit=1000040350`）→ **不可重试 → onError + 状态 `failed`，停止重连** | 无区分，全部退避重连 | ❌ |
| **close 帧 code** | 官方 **不读** close code，`on('close')` 无条件重连 | 同样不读 | ✅ 一致（见 2.4 对 F1 的修正） |
| **连接数上限** | 官方错误码 `exceed_conn_limit = 1000040350`（**在「取连接地址」响应里**，不是 close 帧） | 未识别该码 | ❌ 新增项 |
| **appId 形态** | `start()` 前校验 `/^cli_[0-9a-fA-F]{16}$/` | 无校验 | ⚠️ 可选 |

### 2.4 对上一版报告的修正（原判断 → 修正后）

| 上一版判断 | 官方事实 | 修正 |
|-----------|---------|------|
| F1「**必须**读 close 帧 code 来区分被踢」 | 官方**不读** close code，冲突判据是取配置阶段的 `exceed_conn_limit=1000040350` | F1 降级为「可观测性改进」；**冲突识别的正确落点是取连接配置的响应码** |
| F1「冲突会导致两实例**互相踢 + 无限重连**」 | `exceed_conn_limit` 属**不可重试** → 官方会**停止重连**并置 `failed` | 我方应识别该码 → **停重连 + 健康标 `conflict`**（不是拉长退避） |
| F2「二手来源：`wsConfig { PingInterval: 30, PingTimeout: 5 }`」 | 默认 `pingInterval=120s`；`pingTimeout` **默认为 0（关闭）**；且两者实际由**服务端下发** | 二手来源数值**错误**；我方 30s 硬编码既不来自服务端也不是官方默认 |
| F2「应该依赖协议级 ping/pong 判死」 | 官方默认**不做**无帧判死（`pingTimeout=0`）；启用时语义是「发 ping 后等一个帧」，且不重新武装 | 修法应为：**照实现服务端下发的 pingInterval 发 ping**，无帧保活**按官方语义作为可选开关**（默认关），而不是自创 30s+判死 |
| 退避「1s→60s 指数」 | 官方为**固定间隔**（服务端下发，默认 120s）+ 首次 nonce 抖动 | 指数退避应改为照服务端参数；1s 起步的快速重连对飞书属激进行为 |

## 四、发现清单

### P0-0 —— 协议层（连接建立不了 / 说不上话）

#### F0-1｜WS 取连接地址端点不存在（404）

- **位置**：`src/service/dao/lark/ws.rs:25`（`PATH_WS_ENDPOINT`）、`:104`（拼接）、`:98-131`（`fetch_ws_endpoint`）
- **事实**：我方 `/open-apis/callback/ws/endpoints` **实测 404**；官方 `/callback/ws/endpoint` 实测 200。
- **影响**：**连接从未建立**。所有飞书入站事件、所有依赖入站的功能（Agent 接待、消息落库）在飞书上全部无效。
- **修法**：端点改为官方路径（去掉 `/open-apis`，单数 `endpoint`）。

#### F0-2｜鉴权方式错：WS 模式不需要 tenant_access_token

- **位置**：`src/service/dao/lark/ws.rs:98-114`
- **事实**：官方用 `{AppID, AppSecret}` 作为 body 换连接配置；我方取 tenant token 后塞 `Authorization: Bearer`。
- **影响**：即使端点改对，鉴权仍会被拒（且 `WsTokenSource` 这层抽象本身就是错前提）。
- **修法**：改传 AppID/AppSecret；若保留 `WsTokenSource` 抽象，其语义应改为「提供 app 凭据」而非「提供 token」。
- **顺带**：官方响应里的 `ClientConfig` 必须被消费（F0-4）。

#### F0-3｜帧编码错：飞书是 protobuf 二进制帧，我方按 JSON 文本处理

- **位置**：`src/service/dao/lark/ws.rs:54-82`（`WsIncoming` / `WsPing`）、`:152-211`（`on_frame(text: String)` / `heartbeat_frame() -> Some(String)`）
- **事实**：官方全部帧是 `pbbp2.Frame` protobuf；`method=0` control / `method=1` data；事件 payload 才是 JSON。我方 `pkg::ws` 的读循环只接 `Message::Text`（`src/pkg/ws/mod.rs:398`），**连二进制分支都没有**。
- **影响**：即使端点与鉴权修好，服务端发来的二进制帧会被 `pkg::ws` 直接忽略（`Message::Binary` 不匹配任何分支）→ 仍然「连上但一条事件收不到」。
- **修法**：需要引入 prost 定义（上方 §2.3 的 `pb Frame` 字段）+ 在 `pkg::ws` 增加二进制帧通路（adapter trait 需要能收 `Bytes`，不只是 `String`）。
- **说明**：这是一次**接口层改造**（`WsClientAdapter` 的 `on_frame(String)` → 能带 payload 编码标记），不是改几行。

#### F0-4｜心跳参数未按服务端下发（且间隔错）

- **事实**：`ClientConfig.PingInterval/ReconnectInterval/ReconnectNonce/ReconnectCount`（秒）由服务端下发；**pong payload 还会再次更新**这套参数。官方默认兜底 120s。
- **我方**：`HEARTBEAT_INTERVAL = 30s` 硬编码（`src/pkg/ws/mod.rs:36`），且 pong 里若带参数会被丢弃（`WsIncoming::Pong` 无字段）。
- **修法**：取配置时保存 `ClientConfig`，pong 时按其更新；心跳间隔从硬编码改为运行时参数。

#### F0-5｜重连口径错：应为「固定间隔 + 首次抖动」，非指数退避

- **位置**：`src/pkg/ws/mod.rs:32-36`、`:209-214`（`next_backoff`）、`:266`
- **事实**：官方 `reconnectInterval` 固定（默认 120s），仅**首次**加 `nonce*random()`（≤30s）抖动；`reconnectCount<0` 无限。
- **修法**：换成服务端参数驱动的固定间隔；首次抖动保留。

#### F0-6｜事件缺 ACK（服务端会认为投递失败）

- **事实**：官方收到 data 帧后**必须回一帧**（同 headers + `biz_rt` + payload `{"code":200}`；处理异常 `{"code":500}`）。
- **我方**：无 ACK 概念，`on_frame` 恒 `Continue`。
- **影响**：飞书可能按「未确认」处理（重推 / 标记投递失败）。
- **修法**：`on_frame` 返回语义扩展为「是否 ACK + 结果码」，由 pkg 负责回帧。

#### F0-7｜长事件分片未重组

- **事实**：官方按 `message_id` + `sum` + `seq` 重组，到齐才解析；非法元数据要**报错留痕**（官方 issue #201 的教训）。
- **我方**：无。
- **修法**：加一个带 TTL 的分片缓存；元数据非法 → `log_warn` + 丢弃该 `message_id`。

#### F0-8｜致命错误码未识别（连接冲突会无限重试）

- **事实**：`exceed_conn_limit=1000040350` 从**取连接地址**响应返回；官方归入「不可重试」→ `onError` + `state='failed'` + **停止重连**。`internal_error=1000040343` 才可重试。
- **我方**：`fetch_ws_endpoint` 对 `code != 0` 一律返回错误 → supervisor 一律退避重连。
- **修法**：错误分类（可重试 / 致命）；致命 → 停止重连 + 健康快照标 `conflict` + `warn` 日志给出码与 msg。

### P0 —— 「连上了却收不到」且不可诊断（连接修好后仍存在）

#### F1｜WS 服务端 close 帧的 code/reason 被丢弃

- **现象**：`state` 显示 `connected`，日志只有 `lark ws received close from server` + 重连循环。
- **根因**（`src/pkg/ws/mod.rs:395-416`）：

  ```rust
  frame = read.next() => {
      match frame {
          Some(Ok(msg)) => {
              if let Message::Text(text) = msg          // ← 只匹配 Text
                  && adapter.on_frame(text).await == FrameAction::Reconnect
              { break; }
          }
          ...
          None => { log_info!("{} ws stream closed by server", name); break; }
      }
  }
  ```

  服务端下发的 `Message::Close(Some(CloseFrame { code, reason }))` 不匹配，被静默忽略；随后流返回 `None`，只记一句 `stream closed by server`。
- **修正后的定位**（见 §2.4）：官方自身也不读 close code，所以这条**不再主张「必须按 close code 做冲突判定」**；它的价值是**可观测性**——被服务端主动关闭是必须能看见原因的事件。冲突判定的正确落点是 F0-8。
- **修法**：读循环补 `Message::Close` / `Ping` / `Pong` 分支，`warn` 记录 code/reason；同步处理 F0-3 的二进制分支。

#### F2｜心跳只发不收：无帧超时、停发协议级 Ping

- **现象**：网络抖动 / NAT / 代理静默丢包后，连接对象还在、`state` 还是 `connected`，但一条事件都收不到，只能重启进程。
- **根因**：
  1. `src/pkg/ws/mod.rs:356-379`：心跳任务按 `heartbeat_frame()` 做**二选一**——飞书 adapter 实现了它（`:206-211`），于是**协议级 Ping 完全不发**；
  2. 读循环不记录任何帧时间，`pong` 被 `Continue` 吞掉，**没有「多久没收到任何帧」的判据**；
  3. `WsConnState`（`:122-130`）只有 `phase`/`reconnect_count`/`last_connected_at`，**没有 `last_frame_at`**。
- **修正后的定位**（见 §2.4）：官方**默认关闭**无帧判死（`pingTimeout=0`），启用时语义是「发 ping 后等一个入站帧」，且**不重新武装**。所以我方不该自创「30s 心跳 + 判死」，而应先照 F0-4 对齐心跳，再把「无帧超时」按官方语义做成**可选**（默认关），并把 `last_frame_at` 作为**观测字段**常开。
- **修法**：`last_frame_at` 进 `WsConnState`（常开，纯观测）；无帧超时按官方语义可选启用。

#### F3｜入站「有意跳过」四级过滤里三级无 `info` 证据

- **现象**：给机器人发消息没回应；日志里既没有收帧记录也没有跳过记录。
- **根因**（逐级）：

  | 过滤点 | 代码位置 | 现有日志 |
  |--------|---------|---------|
  | 非 P2P / 非文本（**含群消息**） | `src/service/dal/lark/impl.rs:195-205` | `log_debug!` |
  | 文本内容解析失败 | `src/service/dal/lark/impl.rs:208-219` + `src/models/events/lark.rs:157` 的 `.ok()?` | `log_debug!` |
  | 内容为空串 | `src/service/dal/lark/impl.rs:220-222` | **无任何日志** |
  | 消费侧拿到 `None` | `src/consumer/lark_inbound.rs:73-80` | **无任何日志** |
  | 未绑定渠道 | `src/service/dal/lark/impl.rs:233-240` | `log_info!` ✅（唯一有证据的） |

- **影响**：与微信那轮「解析失败被 `.ok()` 吞掉 → 连收帧日志都不打」同一族。`header.event_id` 在出问题时**不会出现在任何一行日志里**。
- **修法**：按微信口径统一——**「有意跳过」必须是 `info` 级单行证据**（带 `event_id` / `chat_type` / `message_type` / 原因枚举，形如 `lark inbound adapted to nothing: reason=group_message event_id=...`）；`parse_text` 失败要区分「非文本」与「文本但 JSON 不合法」；空内容也留痕。
- **附带物证**：`src/service/dao/lark/error.rs:66-95` 定义了 `LarkWsError`（含 `EventParse`）与 `from_serde`（:103），**全仓零引用**（因 `pub` 不触发 `dead_code`）。「事件解析失败」被设计了却没有调用点，正是这一族静默的物证。

### P1 —— 能通但不会自愈 / 排查黑洞 / 体验反模式

#### F4｜出站空 `message_id` 被当成功，写出脏键 `"lark:"`

- **根因链**：
  1. `src/service/dao/lark/http.rs:120-124`：`SendMessageData.message_id` 带 `#[serde(default)]`；
  2. `:144` `Ok(data.message_id)`——字段缺失时返回**空串而非报错**；
  3. `:300` `Ok(Some(message_id))`——**恒为 `Some`**；
  4. `src/service/dal/message_channel.rs:470-471` `format!("lark:{}", lark_message_id)` → `"lark:"`；
  5. 该列只有普通索引（`migrations/20260909000004_add_external_key_to_messages.sql:15,17`，**非唯一**）→ 多条出站消息共享同一键。
- **影响**：飞书响应若改字段名或返回异常体，**消息其实发出去了但链路显示一切正常、且平台 ID 静默丢失**（`external_key` 语义污染）。将来加唯一约束会立刻冲突。
- **对照**：微信侧 `send_text` 用 **`Result<Option<String>>`**（`None` = 无平台 ID，语义显式）。
- **修法**：`push` 里空串归一为 `None`，或 `send_text_message` 直接报错。

#### F5｜device flow 仍是「我已扫码完成」两步式 + 300s 单请求阻塞

- **根因**：
  1. `frontend/src/pages/finance/identity.rs:294-318`：`handle_auth_complete` 由**用户点按钮**触发；
  2. `:591-606` Modal 里是「打开授权链接」+「**已完成授权**」两个按钮；
  3. `src/pkg/lark_integration.rs:33` `AUTH_COMMAND_TIMEOUT = 300s`、`:283` 调用——`--device-code` 是**阻塞轮询**，前端这一个请求最长挂 300s；
  4. `frontend/src/api/mod.rs:29-31` `Client::new()` 无超时 → 网关 idle timeout 会先切断，用户看到网络错误而非授权结果。
- **影响**：用户不点按钮后端永远不知道；300s 后报 `lark-cli timed out`，toast 说「完成授权失败」而非「授权未完成」——**把「还没做」说成「失败」**。
- **对照**：**就是微信改造前的「我已扫码完成」按钮**（当时明确删掉换自动轮询）。
- **补充事实**：`lark-cli`（官方 Go CLI）的 `auth login` / `auth status` 就是 device flow 工具链，**它本身不提供长连接**，所以「授权用 CLI、收事件自建 WS」的分工是对的，只是两端都要按官方口径实现。
- **修法**：`auth/start` 后**平铺 spawn** 自动发起 `complete`（后台任务），前端同时以 3s 间隔轮询轻量 `auth/status` 收敛 UI，用户零点击；或把 `complete` 改成会话式（仿 `bind` session）由前端轮询。
- **待确认**：并发调用 `lark-cli`（`--device-code` + `auth status`）是否安全，需实测；不行则退化为「自动发起 complete + 界面显示等待中」并保留取消。

#### F6｜健康指标缺「收帧判据」，飞书页只能看「在不在册」

- **根因**：
  1. `common/src/api/system.rs:52-60` `LarkWsAppMetrics` 只有 `app_id`/`state`/`reconnect_count`；
  2. 对照 `:78-90+` `WechatPollChannelMetrics` 有 `state`/`rounds`/`last_poll_at_ms`/失败计数；
  3. `frontend/src/pages/system/health.rs:435` 飞书 Gauge 告警条件只有 `a.state == "reconnecting"`；对照微信有 `wechat_channel_stale`（`last_poll_at_ms` 超 90s 视为疑似卡死）。
- **影响**：F0-1 的 404 死循环、F1/F2 的两种死亡，在健康页上**显示为完全健康或仅仅「重连中」**。这正是微信那轮写在红线里的话——**「句柄在册 ≠ 在跑」**。
- **修法**：`WsConnState` 加 `last_frame_at`（F2）后，`LarkWsAppMetrics` 同步补 `last_frame_at_ms`（+ 可选 `frames_received` + `terminal_reason`，承载 F0-8 的致命码），健康页给出与微信同构的 stale 判定。

#### F7｜绑定轮询循环「无条件 spawn」且缺代次守卫

- **根因**（`frontend/src/pages/finance/identity.rs:199-263`）：

  ```rust
  let handle_bind_start = move |_| {
      spawn(async move { ...lark_bind_start... });   // 任务 A：仅成功时 bind_polling.set(true)
      let running = bind_poll_running.read().clone();
      spawn(async move { loop { ... } });            // 任务 B：无条件启动
  };
  ```

- **影响**：重复点击会叠加轮询循环（同一 `session_id` 被两条循环同时轮询 → `Done` 分支重复触发、Modal 重复弹）。当前靠「`bind_polling` 为 false 时任务 B 下一轮自行退出」兜住，属侥幸。
- **对照**：微信侧用 **`poll_gen` 代次守卫** + `AtomicBool` 卸载守卫；飞书只有后半截。

#### F8｜绑定会话注册竞态：5s 启动窗口内「查不到、取消不掉、进程泄漏」

- **根因**（`src/pkg/lark_integration.rs:526-536`）：先跑「最多 5s 等验证 URL」的循环，**之后**才 `registry.write().await.insert(session_id, session)`。窗口内：
  - `bind/status` → 注册表里没有 → 返回 `NotFound`；
  - `bind/cancel`（`:592-604`）→ `remove` 返回 `None` → `Ok(false)`，**不杀进程**；而 `child` 被局部变量持有，5s 后照样注册进表 —— 用户点了「取消」，进程仍在跑。
- **修法**：**先 `insert` 再等 URL**（5s 等待挪到 insert 之后，URL 由前端轮询补取，这条路径本来已实现）。
