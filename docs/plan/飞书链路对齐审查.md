## 一、结论先行

**飞书链路的骨架是对的**（WS supervisor 退避重连、token 双检锁、凭证引用解析、AOP 异步消费、入站反查挂链都在），但在微信那轮我们花了大力气堵的三类洞，飞书侧**一个都没堵**：

1. **静默失效族**——解析失败 / 有意跳过 / 空字段当成功，全部只留 `debug` 甚至不留痕；
2. **「连上了但收不到」不可见且不自愈**——飞书 WS 有两种死法（服务端 close 踢人、半开连接黑洞），两种都不改 `state`、不带原因、不触发重连；
3. **前端仍是「手动按钮」反模式**——device flow 要用户手点「已完成授权」，与微信改造前的「我已扫码完成」同构。

严重度分布：

| 级别 | 含义 | 条数 |
|------|------|------|
| **P0** | 直接表现为「连上了却收不到消息」，且线上不可诊断 | 3 |
| **P1** | 能通但不会自愈 / 排查黑洞 / 体验反模式 | 5 |
| **P2** | 契约与展示一致性（字段被忽略、降级被当正常） | 7 |
| **P3** | 能力面（群聊 / @mention），登记不做 | 1 |

一句话概括三条 P0：

1. **`Message::Close` 帧的 code/reason 被丢弃**——飞书因「同 App ID 连接数超限」踢人时，我们只看到 `received close from server` + 无限重连循环，**分不清「正常轮换」与「被踢」**；
2. **心跳只发不收、无帧超时**——`heartbeat_frame()` 返回 `Some` 后 pkg **停发协议级 Ping**，收到的 `pong` 也不记时间、不判超时 → 半开连接（TCP 黑洞）下读循环永久挂死，`state` 仍是 `connected`；
3. **入站「有意跳过」零信息**——群消息、非文本、内容解析失败、空内容**四级过滤里三级只有 `debug`、一级完全无日志**，默认 `info` 级别下「群里 @ 机器人一句」在日志里查无此事。

> 这三条与微信那轮的症状同构：**链路看着全绿，消息一条不进**。区别是微信那轮丢在解析层（publish 之前），飞书这两条丢在连接层与过滤层。

## 二、审查方法（清单来源）

按微信方案的四个维度逐项回扫，不是重新发明：

| 维度 | 微信那轮的具体教训 | 飞书侧对应检查点 | 结果 |
|------|-------------------|-----------------|------|
| **A. 静默失效族** | 「解析层 `.ok()` / `log_debug!` 组合 = 排查黑洞」；「解析失败必须留痕」 | 所有 `log_debug` 跳过点、`.ok()?` 降级点、`#[serde(default)]` 空值出口 | ❌ 见 F1–F3 |
| **B. 连接/会话自愈** | `-14` 暂停 + 凭证指纹变化清暂停两端闭合 | WS 死亡分类（close/半开/被踢）、心跳超时、暂停恢复 | ❌ 见 F1/F2 |
| **C. 状态机与轮询穷尽性** | 扫码只认 4 态 → **不是报错而是卡住**；前端必须「平铺 spawn + 代次守卫」 | 绑定/授权状态判定穷尽性、轮询循环启动条件与去重 | ⚠️ 见 F4–F5、F11 |
| **D. 可观测性五层** | DAO 快照 → trait → DAL → Domain → handler 逐层有判活字段；「句柄在册 ≠ 在跑」 | 健康指标字段是否足以回答「活没活」 | ❌ 见 F2/F6 |
| **E. 契约字段一致性** | D9 补 `created_at`/`updated_at`；响应字段必须真被消费 | DTO 字段是否恒 None、是否被前端忽略、降级是否可区分 | ❌ 见 F7–F10 |
| **F. 协议字段对齐** | 以官方实现为 spec（文本字段名 / 枚举类型 / 取码方法） | 飞书官方 SDK / 文档口径核对 | ⚠️ 见 §4 说明（本机无 `lark-cli` 源码，未做逐字段核对） |

> **关于 F 维度的坦白**：微信那轮能逐字段对齐，是因为腾讯官方插件源码可下载（`@tencent-weixin/openclaw-weixin`，已解到 `/tmp/ilink_spec`）作为 SSOT。飞书这轮**本机没有 `lark-cli` 源码**（`which lark-cli` 为空，`~/.lark-cli` 只有空 `cache/`），官方 Node SDK 的 `wsConfig` 等口径只来自二手来源，**质量不足以下结论**。因此本报告**不声称任何飞书协议字段有误**，§4 只登记「需要对账但缺 spec」的项。

## 三、发现清单

### P0 —— 「连上了却收不到」且不可诊断

#### F1｜WS 服务端 close 帧的 code/reason 被丢弃

- **现象**：`state` 显示 `connected`，日志只有 `lark ws received close from server` + `lark ws will reconnect in 1.0s/2.0s/...` 循环，永远连不稳也永远不报错。
- **根因**（`src/pkg/ws/mod.rs:395-416`）：

  ```rust
  frame = read.next() => {
      match frame {
          Some(Ok(msg)) => {
              if let Message::Text(text) = msg          // ← 只匹配 Text
                  && adapter.on_frame(text).await == FrameAction::Reconnect
              { break; }
          }
          ...
          None => { log_info!("{} ws stream closed by server", name); break; }
      }
  }
  ```

  服务端下发的 `Message::Close(Some(CloseFrame { code, reason }))` **不匹配 `Message::Text`**，被静默忽略；随后流返回 `None`，只记一句 `stream closed by server`。**关闭码与原因彻底丢失**。
- **影响**：飞书长连接存在**「同一 App ID 只允许一条活跃连接」**的约束（多实例部署、或 `lark-cli` 自己也在跑时会互相顶掉）——**该约束尚未取到官方原文，见 §4**，但无论是否成立，**被服务端主动关闭**都是一个必须能看见原因的事件。而 `FrameAction::Reconnect` 是无差别的，supervisor 会以 1s→60s 退避**无限重连**：若是连接冲突，两个实例会互相踢 → 双方都永久收不到消息，日志上只有「close + 重连」循环，看不出任何异常原因。
- **修复方向**（最小）：
  1. `pkg/ws` 读循环补 `Message::Close(frame)` 分支，把 `code`/`reason` 透给 adapter（新增 `FrameAction::Closed { code, reason }` 或 `on_close` 回调），并 `log_warn!` 记录；
  2. 飞书 adapter 对已知致命码（如连接冲突类）区分处置：**拉长退避 / 记 error / 在健康快照上标 `conflict`**，而不是当作普通断线无限快重连；
  3. 顺手对齐：`Message::Ping` / `Message::Pong` 也显式处理（见 F2）。
- **对照**：微信侧 `-14` 会话失效 → `SessionGuard` 暂停 1h + 健康指标 `state = paused`，**把「致命的、重试无用的错误」识别出来并停止空转**。飞书缺这一层。

#### F2｜心跳只发不收：无 pong 超时、无帧超时、停发协议级 Ping

- **现象**：网络抖动 / NAT / 代理静默丢包后，连接对象还在、`state` 还是 `connected`，但一条事件都收不到，只能重启进程。
- **根因**：
  1. `src/pkg/ws/mod.rs:356-379`：心跳任务按 `heartbeat_frame()` 做**二选一**——

     ```rust
     let res = match &heartbeat_frame {
         Some(text) => w.send(Message::Text(text.clone())).await,  // 飞书走这条
         None => w.send(Message::Ping(Vec::new())).await,          // 协议级 Ping 不发了
     };
     ```

    飞书 adapter 实现了 `heartbeat_frame()`（`src/service/dao/lark/ws.rs:206-211`，应用层 `{"type":"ping"}`），于是**协议级 Ping 控制帧完全不发**；
  2. 读循环（`src/pkg/ws/mod.rs:386-416`）**不记录任何帧的时间**，`pong` 只被 `WsIncoming::Pong => FrameAction::Continue` 吞掉，**没有「多久没收到任何帧就判死」的判据**；
  3. `WsConnState`（`src/pkg/ws/mod.rs:122-130`）只有 `phase`/`reconnect_count`/`last_connected_at`，**没有 `last_frame_at`**。
- **影响**：半开连接（服务端已死、TCP 未复位）下心跳发送在内核缓冲区「成功」→ 不触发 `log_warn`，读循环永远等不到帧也不退出 → **永久挂死**。
- **修复方向**：给 `WsConnState` 加 `last_frame_at`（每次 `on_frame` 前刷新），心跳任务或读循环里判定「超过 N 秒无任何帧 → 主动断开走重连」；同时决定心跳走哪条路（见 §5 决策 D2）。
- **外部依据（需以官方为准）**：飞书官方 Node SDK 的 `Lark.WSClient` 支持 `wsConfig: { PingInterval: 30, PingTimeout: 5 }`，即**依赖协议级 ping/pong 判死**；社区多处反馈「仅发应用层 ping 不校验 pong」是静默掉线的常见成因。这些来源均为二手，**本报告不据此改协议行为**，只据此指出「当前两套心跳机制都不完整」。

#### F3｜入站「有意跳过」四级过滤里三级无 `info` 证据

- **现象**：微信里给机器人发消息没回应；日志里既没有收帧记录也没有跳过记录。
- **根因**（逐级）：

  | 过滤点 | 代码位置 | 现有日志 |
  |--------|---------|---------|
  | 非 P2P / 非文本（**含群消息**） | `src/service/dal/lark/impl.rs:195-205` | `log_debug!` |
  | 文本内容解析失败 | `src/service/dal/lark/impl.rs:208-219` + `src/models/events/lark.rs:157` 的 `.ok()?` | `log_debug!` |
  | 内容为空串 | `src/service/dal/lark/impl.rs:220-222` | **无任何日志** |
  | 消费侧拿到 `None` | `src/consumer/lark_inbound.rs:73-80` | **无任何日志** |
  | 未绑定渠道 | `src/service/dal/lark/impl.rs:233-240` | `log_info!` ✅（唯一有证据的） |

- **影响**：与微信那轮「解析失败被 `.ok()` 吞掉 → `message_count=0`，连收帧日志都不打」是**同一族**。飞书这里更进一步——`header.event_id` 在出问题时**根本不会出现在任何一行日志里**（`log_debug` 不输出），所以「机器人没反应」既无法确认「事件到了没」，也无法确认「到了但被有意跳过」。群里 @ 机器人是最常见的用户预期，而它属于第一级静默过滤。
- **修复方向**：按微信口径统一——**「有意跳过」必须是 `info` 级单行证据**（带 `event_id` / `chat_type` / `message_type` / 原因枚举，形如 `lark inbound adapted to nothing: reason=group_message event_id=...`）；`parse_text` 失败要区分「非文本」与「文本但 JSON 不合法」两种原因；空内容也要留痕。
- **附带物证**：`src/service/dao/lark/error.rs:66-95` 定义了 `LarkWsError`（含 `EventParse` 变体）与 `from_serde`（:103），**全仓零引用**（因 `pub` 不触发 `dead_code` 警告）。「事件解析失败」这个错误类型被设计出来却没有一个调用点，正是这一族静默的物证。

### P1 —— 能通但不会自愈 / 排查黑洞 / 体验反模式

#### F4｜出站空 `message_id` 被当成功，写出脏键 `"lark:"`

- **根因链**：
  1. `src/service/dao/lark/http.rs:120-124`：`SendMessageData.message_id` 带 `#[serde(default)]`；
  2. `:144` `Ok(data.message_id)`——字段缺失时返回**空串而非报错**；
  3. `:300` `Ok(Some(message_id))`——**恒为 `Some`**；
  4. `src/service/dal/message_channel.rs:470-471` `format!("lark:{}", lark_message_id)` → `"lark:"`；
  5. 该列只有普通索引（`migrations/20260909000004_add_external_key_to_messages.sql:15,17`，**非唯一**）→ 多条出站消息共享同一键。
- **影响**：飞书响应若改字段名或返回异常体，**消息其实发出去了但链路显示一切正常、且平台 ID 静默丢失**（`external_key` 语义污染）。将来若给该列加唯一约束会立刻冲突。
- **对照**：微信侧 `send_text` 用的是 **`Result<Option<String>>`**（`None` = 无平台 ID，语义显式），飞书没有对齐这个语义。
- **修复方向**（一行级）：`push` 里空串归一为 `None`（`Ok(if message_id.is_empty() { None } else { Some(message_id) })`），或 `send_text_message` 直接报错。

#### F5｜device flow 仍是「我已扫码完成」两步式 + 300s 单请求阻塞

- **根因**：
  1. `frontend/src/pages/finance/identity.rs:294-318`：`handle_auth_complete` 由**用户点按钮**触发，`handle_auth_start`（:279-292）拿到 `device_code` 就返回；
  2. `:591-606` Modal 里是「打开授权链接」+「**已完成授权**」两个按钮；
  3. `src/pkg/lark_integration.rs:33` `AUTH_COMMAND_TIMEOUT = 300s`、`:283` 调用——后端 `--device-code` 是**阻塞轮询**，前端这一个请求最长挂 300s；
  4. `frontend/src/api/mod.rs:29-31` `Client::new()` 无超时设置 → 反向代理 / 网关的 idle timeout 会先切断，用户看到的是网络错误而非授权结果。
- **影响**：用户不点按钮，后端永远不知道；点了但没在浏览器完成，300s 后报 `lark-cli timed out`，toast 文案是「完成授权失败」而非「授权未完成，请重试」——**把「还没做」说成「失败」**。
- **对照**：**就是微信改造前的「我已扫码完成」按钮**，我们当时明确把它删掉换成自动轮询。飞书可以做等价改造：`auth/start` 后**平铺 spawn** 自动发起 `complete`（后台任务），前端同时以 3s 间隔轮询 `auth/status`（轻量命令）收敛 UI，用户零点击；或把 `complete` 改成会话式（仿 `bind` session）由前端轮询。
- **注**：并发调用 `lark-cli`（`--device-code` + `auth status`）是否安全，需实测；若不行则退化为「自动发起 complete + 界面显示等待中」并保留取消。

#### F6｜健康指标缺「收帧判据」，飞书页只能看「在不在册」

- **根因**：
  1. `common/src/api/system.rs:52-60` `LarkWsAppMetrics` 只有 `app_id`/`state`/`reconnect_count`；
  2. 对照 `:78-90+` `WechatPollChannelMetrics` 有 `state`/`rounds`/`last_poll_at_ms`/失败计数；
  3. `frontend/src/pages/system/health.rs:435` 飞书 Gauge 的告警条件只有 `a.state == "reconnecting"`；对照 `:99-134` 微信有 `wechat_channel_stale`（`last_poll_at_ms` 超 90s 视为疑似卡死）与 `wechat_gauge_color`。
- **影响**：F1/F2 的两种死亡在健康页上**显示为完全健康**（`connected`、连接数 1）。这恰好是微信那轮我们明确写在红线里的话——**「句柄在册 ≠ 在跑」**——飞书侧连对应的数据都没有。
- **修复方向**：`WsConnState` 加 `last_frame_at`（F2）后，`LarkWsAppMetrics` 同步补 `last_frame_at_ms`（+ 可选 `frames_received`），健康页给出与微信同构的 stale 判定。

#### F7｜绑定轮询循环「无条件 spawn」且缺代次守卫

- **根因**（`frontend/src/pages/finance/identity.rs:199-263`）：

  ```rust
  let handle_bind_start = move |_| {
      spawn(async move { ...lark_bind_start... });   // 任务 A：仅成功时 bind_polling.set(true)
      let running = bind_poll_running.read().clone();
      spawn(async move { loop { ... } });            // 任务 B：无条件启动
  };
  ```

  任务 B 不由任务 A 的成败决定；按钮 `disabled: starting_bind()`（`:384`）只覆盖取码阶段，取码返回后即可再次点击。
- **影响**：重复点击会叠加轮询循环（同一 `session_id` 被两条循环同时轮询 → `Done` 分支重复触发、Modal 重复弹）。当前靠「`bind_polling` 为 false 时任务 B 下一轮自行退出」兜住，属侥幸而非设计。
- **对照**：微信侧用 **`poll_gen` 代次守卫**（每次发起自增，旧循环据此自杀）+ `AtomicBool` 卸载守卫。飞书只有后半截（`:73-79` 的 `bind_poll_running`）。

#### F8｜绑定会话注册竞态：5s 启动窗口内「查不到、取消不掉、进程泄漏」

- **根因**（`src/pkg/lark_integration.rs:526-536`）：先跑「最多 5s 等验证 URL」的循环，**之后**才 `registry.write().await.insert(session_id, session)`。窗口内：
  - `bind/status` → 注册表里没有 → 返回 `NotFound`，前端轮询直接 `continue`；
  - `bind/cancel`（`:592-604`）→ `remove` 返回 `None` → `Ok(false)`，**不杀进程**；而 `child` 此时被局部变量 `session` 持有，5s 后照样被注册进表 —— 用户点了「取消」，进程仍在跑。
- **修复方向**：**先 `insert` 再等 URL**（把 5s 等待挪到 insert 之后，URL 由前端轮询补取，这条路径本来就已实现）。

### P2 —— 契约与展示一致性

#### F9｜`LarkBindStatusResponse` 三个字段恒 `None`

`src/handlers/finance/lark_integration/bind_status.rs` 返回体硬编码 `credential_id: None, channel_id: None, app_id: None`（注释说明「分支 B：secret 不可读，app_id 亦不返回」）。后果：

- 前端 `BindPollOutcome::Done`（`frontend/src/api/lark_integration.rs:109-130`）**不携带任何数据**，无法区分「分支 A 已自动建凭证」与「分支 B 需补填」；
- `frontend/src/pages/finance/identity.rs:241-252` 的 Done 分支**无条件**弹补填 Modal + toast「请手动补填 App Secret」，**即使后端确实已写入凭证**，用户会被告知去做一件已完成的事；
- `bind/status` 明确返回的 `app_id` 预填字段（`common/src/api/lark_integration.rs:271-272` 注释写明「分支 B，app_id 预填」）**从未被前端使用**，用户仍需手敲 App ID。

→ 二选一：**实现分支 A**，或按 YAGNI **删掉这三个恒 None 的字段**并把前端 Done 分支文案写成唯一事实（当前是「契约字段存在但恒空 + 前端假装有两分支」）。

#### F10｜凭证快照缺绑定/轮换时间

`common/src/api/lark_integration.rs:193-207` 的 `LarkCredentialSnapshot` 只有 `credential_id`/`name`/`app_id`/`is_default`/`channels`；对照微信侧 D9 已补 `user_id`/`base_url`/`created_at`/`updated_at`。数据现成（`UserCredentialPo` 有时间戳），前端凭证卡（`frontend/src/pages/finance/identity.rs:417-473`）目前看不到任何时间信息。

#### F11｜`judge_bind_status` 把未知状态当失败终止

`frontend/src/api/lark_integration.rs:119-130`：

```rust
match status {
    "pending" => Continue,
    "done" => Done,
    _ => Failed(...),          // ← 含未知状态
}
```

与微信「只认 4 态 → 空转到超时」是**方向相反的同一种穷尽性缺陷**：后端将来新增中间态（如 `waiting_scan`），前端会直接判失败并停轮询。对照微信：未识别状态应**按可继续处理但留证据**，终局态才收敛。

#### F12｜聚合状态两处 `.unwrap_or_default()` 静默降级

`src/handlers/finance/lark_integration/get_status.rs:47-49`：

```rust
.await
.map(|page| page.items)
.unwrap_or_default(),      // ← 查询失败 = 空列表 = 「暂无渠道引用」
```

渠道查询失败与「确实没有渠道」在前端**完全同形**。`:30-34` 的凭证列表同样形态。另：本 handler 直接跨两个 domain 拼装 DTO（微信侧走 `wechat_integration_status(ctx, user_id)` Domain 包装），属编排上浮，与分层约定不一致。

#### F13｜前端把「加载失败」当成「未绑定」

`frontend/src/pages/finance/identity.rs`：`integration_snapshot` 为 `None`（拉取失败或未返回）时走 `:376` 的 else 分支 → 应用卡显示「尚未绑定飞书应用凭证」（`:403-404`）、**「用户身份」区块整块空白**（`:501-507` 的 `if let Some(auth)` 不成立，既无状态徽章也无授权按钮）。用户会以为「本来就没有」，而实际是请求失败了。

#### F14｜入站渠道定位每条消息 N+1 查询

`src/service/dal/lark/impl.rs:409-445` `find_channel_by_lark_identity`：遍历全部启用飞书渠道，**每个渠道都调一次 `resolve_channel_app_id` → `load_credential_row` 查库**（未复用同文件 `:117-130` 已有的 `cached_credential` 机制）。该函数在**每一条入站消息**上执行。

#### F15｜接入域硬编码，不支持 Lark 国际版

`src/service/dao/lark/http.rs:28` `API_BASE = "https://open.feishu.cn"`、`src/service/dao/lark/ws.rs:104` 同一硬编码；无任何配置项。微信侧本轮刚补了 `base_url`（D9）。若目标用户含 Lark 国际版（`open.larksuite.com`）则完全不可用——**属能力缺口还是有意限定，需拍板**（见 §5）。

### P3 —— 能力面（登记不做）

**F16｜群聊与 @mention 完全不支持**：`src/models/events/lark.rs:143-145` `is_p2p()` 只放 `chat_type == "p2p"`，且事件结构**没有 `mentions` 字段**，无法识别「群里被 @」。这与飞书机器人最常见的用法（群内 @ 触发）不符，但属能力面扩展，与微信侧 P3（媒体/引用/typing）同级。

## 四、协议字段对账（未完成，需补 spec）

微信那轮之所以能收敛，是因为拿到了**官方实现源码**当 spec。飞书这轮缺这一环：

| 需对账项 | 现状 | 缺什么 |
|---------|------|--------|
| `close` 帧结构（是否含 `data.code`/`data.reason`） | `WsIncoming::Close` 是无字段单元变体（`src/service/dao/lark/ws.rs:69-71`） | 官方 SDK / 文档确认帧格式 |
| 是否需要应答服务端 Ping / 是否需要校验 Pong | 两条心跳机制都不完整（F2） | 官方 `wsConfig` 语义与推荐值 |
| 同 App ID 多连接的处置（拒绝 vs 踢旧） | 无专门处理（F1） | 官方约束原文 |
| 事件订阅是否需要 ACK（是否有服务端重推） | 当前无 ACK 概念，`on_frame` 恒 `Continue` | 长连接事件投递语义 |
| `message_id` 等响应字段名 | 未核对 | 官方 OpenAPI 响应体 |

**建议**：与微信同法，**取官方物证**（`lark-cli` 源码 / `@larksuiteoapi/node-sdk` tarball 解包 / 官方文档），确认后再改协议行为。在拿到 spec 之前，F1/F2 的修复应限于「补可观测性 (`last_frame_at` / close code 记录)」，**不擅自改心跳与重连策略**。
