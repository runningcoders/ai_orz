# docs/wiki — 代码现状百科（手工维护）

> **定位**：回答「代码现在是什么样」。四象限里的「是什么」一栏，阅读第一站。
>
> **维护方式**：**团队手工增量维护**。原 `repowiki`（Qoder IDE 插件）已下线，本目录不再由 IDE 生成，
> 也不会被任何工具覆盖——改什么就留下什么。
>
> **入口**：[INDEX.md](INDEX.md) 是全量页面索引（497 篇，自动生成）；本文件是语义入口与维护手册。

---

## 1. 目录结构

| 路径 | 是什么 | 谁维护 |
|------|--------|--------|
| `zh/content/` | **代码 Wiki 长文**（377 篇）：按主题分类的现状百科，单页 5~30 KB | 手工 |
| `knowledge/zh/` | **RAG 原子知识卡**（120 张）：单一主题的细粒度召回单元，带 frontmatter | 手工（走 5 级查重，见 `docs/DOCUMENTATION.md` §3） |

## 2. 三个日常动作

### 2.1 查：我要找的东西在哪一篇？

1. 先翻 [INDEX.md](INDEX.md) 的分类概览，定位到分类；
2. 再在该分类的表格里按标题找页（标题是 H1 或 frontmatter `name`，与内容一致）；
3. 找到页面后读正文；页面头部 `<cite>` 区列了它引用的源文件，可直接跳到代码。

> 不知道属于哪一类时的兜底顺序：`INDEX.md` 全文搜索关键词 → [../CODE_WIKI.md](../CODE_WIKI.md) 模块速查表 → 直接 grep 源码。

### 2.2 增：新增一篇

1. **先查重**（强制）：RAG 卡按 `docs/DOCUMENTATION.md` §3.2 的五级算法判定「合并 / 拆分 / 新建」；长文先 grep `zh/content/` 同名主题；
2. **落到正确位置**：`zh/content/<分类>/<页面>.md`；分类沿用现有 10 类（项目概述 / 架构设计 / 核心模块 / 基础设施 / 功能模块 / 数据模型 / 前端应用 / API 参考 / 测试指南 / 总纲与运维），不轻易开新类；
3. **补齐页面骨架**：`# 标题` + `<cite>` 引用文件清单 + `## 更新摘要` + `## 目录` + 正文章节 + `**章节来源**`；
4. **重建索引**：`make wiki-index`；
5. **跑门禁**：`make wiki-lint`（索引一致性）+ `make docs-lint`（路径写法）。

> 新增页**必须**在同一个提交里带上重建后的 `INDEX.md`，否则 `make wiki-lint` 会红。

### 2.3 改：代码变了，怎么让 wiki 跟上

这是手工维护唯一的真问题——**不是写不出文档，而是不知道哪一篇过期了**。当前采用「三条触发线」：

| 触发线 | 谁触发 | 做什么 |
|--------|--------|--------|
| **改代码时** | 改动者本人 | 提交前搜 `zh/content/` 与 `knowledge/zh/` 里出现该文件路径的页面，同步修订；`make wiki-lint` 通过即可提交 |
| **沉淀知识时** | Agent（见 `docs/DOCUMENTATION.md` §3） | 沉淀新知识节点时，同步落到 wiki 长文或 RAG 卡，不留「只在对话里说过」的结论 |
| **体检时** | 任意人 / 定时 | `python3 tools/wiki_index.py --stale` 输出「文档引用的代码路径已不存在」清单，按清单批量校正 |

`--stale` 是诊断输出**不参与门禁**（历史文档里含示例占位名，机器无法分辨真假），但它把「猜哪里过期」变成了「照清单核对」。

## 3. 维护五条纪律

1. **目录即真源**：`INDEX.md` 永远是派生物，任何人一条命令重建，禁止手工编辑（文件头有标记）；
2. **一页一主题**：长文讲「一个子系统/一个主题的现状」，不要把多个主题塞进一篇；
3. **引用用相对仓库根**：`src/service/dal/ontology.rs` 这种写法，不要写绝对路径、不要写 `file://`、行号用 `#L12-L34`（`docs_lint` 三条规则会拦）；
4. **不写「将来会怎样」**：现状写 wiki，设计动机写 `design/`，规划写 `plan/`——四象限分工不混；
5. **过期宁可删条目也不留错**：正文里被重构掉的路径/表名，发现就改；无法判断的，在页面顶部标一行 `> ⚠️ 待校正：<说明>` 让人知道。

## 4. 命令

```bash
make wiki-index    # 重建 docs/wiki/INDEX.md（新增/删除/改名页面后必跑）
make wiki-lint     # 门禁：索引与目录是否一致（不一致退码 1）
make docs-lint     # 门禁：文档路径写法（file:// / 绝对路径 / 冒号行号）

python3 tools/wiki_index.py --write   # 等价 make wiki-index
python3 tools/wiki_index.py --check   # 等价 make wiki-lint
python3 tools/wiki_index.py --stale   # 诊断：失效的代码路径引用
```

## 6. 已知局限（诚实记录）

1. **没有自动新鲜度判定**：文件 mtime 经 git clone 后会全部刷新，不可靠；本目录靠「三条触发线 + `--stale` 清单」人工把关，不做自动 stale 标记；
2. **`<cite>` 链接是「相对仓库根」**，在编辑器里从页面所在目录点开会失效（历史生成格式遗留），阅读时请以路径文本为准；
3. **62 张 RAG 卡没有 H1**，标题在 frontmatter `name` 字段——索引已兼容，但人工 grep 标题时需注意两种格式；
4. **`knowledge/zh/` 存在历史路径污染**：早期生成器把标题里的 `/` 当成目录分隔符（如 `pkg/http`），导致约 12 张卡嵌在 4~10 层目录里。索引按真实路径列出，未做搬迁（搬迁会打断既有 RAG 召回链接），如需治理另开批。
