## §1 概述

本卡片定义 AI Orz 项目的数据库迁移管理策略与工程约定。核心决策为：**采用单文件合并策略**——将历史 28 个增量迁移文件合并为 `migrations/20260420000000_initial.sql` 作为唯一基准 Schema，包含 21 张主表、8 张 FTS5 虚拟表、24 个触发器和全部索引。项目不再引入零散的新增迁移文件，所有表结构变更直接在基准文件中维护。

## §3 架构约定

### 3.1 单文件基准

项目迁移采用 Squash 策略，所有历史迁移已合并为单一 SQL 文件：

- `migrations/20260420000000_initial.sql` 是唯一的 Schema 来源
- 启动时 `sqlx::migrate!` 自动执行，保证幂等性
- 新环境首次启动直接获得完整 Schema，无需逐文件回放

### 3.2 STRICT 模式

所有 `CREATE TABLE` 强制加 `STRICT` 关键字：

```sql
CREATE TABLE IF NOT EXISTS organizations (
    id TEXT NOT NULL PRIMARY KEY,
    ...
) STRICT;
```

STRICT 模式确保 SQLx 编译期类型推断正确，禁止 TEXT NOT NULL DEFAULT '' 被推断为 `Option<String>`。

### 3.3 FTS5 自动触发器

每张支持全文检索的主表对应一张 FTS5 虚拟表和三个触发器：

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS skills_fts USING fts5(
    name, description, tags,
    tokenize = 'trigram'
);

CREATE TRIGGER IF NOT EXISTS skills_fts_ai
AFTER INSERT ON skills BEGIN
    INSERT INTO skills_fts(rowid, name, description, tags)
    VALUES (new.rowid, new.name, new.description, new.tags);
END;
-- skills_fts_ad (DELETE) + skills_fts_au (UPDATE) 同理
```

8 个 FTS5 虚拟表：short_term_memory_fts、knowledge_node_fts、skills_fts、tools_fts、messages_fts、tasks_fts、projects_fts、agents_fts。共 24 个触发器（每表 3 个：ai/ad/au）。

### 3.4 DAO 层模式

所有 DAO 遵循统一模式：

1. **trait 定义**：`src/service/dao/{entity}/mod.rs` 定义 `{Entity}Dao` trait
2. **SQLite 实现**：`src/service/dao/{entity}/sqlite.rs` 实现 trait
3. **单例管理**：`OnceLock<Arc<dyn Dao>>` 全局单例 + `init()` 初始化 + `new()` 测试用
4. **查询方式**：简单 CRUD 用 `sqlx::query!` 宏，动态条件用 `QueryBuilder`
5. **软删除**：所有 find/list 查询加 `AND "status" != 0`

```rust
static USER_DAO: OnceLock<Arc<dyn UserDao>> = OnceLock::new();
pub fn init() { let _ = USER_DAO.set(new()); }
pub fn dao() -> Arc<dyn UserDao> { USER_DAO.get().cloned().unwrap() }
pub fn new() -> Arc<dyn UserDao> { Arc::new(UserDaoSqliteImpl::new()) }
```

### 3.5 时间戳与索引

- 毫秒级 Unix 时间戳：`CAST(strftime('%s', 'now') * 1000 AS INTEGER)`
- 高频查询字段自动建索引（messages.created_at、short_term_memory_index.agent_id 等）
- 条件索引：`WHERE is_published = 1`、`WHERE status != 0` 等

### 3.6 测试隔离

集成测试通过 `tests/common/env.rs::init_full_test_env` 初始化：

- 用 `tempfile::tempdir()` 隔离基础数据目录
- 用 `tokio::sync::OnceCell` 串行化全局初始化
- 用 `InMemory` 向量存储避免 LanceDB 依赖
- DAO 单元测试用 `#[sqlx::test]` 宏创建独立内存库

## §4 硬约束

1. **禁止新增零散 migration 文件**：不得在 `migrations/` 下创建新的增量迁移文件，所有变更直接修改 `20260420000000_initial.sql`。
2. **单文件管理**：`20260420000000_initial.sql` 是唯一 Schema 事实源，任何表结构变更、索引新增、FTS5 调整必须在此文件中完成。
3. **所有建表必须 STRICT**：新增或修改 CREATE TABLE 遗漏 STRICT 为一级红线，会导致 sqlx 可空性推断错误。
4. **FTS5 必须配三触发器**：新增 FTS5 虚拟表必须同时创建 ai（INSERT）、ad（DELETE）、au（UPDATE）三个触发器。
5. **DAO 必须走统一模式**：所有 DAO 实现必须使用 OnceLock 单例 + trait 抽象 + `new()` 测试工厂方法。
6. **禁止裸写 SQL 迁移**：不得绕过 DAO 层直接写 SQL 操作数据库，所有数据访问通过 DAO/DAL/Domain 分层完成。
7. **时间戳必须毫秒级**：DEFAULT 表达式必须 `* 1000`，禁止秒级时间戳。
8. **软删除必须默认过滤**：所有 find_by_id/list_by_*/count_* 查询必须包含 `AND "status" != 0`。
9. **FTS5 关键词必须转义**：用户输入必须经 `escape_fts5_keyword` 转义后才能拼接到 MATCH 查询。
10. **迁移变更必须同步 .sqlx 缓存**：修改 Schema 或 DAO 查询后必须重新生成 `.sqlx/` 离线查询缓存，纳入 git 版本控制。
