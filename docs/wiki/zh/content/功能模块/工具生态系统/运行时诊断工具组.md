## 简介
运行时诊断工具组（Runtime Diagnostic Tool Suite）是 d1d1013f 变更落地的 Agent 自省能力增强模块。它把原本仅供前端面板 UI 轮询使用的 3 个 HTTP 接口（runtime-status / cancel-thinking / runtime-list），通过工具系统三层调用架构的 Builtin 协议路由，注册为 Agent 可直接调用的 Builtin 工具。这让 Agent 在思考过程中具备了三项新的自省能力：

1. **自我诊断**：Agent 可随时调用 `runtime_status` 工具查询自己当前思考轮次、已用时间、策略命中情况（hard_hit / soft_hit 列表）、累计 token 消耗等诊断元数据，用于自我调节或生成用户可理解的进度报告。
2. **主动取消**：Agent 诊断到 rounds 已超 soft 预警或业务判断需要提前终止时，可调用 `cancel_thinking` 工具，向自己的 cancel_token 写 true，触发策略引擎 PolicyMixed hard 层下一轮强制退出，exit_reason 前缀为 `cancel_by_agent_self`，与前端用户取消的 `user_cancel_frontend` 语义区分。
3. **协作感知**：同一 org 下多 Agent 协作场景中，Agent B 可先 `runtime_list` 找到 Agent A 的活跃 runtime，再 `runtime_status` 查 A 当前进度，决定自己是等待还是先处理独立子任务。

本章系统化阐述运行时诊断工具组的 10 节结构，覆盖数据结构、架构流程、边界红线、实现分析、扩展点、运维监控、Troubleshooting 及最佳实践。

## 核心数据结构与 API
运行时诊断工具组涉及的核心数据结构分为三层：**工具 schema（CoreTool impl）**、**Domain 层视图（DTO）**、**AOP registry 内存键值**。

### 工具 Schema 层（CoreTool trait）
三个工具的 JSON Schema 与对应 common DTO 严格对齐：

| 工具名 | tool:// URL | Schema 输入字段 | 对应 Handler DTO |
|--------|-------------|----------------|------------------|
| RuntimeStatusTool | `builtin/runtime_status` | agent_id: string, trace_id: string | RuntimeStatusRequest |
| CancelThinkingTool | `builtin/cancel_thinking` | trace_id: string, reason?: string | CancelThinkingRequest |
| RuntimeListTool | `builtin/runtime_list` | org_id: string, page?: i32, page_size?: i32 | RuntimeListRequest |

Schema 与 DTO 对齐由单测 `runtime_tool_schema_eq_handler_dto` 保证：对比 JSON Schema input 字段集合与 common DTO 字段集合（允许工具 schema 缺 org_id 这类 context 注入字段）。

### Domain 层视图
`RuntimeManagement` trait 在 management.rs 中暴露三个类型无关方法：
- `get_runtime_status(ctx, agent_id, trace_id) -> Result<RuntimeStatusView>`：返回 rounds/elapsed_ms/cancel_token 原子读/tokens/hard_hit_ids/soft_hit_ids
- `cancel_thinking(ctx, trace_id, reason) -> Result<CancelResult>`：CancelResult 含 success/already_cancelled/already_existed 三态，幂等
- `list_active_runtimes(ctx, org_id, pagination) -> Result<PagedResult<RuntimeListView>>`：只从 AOP think registry 取活跃键（防止 status=running 但进程已 panic 的僵尸 runtime 误报）

### AOP think registry 内存结构
`ThinkRuntimeRegistry`（pkg/aop/think/registry.rs）内维护：`Arc<RwLock<HashMap<(Uuid, Uuid), Arc<AgentThinkRuntime>>>>`，键 = `(org_id, trace_id)`。所有 AgentAwakeEvent 启动时 `register`、think_loop 正常/异常退出时 `unregister`。

## 架构原理与流程
### 注册链路
`register_runtime_tools(registry: &ToolRegistry, identity_domain: Arc<dyn RuntimeDomain>)` 在 `AgentCallContext` 构造时调用，内部三次 `registry.register(Arc::new(RuntimeStatusTool::new(domain.clone())))`，把三工具注入 Builtin 协议路由表。此注册位置与 Handler 层 HTTP 路由是对称的：
- HTTP 侧：Handler -> RuntimeDomain.xxx_method
- 工具侧：CoreTool.invoke() -> RuntimeDomain.xxx_method

两侧共享同一 Domain 方法单一事实源，DRY 原则避免字段漂移。

### 调用链路（以 runtime_status 为例）
1. Agent prompt 中推理需要查询状态，LLM 产出 tool_call: `{ name: "builtin/runtime_status", input: { agent_id: "...", trace_id: "..." } }`
2. 工具系统三层调用分发：Builtin 协议路由 -> RuntimeStatusTool.invoke(&ctx, input)
3. 工具内部先做**权限三层 gate**：判断 ctx.uid() 是否与 input.agent_id 属于同一 user（Agent 只查自己），或 ctx.role() == Admin/SuperAdmin 才放开
4. 通过后：`domain.get_runtime_status(ctx, agent_id, trace_id)` → 查 AOP think registry → 补业务字段 → 返回 RuntimeStatusView
5. 工具输出结构化 JSON：`{ "rounds": 15, "elapsed_ms": 32450, "hard_hit": ["MaxRoundsPolicy"], ... }`

### cancel_thinking 取消链路
工具内部 `cancel_token.store(true, Ordering::SeqCst)`（原子写，幂等）→ think_loop 下一轮构造 Metrics 时 `with("cancel", true)` → UserCancelPolicy.evaluate() 命中 → PolicyMixed hard_hit=true → `map_triggered_to_result` 根据 reason 字段判断前缀：
- reason = "cancel_by_agent_self" → 日志前缀 `cancel_by_agent_self:{用户传入reason}`
- reason 为空 → 视作前端用户取消 → 日志前缀 `user_cancel_frontend`

## 边界与行为红线
### 1. 分层架构边界
- ❌ **CoreTool.invoke 禁止直接查 DAO/DAL**：必须全走 RuntimeDomain 方法（management.rs）。工具构造时注入 `Arc<dyn RuntimeDomain>` 而非 DAO 实例，违反分层架构。
- ❌ **Domain 禁止跨层调用外部集成 Handler**：Domain 只做业务逻辑 + 权限 gate + AOP registry 查询，不直接调 HTTP Handler。

### 2. 安全与敏感信息边界
- ❌ **runtime_status 禁止返回思考 prompt / 中间输出**：状态视图只返回诊断元数据（rounds/tokens/策略命中列表），思考内容属于 WorkingMemory 敏感数据，工具侧无权访问。需要读思考过程走 WorkingMemory 专用记忆工具。
- ✅ **权限三层隔离强制**：
  - runtime_status：Agent 只查自己 agent_id 下的 trace_id；Admin 跨 agent 查询放开
  - cancel_thinking：Agent 只取消自己发起的 trace_id；Admin 可取消 org 下任意；SuperAdmin 跨 org
  - runtime_list：Agent 只看自己 org 下自己的 + 共享协作标记 runtime

### 3. 幂等与一致性边界
- ✅ **cancel_thinking 必须幂等**：同一 trace_id 连续取消 N 次 → 第 1 次 already_cancelled=false，第 2~N 次 already_cancelled=true，每次都 success=true。禁止「重复取消 = error」。
- ❌ **runtime_list 禁止返回已退出 runtime**：必须从 AOP think registry（仅活跃注册）取键集合；禁止走 SQL status=running 查（僵尸 runtime 误报）。
- ✅ **exit_reason 前缀强制约定**：cancel_by_agent_self 与 user_cancel_frontend 语义严格区分，前缀不一致=诊断分析错误。

关键实现点：
- **权限 gate 位置**：在 invoke 入口与 management.rs 方法内双重检查（invoke 先快速 fail，Domain 再兜底，防止调用方绕过工具层直接调 Domain）。

- **soft/hard 命中列表**：从 AgentThinkRuntime.last_eval_result 读最近一次 PolicyMixed 评估结果的 hard_hit_ids + soft_hit_ids，区分「强制退出即将触发」与「预警已触发但未退出」。

## 常见故障排查
### Troubleshooting 1：Agent 调用 runtime_status 总是 403 "forbidden: cannot query other agent's runtime"
**典型场景**：多 Agent 协作时 Agent B 想查 Agent A 的当前进度，调 runtime_status(agent_id=A 的 id, trace_id=xxx) 返回 403。

**排查步骤**：
1. 确认 ctx.role() 是否为 Member 角色 → Member 只允许查自己的 agent_id。如果 Agent B 是 Member 但需要查询 A → 走「runtime share」显式授权机制（见 §6 扩展点 2），或让 A 自己调用 runtime_status 后把结果写入共享 WorkingMemory slot。
2. 确认 trace_id 对应的 registry key 是否匹配权限：`management.rs` 中权限 gate 的 `assert_can_query_agent()` 函数——如果 A 与 B 同 org 且 runtime 有 shared_tag=true，B 应该能看到；检查 shared_tag 是否在 AgentAwakeEvent 时设置正确。
3. 源码位置：[src/service/domain/runtime/management.rs#L50-L80](src/service/domain/runtime/management.rs#L50-L80)（权限 gate 实现段）

### Troubleshooting 2：cancel_thinking 调用成功返回 `{ success: true }` 但 runtime 还在继续运行 10+ 轮
**典型场景**：Agent 诊断到 soft_warn 后调了 cancel_thinking，但从前端面板看到后续又跑了 N 轮才真正退出。

**排查步骤**：
1. 确认策略引擎 UserCancelPolicy 是否放在 PolicyMixed hard 组而非 soft 组：如果误放到 soft 组 → soft_hit=true 只会写 warn 日志，不会触发强制退出。检查 `src/pkg/policy/mixed.rs` 和 `policy_set!` 宏定义中 UserCancelPolicy 的分类。
2. 确认 cancel_token 的 Ordering：management.rs 中用 `Ordering::SeqCst`，UserCancelPolicy 读时也需要 `Ordering::SeqCst`（不是 Relaxed）——弱内存序下 CPU 缓存可能延迟可见。
3. 检查 think_loop 的最大轮次间歇：如果 think_loop 内部有 LLM HTTP 请求阻塞了 30s → cancel 信号要等该轮 LLM 返回后进入下一轮 evaluate 才会命中，属于正常延迟。如果期望「立刻中断 LLM 请求」，需要在 LLM client 实现超时 + cancel_token 触发时 abort（不在本工具范围，属于 LLMProvider 改造）。
4. 源码位置：
   - [src/service/domain/runtime/management.rs#L120-L160](src/service/domain/runtime/management.rs#L120-L160)（cancel_thinking 原子写段）
   - [src/pkg/policy/builtin.rs#L60-L90](src/pkg/policy/builtin.rs#L60-L90)（UserCancelPolicy 读段）
   - [src/service/domain/runtime/think_loop.rs#L80-L120](src/service/domain/runtime/think_loop.rs#L80-L120)（think_loop 每轮 evaluate 入口段）

## 最佳实践
1. **Agent 自我健康检查节奏**：建议每 10 轮调用一次 runtime_status 做自我诊断，不要每轮都调（额外开销 + 占用 tool call slots）。触发 soft_hit 时或 elapsed_ms > 30s 时再调是合理节奏。
2. **cancel_thinking reason 传业务含义**：Agent 主动取消时 reason 不要传空，写成结构化字符串如 `cancel_by_agent_self:soft_context_overflow_in_round_42`，便于 exit_reason 日志分析统计根因分布。
3. **协作场景先 list 再 status**：Agent 想了解协作方进度时，先 `runtime_list(org_id)` → 过滤共享协作标记 → 拿到 trace_id 再 `runtime_status(agent_id, trace_id)`，直接猜 trace_id 大概率 403 或 not_found。
4. **Handler 与工具的单测对称**：新增 runtime 诊断能力，Handler 的单测与 Tool 的单测用同一组 fixtures（同一段 Domain mock）——保证两侧对同一输入返回的字段集合完全一致。
5. **runtime_list 分页合理**：org 很大时活跃 runtimes 可能 100+，禁止 `page_size=9999` 一次全拉，默认 page_size=20，配合前端或 Agent 侧翻页。

## 结论与未来方向
运行时诊断工具组通过把 HTTP Handler 的 runtime 三接口注册为 Builtin 工具，赋予了 Agent 自省（runtime_status）、自主终止（cancel_thinking）和协作感知（runtime_list）三项能力。架构上严格遵守「Handler 与工具复用同一 Domain 方法」的单一事实源原则，权限 gate 在 Domain 层统一实现，避免了两套代码各自实现导致的字段漂移与安全漏洞。

**未来方向**：
1. **诊断工具链路深度整合**：把 runtime_status 的结果结构化沉淀为 WorkingMemory 的「自省日志」，Agent 下一轮思考自动能看到自己的趋势（rounds 飙升、soft_hit 连续 3 轮等），无需再手动调工具。
2. **跨节点 runtime 发现**：当前 AOP think registry 是内存 HashMap，仅单节点；部署为多实例集群时，runtime_list 需要通过 Redis pub/sub 广播 runtime 上下线事件，聚合全局活跃列表。
3. **诊断视图可视化**：把 runtime_status 的 JSON 结果通过前端 MarkdownRenderer + Mermaid 渲染为实时仪表盘（当前 rounds 进度条、hard/soft_hit 命中时间线、token 消耗饼图），Agent 可输出到聊天窗口供人类用户直观查看。
