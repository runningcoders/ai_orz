## 简介
本地文件安全与工作区隔离是 6b883e37 变更落地的两个联动改造，为 AI Orz 多用户/多组织下 Agent 文件操作提供**双重安全防线**：

**防线 1：存储层（目录结构拆分）**
原方案全局共享 `{AI_ORZ_HOME}/workspace/{org_id}/` —— 同一 org 下所有用户的上传文件、Agent 产物、附件等混放，Agent A 能随便读 Agent B 上载的 attachment；6b883e37 改造为**用户维度工作区**：`{AI_ORZ_HOME}/workspace/{user_uid}/{org_id}/` 且拆分为 4 个子目录：
- `uploads/`：用户前端上传的原始文件
- `agent_outputs/`：Agent 运行产生的临时产物
- `shared/`：org 级共享目录（显式标记 shared=true 时复制过去）
- `attachments/`：task/project 绑定的附件，元数据进 DB，物理文件在 user 目录下

**防线 2：工具层（BoundaryChecker 前缀校验）**
即使目录结构调整了，仍需在涉及文件系统的三个 Builtin 工具（shell_exec / file_read / file_write）的 invoke 入口加入**路径规范化 + 前缀白名单校验**，防止：
- `../../etc/passwd` 路径逃逸
- 绝对路径裸访问 `/root/.ssh/id_rsa`
- 跨 user 目录访问 `../user_B/agent_outputs/secret.txt`
- Unicode 归一化绕过 / symlink 指向边界外等高级攻击

双重隔离 = 即使目录结构未来改了，BoundaryChecker 仍能作为第二道防线；反之即使 BoundaryChecker 有 bug，目录结构 user 分离也降低跨用户损害半径。

整个项目任何模块拼工作区路径，**必须走上述函数**，禁止业务代码里手工拼。

### SecurityBoundaryChecker 与 CleanPath
```rust
pub struct SecurityBoundaryChecker {
    pub user_workspace_root: PathBuf,
    pub shared_root: PathBuf,
    pub allow_system_tmp: bool,
    pub write_only_user_dirs: bool, // Member 写 shared 禁止
    pub role: Role,
}

pub struct CleanPath(PathBuf); // 私有 inner，外部 crate 无法构造，newtype 屏障

impl SecurityBoundaryChecker {
    pub fn enforce(&self, path: &Path) -> Result<CleanPath, SecurityError>;
}

pub enum SecurityError {
    PathEscape { raw: String, canon: String },
    CrossUserAccess { target_uid: Uuid, expected_uid: Uuid },
    SymlinkOutsideBoundary { link: String, real_target: String },
    NotRegularFile { file_type: String },
    SessionQuotaExceeded { used: u64, limit: u64 },
    WriteDeniedToShared { role: Role },
}
```
CleanPath 没有公开的 From<PathBuf> / From<String> impl，只能通过 enforce() 得到——**类型系统层面保证 IO 函数只接受合法路径**。

### 三个文件工具的 enforce 接入点
| 工具 | enforce 位置 | 额外限制 |
|------|-------------|----------|
| shell_exec | cwd（current working directory）→ 强制 enforce；默认 cwd = agent_outputs_dir | cwd 强制过；allow_network / allow_root 独立 gate |
| file_read | target_path → enforce；禁止 symlink；mime type 白名单（文本型 md/txt/json/csv/rs/ts/js/yaml 等） | 二进制（图片/PDF/elf）强制拒绝，防止 base64 让 token 爆炸 |
| file_write | target_path → enforce；只允许 agent_outputs_dir / uploads_dir（禁止 shared 写 for Member） | 单文件 ≤ 50MB / session 累计 ≤ 500MB（按 uid 维度 session 级） |

## 架构原理与流程
### 路径构造统一出口原理
`src/pkg/paths.rs` 是 pkg 层公共基础工具，**单一事实源**：未来路径从 `workspace/{uid}/{org}` 改为 `workspace/v2/{uid}/{org}`，全仓 60+ 调用零修改，只改 paths.rs 一处。

路径函数全部基于 `ai_orz_root()` 向上拼，不依赖 PWD——避免用户 cd 到子目录运行脚本时相对路径错位。

### SecurityBoundaryChecker.enforce 流程
```
enforce(raw_path)
  │
  ├─► 1. dunce::canonicalize(path)
  │     ① symlink 展开
  │     ② . / .. 消除
  │     ③ Windows UNC 兼容
  │     ④ 失败 = 文件不存在 / 权限不足 → SecurityError
  │
  ├─► 2. 前缀匹配（顺序：白名单命中任一即通过）
  │     ├─► canon.starts_with(user_workspace_root) → ✅ 用户工作区
  │     ├─► canon.starts_with(shared_root)        → ✅ 共享目录（写权限看 write_only_user_dirs gate）
  │     ├─► allow_system_tmp && canon.starts_with(std::env::temp_dir()) → ✅ 系统临时
  │     └─► 以上均不命中 → ❌ PathEscape / CrossUserAccess
  │
  ├─► 3. 写权限二次 gate（仅 file_write / shell_exec cwd 写场景）
  │     ├─► write_only_user_dirs = true && role = Member && canon 在 shared_root 下 → ❌ WriteDeniedToShared
  │     └─► 否则 → ✅
  │
  └─► 4. 返回 CleanPath(canon) → 下游 IO 函数签名只接受 CleanPath 类型
```

### 类型屏障（新类型主义）
storage/local_file.rs 的 IO 签名：
```rust
pub fn read_file(clean: CleanPath) -> Result<Vec<u8>>;
pub fn write_file(clean: CleanPath, content: &[u8]) -> Result<()>;
```
下游工具 file_read/file_write 必须先 enforce → 拿到 CleanPath → 才能调 IO。**从类型系统保证：没 enforce 的路径编译不过**，不是靠「代码 review 相信大家都调 enforce」。

## 边界与行为红线
### 硬红线 1：路径构造统一
- ❌ **禁止业务代码手工拼工作区路径字符串**：`grep "workspace/" src/`（paths.rs 自身除外）应 0 命中；任何业务模块里的 `format!("workspace/...")` 必须改成 `paths::xxx_dir(ctx, org_id).join(...)`。

### 硬红线 2：类型屏障
- ❌ **禁止 CleanPath 暴露 From<PathBuf> 或 inner() 后随意修改**：CleanPath 的 inner 字段是 `pub(crate)` 级别，外部 crate 无法构造；下游拿到 CleanPath 后若做 `.join("../")` 则必须重新 enforce。

### 硬红线 3：攻击向量覆盖
- ✅ **强制 12 条路径逃逸攻击矩阵全通过**：① ../../etc/passwd ② /root/.ssh/id_rsa 绝对 ③ symlink /tmp → workspace 内 ④ Unicode %2F 归一化 ⑤ Windows `..\\` ⑥ 嵌套多重 a/b/../../c ⑦ 尾部加斜杠+空格 ⑧ 多字节字符 ⑨ cd /tmp 后相对写（cwd enforce 先）⑩ symlink 链 A→B→C→/etc ⑪ file_write ../../../etc/motd ⑫ shell_exec cwd=/proc。12 条全返回 SecurityError。
- ✅ **共享目录写权限分级**：Member 写 shared_dir → 拒绝；Admin → 允许；SuperAdmin → 允许。

### 硬红线 4：分层架构
- ❌ **禁止 file_read/file_write 工具在 BoundaryChecker 外部直接调用 std::fs**：必须通过 storage::read_file(clean: CleanPath)。
- ✅ **磁盘配额 session 级按 uid 维度**：用户 A 写 400MB 不影响用户 B 写 400MB；第 2 次 300MB 触发 500MB SessionQuotaExceeded。

### SecurityBoundaryChecker.enforce 关键段
```rust
pub fn enforce(&self, path: &Path) -> Result<CleanPath, SecurityError> {
    // 1. canonicalize（展开 symlink + 归一化）
    let canon = dunce::canonicalize(path)
        .map_err(|e| SecurityError::PathEscape { raw: path.display().to_string(), canon: e.to_string() })?;

    // 2. 前缀匹配
    let in_user = canon.starts_with(&self.user_workspace_root);
    let in_shared = canon.starts_with(&self.shared_root);
    let in_tmp = self.allow_system_tmp && canon.starts_with(&std::env::temp_dir());

    if !in_user && !in_shared && !in_tmp {
        return Err(SecurityError::PathEscape {
            raw: path.display().to_string(),
            canon: canon.display().to_string(),
        });
    }

    // 3. CrossUserAccess：交叉 user_uid 检测（如果路径包含 workspace/{other_uid}/）
    if let Some(uid_from_path) = extract_user_uid_from_path(&canon) {
        if self.expected_user_id.is_some() && uid_from_path != self.expected_user_id.unwrap() {
            return Err(SecurityError::CrossUserAccess {
                target_uid: uid_from_path,
                expected_uid: self.expected_user_id.unwrap(),
            });
        }
    }

    // 4. Write gate（仅写场景）
    if self.enforce_write_gate && in_shared && matches!(self.role, Role::Member) {
        return Err(SecurityError::WriteDeniedToShared { role: self.role.clone() });
    }

    Ok(CleanPath(canon))
}
```

### shell_exec cwd enforce
```rust
fn invoke_shell_exec(&self, ctx: &AgentCallContext, input: ShellExecInput) -> ToolResult {
    // cwd enforce：未指定则 agent_outputs_dir
    let cwd_raw = input.cwd.clone().unwrap_or_else(||
        paths::agent_outputs_dir(ctx, ctx.org_id()).to_string_lossy().into()
    );
    let checker = SecurityBoundaryChecker::for_user(ctx);
    let clean_cwd = checker.enforce(Path::new(&cwd_raw))?; // ❌ PathEscape 直接 fail

    // 子进程 current_dir = clean_cwd
    let mut cmd = Command::new(&input.script);
    cmd.current_dir(clean_cwd.inner());
    // ... 后续执行
}
```
关键点：enforce 通过后才设置 current_dir，**防止 Agent 试图 `cwd="/proc"` 或 `cwd="../../"` 绕过**。

## 常见故障排查
### Troubleshooting 1：file_read 读不到明明在 user_uploads_dir 下的文件，报错 SecurityError(PathEscape)
**典型场景**：用户前端上传文件后，Agent 读附件时报路径逃逸。通常是 uploads 目录的 symlink 被 Docker / K8s mount 挂载到另一块盘，canonicalize 后真实路径落在 user_workspace_root 之外。

**排查步骤**：
1. 打印 debug：`dbg!(dunce::canonicalize(target_path).unwrap())` → 看真实 canon 路径是什么。
2. 如果 canon 路径是 `/mnt/efs/uploads/xxx` 但 user_workspace_root 是 `/home/ai_orz/.ai_orz/users/xxx/workspace/xxx/uploads`（两者都是同一目录但一个是 symlink 到 mount 点、一个是 symlink 母目录相对）→ 这是常见 mount 场景。
3. 修复：在 SecurityBoundaryChecker 构造时，把 mount 点路径作为 `extra_whitelist_roots: Vec<PathBuf>` 追加，enforce 时额外判断 `extra_whitelist_roots.iter().any(|r| canon.starts_with(r))`。
4. 源码位置：[src/service/domain/tool_execution/sandbox.rs#L80-L140](src/service/domain/tool_execution/sandbox.rs#L80-L140)（enforce 前缀匹配段）

### Troubleshooting 2：旧业务代码（6b883e37 之前写的）把附件路径写成 `workspace/{org_id}/attachments/`，迁移后新代码读不到，路径 not found
**典型场景**：6b883e37 前的 attachment DB 元数据里存的是旧全局路径格式，新 storage/local_file.rs 用 paths::user_attachments_dir 拼路径 → 两边不一致，读不到文件。

1. 扫 attachment DB 表，取 10 条记录的 file_path 字段，确认格式是旧 `workspace/{org_id}/attachments/` 还是新 `users/{uid}/workspace/{org_id}/attachments/`。
2. 如果有旧格式残留 → docs_migrate 对应迁移写一个 DB 级脚本：

//   new_path = file_path.replace("workspace/{org_id}", "users/{created_by}/workspace/{org_id}")

## 结论与未来方向
用户维度工作区改造 + 安全边界检查通过「存储层目录拆分 + 工具层类型屏障 enforce」双保险，为 AI Orz 多用户场景下 Agent 文件操作提供了**零穿透**的安全基础。CleanPath 新类型主义把原本「相信开发者会调检查」变成「编译期不允许跳过」，从根本上解决了路径逃逸风险。

**未来方向**：
1. **SELinux / AppArmor 系统级 LSM 兜底**：当前是用户态 enforce；未来部署侧配合容器级 SELinux 规则（AI Orz 进程只能写 ~/.ai_orz/ + /tmp，其它 write 系统调用内核拒绝）作为用户态之外的第三道防线。
2. **细粒度文件访问审计**：所有 file_read/file_write/shell_exec 成功执行后的 file_path + size + uid → 追加写入独立 DuckDB `file_access_audit` 表，事后追溯「Agent X 在 Y 项目下读了哪些敏感文件」。
3. **Serverless 工作区挂载**：部署到多租户 SaaS 时，每个 org 的工作区目录通过 FUSE 动态挂载到对象存储（S3 / OSS）；BoundaryChecker 的前缀匹配保持不变，下层 FUSE 对 Agent 透明。
