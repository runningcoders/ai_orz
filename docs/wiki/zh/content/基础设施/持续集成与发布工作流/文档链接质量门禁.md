## 简介
文档链接质量门禁（fc5454e3 变更）是 AI Orz 4-docs 完整链（Design/Plan/Wiki/RAG）的基础设施级支撑模块，解决了 4 类历史积累问题：

**问题 1：链接格式不统一**
- 存量文档中 mix 多种链接格式：`file:///Users/aman/Technology/rust/ai_orz/docs/wiki/...`、`src/pkg/foo.rs:15-42`（旧冒号行号）、`docs/archive/plan-archive/../design/thinking.md`（相对路径未归一化）→ grep 统计同一份文档在不同格式下 4 种写法，RAG 召回无法对齐。

**问题 2：伪协议与绝对路径死链接**
- 历史 v1.0 SKILL 时代产物中大量 `file:///` 伪协议和 `/Users/aman/...` 本机绝对路径 → 其他用户机器或 CI 环境全是死链接。

**问题 3：四类互引缺失**
- Design 文档没有指向 Wiki 长文和 RAG 卡的回链；RAG 卡 source_files[] 只填了代码锚点没填 Wiki/Design/Plan 路径 → 四类闭环断裂，AGENTS §2.1.2 四类互引原则形同虚设。

**问题 4：前端点击 404**
- Wiki 文档中点 markdown 链接 404：代码路径没有前端路由、相对路径 design 文档直接跳静态文件 404、XSS 风险链接 `javascript:` 无防护。

fc5454e3 交付了**三件套**解决上述问题：
1. **DocLinkClassifier（common crate，前后端共用）**：统一字符串 parse + 分类 + 归一化。
2. **docs_lint（独立 Rust bin，CI 门禁）**：3 条规则 0 violation 门槛，PR 不合规直接 fail。
3. **docs_migrate（独立 Rust bin，存量修复）**：pulldown-cmark AST 级安全迁移，默认 --dry-run 预览 diff 才落盘。

## 核心数据结构与 API
### LinkKind 枚举（8 类分类）
```rust
#[non_exhaustive]
pub enum LinkKind {
    RepoRelative { path: String, line_range: Option<(u64, u64)> },
    WikiLong(String),
    DesignDoc(String),
    PlanDoc(String),
    ArchiveDoc(String),
    RagCard(String),
    ExternalHttp(String),
    FileProtocol { raw: String },
    LegacyColonLineNumber { path: String, line_start: u64, line_end: Option<u64> },
    Invalid(String),
}

pub struct ClassifiedLink {
    pub kind: LinkKind,
    pub normalized: Option<String>, // normalize_to_repo_relative 结果（若可归一）
    pub safe_to_render: bool,
}
```

### classify + normalize 双入口
```rust
pub fn classify(raw_target: &str) -> ClassifiedLink;
pub fn normalize_to_repo_relative(raw: &str) -> Result<String, ClassifyError>;
pub fn repo_relative_from_absolute(abs_path: &Path, repo_root: &Path) -> Option<String>;
```
- classify 只负责「判类型」，不做归一副作用。
- normalize 幂等：输入已合法 RepoRelative 原样返回；输入 LegacyColon / FileProtocol → 归一化后标准形式；重复调用结果相同。

## 架构原理与流程
### DocLinkClassifier 单一事实源原则
```
             ┌──────────────────────┐
             │ common/src/doc_link │
             │   classify() 唯一    │
             │  normalize() 唯一    │
             └─────────┬────────────┘
                       │
     ┌─────────────────┼─────────────────┐
     ▼                 ▼                 ▼
 docs_lint rules   docs_migrate   前端 MarkdownRenderer
 （判断违规）      （判断需迁移）  （判断点击行为）
```
**三方绝不独立写 regex 分类**——如果分类漂移（比如前端认为某链接是 WikiLong，docs_lint 认为 RepoRelative）→ 唯一修法 = 改 common/src/doc_link.rs 一处，三处齐受益。

### docs_lint CI 流程
```
PR / push main
    │
    ▼
make ci-docs-lint  →  scripts/tools/docs_lint.sh
                            │
                            ▼
                    cargo run -p docs_lint -- --root . --rules all
                            │
                            ├─► rule1 illegal_path_prefix（file:/// + 裸绝对路径）
                            ├─► rule2 legacy_colon_line_number（path:15-42）
                            └─► rule3 missing_cross_reference（四类互引不全）
                            │
                   exit_code = total_violations
                       0 → ✅ CI 通过
                      >0 → ❌ CI fail，打印 violation 摘要（文件 + 行号 + 建议修复）
```

### docs_migrate 迁移流程
```
用户运行 scripts/tools/docs_migrate.sh（默认 --dry-run）
    │
    ▼
cargo run -p docs_migrate -- --dry-run --output-diff
    │
    ├─► 遍历 docs/**/*.md（353 Wiki + 54+ RAG 卡 + 20+ Design/Plan）
    │
    ├─► 每篇 md：pulldown-cmark 解析 Event 流
    │       │
    │       ├─► Migration1 file_protocol_cleaner：
    │       │     Event::Start(Tag::Link(_, target, _)) 时
    │       │     target.starts_with("file://") → 删前缀 → repo_relative_from_absolute
    │       │
    │       └─► Migration2 path_to_hash_fragment：
    │             target 匹配 path:15-42 → 重写 path#L15-L42
    │             （单行→#L15，范围逆序#L42-L15自动#L15-L42 swap）
    │
    ├─► 输出 unified diff（不改文件）
    │
    └─► 用户确认 diff 正确 → 重跑去掉 --dry-run → --apply → 落盘
```
**AST 级替换**：只改 markdown link 的 target，不误伤代码块、yaml frontmatter 中的冒号行号。

## 边界与行为红线
### 红线 1：分类器唯一性
- ❌ **禁止 docs_lint / docs_migrate / 前端各自独立写 classify regex**：3 端独立写 regex = 一定会漂移。`grep "LinkKind" common/src/doc_link.rs -c` 以外出现 = 直接 fail。

### 红线 2：Migrate 安全
- ❌ **禁止 migrate 工具非 dry-run 默认**：`docs_migrate` CLI 不加参数 = 默认 `--dry-run` + 大红色 warning stdout 提示「未应用修改，加 --apply 才落盘」，输出 unified diff。
- ❌ **禁止 Migrate 改动 yaml frontmatter**：虽然 frontmatter 的 source_files 里 path:Ln-Lm 理论也需要迁移，但 pulldown-cmark 只识别 markdown 正文，不碰 yaml frontmatter——frontmatter 修复走独立 Python 一次性脚本，YAML 中 `- src/file.rs#L15` 的 `#` 是注释，不能被误伤。

### 红线 3：docs_lint 规则下限
- ✅ **RAG 卡 source_files[] 四类齐全**：每张 RAG 卡 source_files[] 数组 = ① ≥1 src/**/*.rs（代码）② ≥1 docs/wiki/zh/content/**（Wiki 长文）③ ≥1 docs/{design,plan,superpowers/plans}/**（设计/计划）④ Level2/3/4 卡额外 ≥1 兄弟/主/总卡（docs/wiki/knowledge/**）——四类各 ≥1，少于 = missing_cross_reference violation。
- ✅ **LinkKind 分类 + normalize 单测 50+ 矩阵**：doc_link_classify_matrix 至少 50 条，覆盖 8 类 + normalize 幂等 + 前后端一致。

### 红线 4：向后兼容
- ✅ **DocLinkClassifier Backward Compat**：`LinkKind` 枚举 `#[non_exhaustive]`，新增变体不破下游。历史 legacy 输入 classify 结果永远与 v2 预期一致（10 条 BC 单测）。

## 详细实现分析
### classify 解析逻辑（内部伪代码）
```rust
pub fn classify(raw: &str) -> ClassifiedLink {
    // 优先级从上到下，先匹配上的先返回
    if raw.starts_with("http://") || raw.starts_with("https://") {
        return ClassifiedLink { kind: ExternalHttp(raw.into()), ... };
    }
    if raw.starts_with("file://") {
        return ClassifiedLink { kind: FileProtocol { raw: raw.into() }, safe_to_render: false };
    }
    // LegacyColon：排除 http 端口号后匹配 path:15-42
    if looks_like_legacy_colon_line_number(raw) {
        let (p, s, e) = parse_path_and_line_numbers(raw);
        return ClassifiedLink { kind: LegacyColonLineNumber { path: p, line_start: s, line_end: e }, ... };
    }
    // RepoRelative：存在 hash fragment #Lx-Ly 的抽出来
    if let Some((path_part, line_range)) = parse_repo_relative_and_line_fragment(raw) {
        // 进一步判断 path_part 是 docs/wiki/ → WikiLong 等
        let kind = if path_part.starts_with("docs/wiki/knowledge/") { RagCard(path_part) }
                   else if path_part.starts_with("docs/wiki/zh/content/") { WikiLong(path_part) }
                   else if path_part.starts_with("docs/design/") { DesignDoc(path_part) }
                   else if path_part.starts_with("docs/archive/plan-archive/") { PlanDoc(path_part) }
                   else { RepoRelative { path: path_part, line_range } };
        return ClassifiedLink { kind, normalized: Some(format!("{}...")), safe_to_render: true };
    }
    // ... 剩余分支
}
```

### path_to_hash_fragment AST 级迁移（核心）
```rust
fn run_on_ast(&self, events: Vec<Event>, ctx: &MigrateCtx) -> Vec<Event> {
    events.into_iter().map(|e| match e {
        Event::Start(Tag::Link(link_type, target, title)) => {
            // 只在 target 上做 normalize_to_repo_relative
            match normalize_to_repo_relative(&target) {
                Ok(new_target) if new_target != target => {
                    ctx.report_diff(&target, &new_target); // 记录 diff
                    Event::Start(Tag::Link(link_type, new_target.into(), title))
                }
                _ => Event::Start(Tag::Link(link_type, target, title)),
            }
        }
        // Code / CodeBlock / Html / InlineHtml → 原样返回（防止误伤）
        other => other,
    }).collect()
}
```
关键点：**只改 Tag::Link 的 target**——代码块里 `src/pkg/file.rs:15` 举例片段、yaml frontmatter 的 source_files 数组、mermaid 图表中 `src/pkg/xxx:10` 全部不会被 regex 裸替换误伤。

### missing_cross_reference_rule 逻辑（RAG 卡）

fn check_rag_card_yaml(&self, source_files: &[String]) -> Vec<Violation> {
    let has_code = source_files.iter().any(|f| f.starts_with("src/"));
    let has_wiki = source_files.iter().any(|f| f.starts_with("docs/wiki/zh/content/"));

        if !has_wiki { Some(Violation::new("missing wiki long article ref")) } else { None },
        // ... 其余判断

}

## 常见故障排查
### Troubleshooting 1：docs_migrate --apply 运行后，yaml frontmatter 的 source_files 数组报错「YAML parse error: found comment where value expected」
**典型场景**：旧 v1 SKILL 产物中 RAG 卡 source_files 有 `- src/pkg/policy/mod.rs:15-42`，用户误以为 migrate 也会改 YAML，结果自己写了个 sed 全局替换把 YAML 里的 `:15` 换成了 `#L15`，YAML 解析 `#` 是注释 → parse error。

**排查步骤**：
1. 确认 migrate 设计：migrate 走 pulldown-cmark，**只识别 markdown 正文 Event 流**，不动 YAML frontmatter。官方说明：「YAML 的修复走独立一次性 Python 脚本 yaml_frontmatter_fix.py」（已经在 fc5454e3 前置跑完，残留的个别 YAML 漏网需要手动修）。

## 最佳实践
1. **写文档时只用标准格式 RepoRelative**：代码锚点 `src/pkg/foo.rs#L15-L42`（相对仓库根，`#Lx-Ly` 行号 fragment）；设计文档 `docs/design/thinking.md`；Wiki 长文 `docs/wiki/zh/content/功能模块/xxx.md`。永远不写 `file:///`、绝对路径、冒号行号。
2. **提交前本地先跑 docs_lint 快速规则**：`scripts/tools/docs_lint.sh --rules illegal_prefix,legacy_colon`（5s 内跑完），missing_cross_reference 慢但 CI 会验。
3. **新增 RAG 卡时 source_files[] 四类齐全再合 PR**：写 RAG 卡时，卡写完立刻在 source_files[] 里填 ① 3-8 代码锚点 ② Design/Plan 真实或占位 ③ Wiki 长文真实或占位 ④ Level3 兄弟卡；四类齐了再 commit，避免 missing_cross_reference CI fail 返工。
4. **Migrate 前 --dry-run 预览 diff 存到 PR 评论**：跑 docs_migrate 产生大 diff 时（首次 400+ 文件），把 diff 统一 patch 作为 PR 评论附件，让 reviewer 一眼确认「只改 link target，没改代码片段内容」。
5. **前端 Blocked 提示要包含修复指引**：FileProtocol 拦截 toast 文本 = "链接格式已废弃(`file://` 伪协议)，请运行 scripts/tools/docs_migrate.sh --apply 修复"；用户知道下一步是什么，不会只报「无法点击」手足无措。

## 结论与未来方向
文档链接质量门禁三件套通过「common crate 单一事实源分类器 + CI 硬门禁 + AST 级安全迁移」把 AI Orz 文档体系从「4 种格式混写、伪协议绝对路径泛滥、四类互引断裂、前端点击 404」历史状态统一到「单一标准相对路径 + #Lx-Ly 行号 fragment + 四类互引全闭环」的健康状态。fc5454e3 已跑 docs_migrate --apply 全仓，理论 0 violation 基线已建立。

**未来方向**：
1. **Internal Broken Link Checker**：现有 missing_cross_reference 只检查「有没有字段」，未来扩展 broken_internal_link_rule：对 docs/ 文档中所有 RepoRelative 链接，walkdir 检查路径是否存在（glob 存在性 + 代码文件实际存在），不存在 = violation，从「格式合规」升级到「内容指向不 404」。
2. **VS Code 插件实时检查**：写 docs 时 VS Code 插件后台跑 classify，检测到 LegacyColon / FileProtocol 立即标红波浪线 + quick fix "一键 normalize_to_repo_relative"，提交前就修好，不用等 CI 返工。
3. **自动 PR suggestion bot**：CI 扫到 docs_lint violations 时，bot 自动对 PR 发 review comment 并附带「建议修复的 unified patch」，用户点击 `Apply suggestion` 一键修复。
