# 本体认知

知识图谱是**蜂巢共享**的：你写的每个节点、每条关系，其他 Agent 都能读到。而「同一件事用不同的词」是图谱最大的慢性病——三个人分别写下「部署流程」「上线步骤」「发布规程」，图谱里就有了三条互不相认的知识，检索漏召回、遍历走不通、统计永远差一截。**本体就是治这个病的共享词汇约定**：它不产生新知识，它让已有的知识能被稳定地找到和连起来。

本技能讲两件事：**写的时候怎么选词**（每个 Agent 每轮都在做），以及**词表本身怎么演进**（治理侧，人审为主）。写记忆的具体操作（节点粒度、tags 桥梁、六种新旧交替模式）在**记忆认知**技能，本技能不重复。

## 一、先搞清我们有什么：不是 OWL 推理机，是受控词表

**别期待不存在的东西**。我们没有描述逻辑、没有自动分类、没有 `subClassOf` 传递闭包。当前本体域提供的是：

| 能力 | 有 / 无 |
|---|---|
| 受控词表（节点类型、关系词、属性定义）+ 同义归并 | ✅ 有 |
| 结构化属性（类型/基数/值域/载体约束 + 按值反查） | ✅ 有 |
| 漂移检测（写后自动认证 + 漂移看板） | ✅ 有 |
| 词表自动进 Prompt 引导你用词 | ✅ 有 |
| 自动推理、隐含关系推导、一致性证明 | ❌ 无，也不要等它 |
| 启动时自动改存量图谱 | ❌ 不做（违反设计决策；存量修正走确定性派生/人审提报） |

所以本体的价值全部落在**用词一致性**和**结构化可检索**上。判断一个词该不该进词表，标准也就只有这两条：**它会不会被反复用来描述同一类东西**（一致性），**它会不会被用来筛选或比较**（结构化）。

## 二、四选一：这个信息该落成什么

写知识前先做这一次判别。选错的成本是后期要拆节点重连边，远比多想 10 秒贵。

| 形态 | 判断标准 | 例子 |
|---|---|---|
| **实体类**（TBox） | 一类可重复出现的节点类型；`{X}` 里能填很多具体实例 | `project`、`规范`、`踩坑经验` |
| **知识节点**（ABox） | 某个具体实例；有独立生命、会被单独检索到 | 「ai_orz 的记忆搜索链路」 |
| **关系**（TBox 定类型，ABox 建边） | 另一端是**图谱里有独立生命**的节点 | `contains`、`depends_on`、`opposite` |
| **属性**（TBox 定定义，ABox 存值） | 另一端只是个**值**（数字/日期/枚举/短文本），不是实体 | `confidence=0.9`、`status=active`、`effective_from` |

**属性 vs 关系**是最容易搞混的一对，记住一句：*把另一端删掉，这边还说得通吗？* `depends_on → 某个模块` 删了模块这句话就废了 → 关系；`confidence=0.9` 里的 0.9 不是一个节点 → 属性。

**属性 vs 写进正文**同理：这条事实**会被用来筛选/比较/排序**吗？会 → 属性（可 `property_filters` 精确召回）；只是背景描述 → 正文。把「这个方案我试过三次都失败」里的「三次」写进正文，就永远搜不到「失败次数 ≥ 2 的方案」。

## 三、选词的四条硬规矩

1. **先查词表再落笔**。`list_ontology_classes` / `list_ontology_relation_types` / `list_ontology_properties` 是常驻工具，写前扫一眼比事后返工便宜。Prompt 里的【本体词表】区块已经是同一份数据的摘要——它每轮都在，别视而不见。
2. **同义归并优于新建**。碰到一个词表里没有的说法，先问：*它是不是已有概念的另一种叫法？* 是 → 记下来按规范词写（治理侧会补同义映射），**不要**为它新建类。词表爆炸（一堆只用过一次的类）是本体的头号失败模式，比词表不足更难救。
3. **term_key 用 snake_case，一旦创建不可改**。它是规范标识，不是展示名；改 key 会让所有历史节点的引用悬空。
4. **词表不贴切就自拟，别硬套**。**语义准确 > 用词规范**。词表是引导不是牢笼——用了不贴切的词，代价是把不同东西塞进同一个类型里，比临时造词严重得多。自拟之后把缺口记下来走提报（见第五节）。

## 四、理论侧：五条原则（Gruber 1995，按我们的场景改写）

本体工程学界公认的评判标准，落到「我要不要新建这个词」这个日常决策上：

| 原则 | 人话版本 |
|---|---|
| **清晰性** | 定义要让别人读完就知道什么该归进来、什么不该。描述里别引入另一个没定义的词 |
| **一致性** | 新词的用法不能和既有词冲突。`contains` 是父→子，就别拿它表达「引用」 |
| **可扩展性** | 加新词不该要求推翻已有词。如果你发现要改一堆旧定义才说得通，说明抽象层级选错了 |
| **最小编码偏差** | 概念层别绑实现细节。别把数据库列名、枚举值、文件路径当本体词——实现会变，概念不该跟着变 |
| **最小本体承诺** | 只承诺必需的约束。能不确定就不确定：别为了「以后可能用得上」加一堆没人填的必填属性和枚举白名单 |

配套一条实践守则：**软退役，不硬删**。词表条目废弃走 retire（软删除），历史节点仍用旧词但**依然可解释**；硬删会让存量图谱变成一堆无法解读的字符串。retire 只挡新写，不改存量——这正是要的效果。

## 五、漂移与治理：发现词表不对怎么办

### 漂移是怎么被发现的（不用你管，但要知道）

你每次写记忆，框架会发一个 `memory.terms.written` 事件，`OntologyCertifyConsumer` **异步**做「写后认证」：把你写的原始词 trim + 小写后依次查同义映射 → 查规范词 → 都没有就判为 Drift，把**原文**记进 DuckDB。两个关键语义：

- **只记原文，不记结论**。解析结论会随词表进化而过期，原文不会 —— 所以今天判为漂移的词，明天补了同义映射就**自动愈合**，不需要清洗历史数据。
- **是异步的**。写完立刻去看板查不到刚才那条，不是失效，是还没消费到。

### 你能做 / 不能做

| 场景 | 你的动作 |
|---|---|
| 读完看板发现一批漂移词 | **提报**：把「原文 → 应该归到哪个规范词」整理出来，发给负责图谱治理的管理员 Agent / 用户。你**不自己建** |
| 发现自己造了个词，词表里其实有近义的 | 用 `update_memory` 把节点类型改成规范词；正文里保留原说法不影响 |
| 确信需要一个全新的类 / 关系类型 | 同上，走提报。附带：你会用它描述什么、举 2~3 个实例、和现有哪个词的区别 |

**为什么不让你自己改词表**：词表是蜂巢共享的全局约定，一个 Agent 的错误建词会污染所有人的图谱，且 retire 只挡新写、历史照旧，没有低成本回收路径。语义判断类变更（「这两个词是不是一回事」）按设计走**提案 + 人审**。写侧工具（`create_ontology_*` / `update_*` / `retire_*` / `delete_ontology_synonym`）因此不对你开放——它们需要 `ontology_management` 包授权，你调不到是正常的，不是工具坏了。

### 常驻的读侧工具（这些你随时可以调）

| 工具 | 用途 |
|---|---|
| `list_ontology_lexicon` | 词表注入视图（三段 + 属性段），与 Prompt 里那份同源 |
| `list_ontology_classes` / `list_ontology_relation_types` / `list_ontology_properties` / `list_ontology_synonyms` | 分页查词表，可按状态 / 关键词过滤 |
| `get_ontology_drift_dashboard` | 漂移看板：Top 漂移词（含出现频次与多 Agent 来源信号）、关系维词表覆盖率、节点漂移占比 |
| `list_ontology_drift_class_details` / `list_ontology_drift_relation_details` | 漂移明细下钻（哪些节点在用漂移词） |

看板的正确读法：**Top 漂移词按「频次 × 来源 Agent 数」排序**，一个词被多个 Agent 反复用到 = 词表缺这个概念，提报优先级最高；只被一个 Agent 用过一次 = 大概率自拟，先确认它是不是真需要独立存在。

### 配套工具属于同一个 `ontology` 主题域

词表不是孤立的，真正消费它的是这一组工具——它们和上面的读侧工具同属 `ontology` tag：`save_long_term_memory`（写节点类型/关系/属性，词表主消费方，也是写后认证的触发点）、`update_memory`（给既有节点补关系与属性）、`search_memory`（`property_filters` 按属性精确召回）、`settle_memory`（沉淀出知识节点，漂移词的主要来源）、`get_knowledge_graph`（遍历，边类型来自关系词表）。它们都是常驻能力，不需要装包；`install_tool_pack("ontology")` 装的正是这一整套（**不含**改词表的管理类工具——治理侧是独立授权面）。

## 六、反模式清单

| ❌ 反模式 | 为什么错 |
|---|---|
| 把具体实例建成类（`ai_orz_项目` 当 `node_type`） | 类要可复用；实例是节点。这么做的结果是每来一个新项目词表就涨一条 |
| 用属性表达关系（`related_module="X"`） | 属性存的是值不是实体，图谱遍历走不到 X，FTS 才能碰运气搜到 |
| 为一次性说法新建类 | 词表爆炸；先用规范词 + 正文保留原说法，等它出现第三次再提议建类 |
| 硬套不贴切的词 | 语义准确优先；把不同的东西塞进同一个类型，比临时造词危害大 |
| 直接改存量节点来「修正历史」 | 语义判断类修正走提报 + 人审；你自己改的是**你的理解**，不是共享事实 |
| 期待本体自动推理出隐含关系 | 没有推理机。要连的边，显式建 |
| 写完立刻去看板找刚才那条漂移 | 写后认证是异步 AOP，稍后再查 |

## 七、与记忆认知的分工

- **本技能**：用什么词、词不够怎么办、词表怎么演进 → 面向**词汇与约定**
- **记忆认知**：节点粒度、tags 桥梁、六种新旧交替、搜索与遍历 → 面向**内容与结构**

写一条知识时，通常先过本技能的「四选一」，再按记忆认知的沉淀流程落库。属性写入的具体门闩（类型错/基数超硬拒，值域/载体/未定义仅告警照写）与 `property_issues` 回执，见**记忆认知**的「结构化属性」小节。
